# iOS 内存管理底层笔记
> 前置：基于 Objective-C 2.0，Runtime 源码（objc4），不涉及 Swift ARC 额外逻辑

## 一、基础概念：为什么需要内存管理
OC 对象分配在**堆(Heap)**，由开发者管理生命周期；栈上内存自动回收。
核心目标：保证对象不用时释放，避免：
1. 内存泄漏：对象没人释放，一直占用堆内存
2. 野指针：对象已经释放，指针还访问它（EXC_BAD_ACCESS）

OC 采用**引用计数（Reference Count）** 模型：
> 引用计数 = 有多少个指针“正在使用这个对象”
> retain：计数 +1；release：计数 -1；计数 == 0 时调用 dealloc，释放内存

> 注意：引用计数只是管理对象生命周期，**不管理对象内部成员的内存**。

两种模式：
- **MRC（手动引用计数）**：手动写 retain / release / autorelease
- **ARC（自动引用计数）**：编译器在编译期自动插入 retain/release/autorelease，运行时逻辑和 MRC 一致，**ARC 不是运行时机制，是编译期语法分析 + 代码插入**

## 二、对象的内存布局 & isa 与 NONPOINTER_ISA
objc 对象本质结构体（简化版）
```c
struct objc_object {
    Class isa;
};
```
在 64 位系统下，isa 是一个 64bit 数字，不再单纯是一个指针，开启 **NONPOINTER_ISA**（默认开启）：
把 isa 的 64 位比特位拆分复用，一部分存类指针，一部分**直接存储引用计数、是否弱引用、是否正在释放、是否有 C++ 析构函数等标记**，以此提升性能，减少访问 SideTable 的开销。

64位 isa 位域（objc4）：
- 0 bit：nonpointer 标记位，1=开启NONPOINTER_ISA
- 1 bit：has_assoc 是否有关联对象
- 2 bit：has_cxx_dtor 是否有C++析构/自定义dealloc
- 3 bit：shiftcls 类指针（33bit）
- 其他位：引用计数、weakly_referenced、deallocating 标记

⚠️ 重点：
**isa 里面存储的引用计数是有限容量的，计数值溢出之后，引用计数就不再存在 isa 里，转移到 SideTable 里单独维护。**
这是很多人容易踩的误区：不是所有对象的引用计数都存在 isa。

## 三、SideTable：引用计数、弱引用表的真正容器
objc 内部维护一个 SideTable 数组，多个 SideTable（数量和CPU核数相关），用哈希表分散对象，解决锁竞争，提升并发性能。
```c
struct SideTable {
    spinlock_t slock;          // 自旋锁，保护读写
    RefcountMap refcnts;       // 引用计数哈希表（key:对象地址，value:计数值）
    weak_table_t weak_table;   // 弱引用表
};
```
### 什么时候走 SideTable 的 RefcountMap？
1. isa 内部的引用计数存不下（溢出）
2. TaggedPointer 对象：**没有 isa，没有引用计数，不走 SideTable**
3. 类对象、元类对象：特殊处理，一般不参与常规引用计数

### weak_table_t 弱引用表
弱引用表是一个哈希结构：
- key：对象地址
- value：存放所有指向这个对象的弱指针地址数组

当对象 dealloc 时：
1. 在 weak_table 找到这个对象对应的所有弱指针
2. 把每一个弱指针的值置为 `nil`
3. 清除这条弱引用记录
👉 这就是 weak 自动置 nil 的底层来源！

> 所以 weak 变量访问时不是直接读对象，每次都要查弱引用表；weak 比 __unsafe_unretained 安全，但有开销。
> __unsafe_unretained：不加入弱引用表，对象销毁后指针变成野指针，不会置 nil。

## 四、TaggedPointer：特殊的“伪对象”
64位 iOS 引入 TaggedPointer，用来优化小数字、小字符串对象（NSNumber、NSString）。
特点：
1. **不在堆上分配内存！没有 malloc，没有 free**
2. 指针本身的值，直接存数据 + 标记位，不是指向堆内存的地址
3. **没有引用计数，不需要 retain/release，不走 SideTable**
4. 线程安全，不需要锁
5. 当值超出容量（字符串太长、数字太大），自动变回正常堆对象

识别：指针地址最高位标记。
面试高频坑：
```objc
NSString *s1 = @"abc";
NSString *s2 = [NSString stringWithFormat:@"abc"];
// 短字符串有可能是TaggedPointer，打印指针地址能看出特征
```
> TaggedPointer 是苹果巨大的性能优化，大量小对象场景减少堆分配开销。

## 五、AutoreleasePool 自动释放池
### 1. 作用
autorelease 不是立刻 release，而是把对象**加入自动释放池**，等到池子出作用域（drain）的时候统一 release。
MRC 时代手动用；ARC 下编译器依然会大量插入 autorelease。

### 2. 底层结构：不是数组，是双向链表
```c
struct AutoreleasePoolPage {
    magic_t magic;
    id *next;          // 下一个可存放autorelease对象的位置
    pthread_t thread;  // 归属线程，autorelease池和线程绑定！
    struct AutoreleasePoolPage *parent;
    struct AutoreleasePoolPage *child;
    // 这里后面紧跟着存放对象指针的内存
};
```
- 每一页是 4096 字节（一页内存页大小）
- `next` 指针类似栈顶，每 autorelease 一个对象，next 往前移动，存入对象地址
- 当一页满了，新建 child 页，串成链表
- `@autoreleasepool {}` 在底层插入一个 **POOL_BOUNDARY（哨兵标记）**，不是对象

### 3. 什么时候 drain（释放）？
1. `@autoreleasepool{}` 大括号结束：从 next 往回遍历，直到遇到 POOL_BOUNDARY，逐个给对象发 release
2. Runloop 循环：主线程 Runloop 每次循环休眠前，会自动 drain 自动释放池
> 所以：主线程里，不手动加 autoreleasepool，临时 autorelease 对象也会在 runloop 周期释放，但大量循环创建临时对象会瞬间撑高内存！

### 4. 经典场景：循环内大量创建临时对象
```objc
// 坏写法，循环产生大量autorelease对象，要等runloop才释放
for (int i=0; i<100000; i++) {
    NSString *str = [NSString stringWithFormat:@"%d", i];
}
// 优化：包一层 @autoreleasepool，每一轮循环结束就释放
for (int i=0; i<100000; i++) {
    @autoreleasepool {
        NSString *str = [NSString stringWithFormat:@"%d", i];
    }
}
```
### 5. 重要规则
- AutoreleasePool **和线程绑定**；子线程如果没有 Runloop，也没有手动 @autoreleasepool，autorelease 对象不会被释放，直接内存泄漏！
- `autorelease` 只是把对象加入池子，引用计数 +1（和 retain 一样，只是 release 时机延后）

## 六、ARC 修饰符底层区别（__strong / __weak / __unsafe_unretained / __autoreleasing）
ARC 修饰符本质是告诉编译器：在合适位置插入 retain / release / autorelease 代码。

| 修饰符 | 行为 | 底层 |
|---|---|---|
| __strong | 默认，持有对象，指针赋值时编译器插入 retain；指针离开作用域插入 release | 走正常引用计数 |
| __weak | 不持有，加入 SideTable 弱引用表；对象销毁自动置 nil | 查询 weak_table，有锁开销 |
| __unsafe_unretained | 不持有，不加入弱引用表；对象销毁不置 nil，野指针 | 无额外开销，不安全 |
| __autoreleasing | 存放 autorelease 对象；一般用于 NSError** 传参 | 对象加入 autorelease pool |

> NSError **error 参数为什么是 __autoreleasing？
> 编译器自动把 `NSError **` 补成 `NSError * __autoreleasing *`，方法内部生成的 error 对象放到自动释放池，由调用方的池管理生命周期。

### 循环引用（Retain Cycle）
__strong 互相持有就会循环引用：A 强引用 B，B 强引用 A，两者引用计数永远不能到 0，都无法 dealloc，内存泄漏。
解决方案：一端改成 __weak / __unsafe_unretained。
常见场景：Block 捕获外部变量、Delegate。
> Block 捕获 __strong 变量会 retain；捕获 __weak 不会 retain。

> 补充：Block 在堆上才会捕获变量；栈 Block 不持有。

## 七、对象销毁流程：dealloc 底层调用链路
当 `refcount == 0`，runtime 触发 dealloc：
1. `objc_object::rootDealloc()`
2. 判断：是否 TaggedPointer？是，直接返回，不处理
3. 判断是否有 C++ 析构、关联对象、弱引用：
   - 如果都没有：快速释放，直接 free 内存（fast path，性能很高）
   - 如果有：走慢速流程 `object_dispose()`
4. `object_dispose`：
   - 调用 objc_destructInstance：
     - 执行 C++ 析构函数
     - 清除关联对象（objc_removeAssociatedObjects）
     - 清除弱引用表：找到所有 weak 指针，置 nil
5. 最后调用 free 释放堆内存

⚠️ 关键点：
- dealloc 是 runtime 调用，不是你手动调用；MRC 手动调用 dealloc 是错误行为
- dealloc 里面**不能直接访问 self 的 __weak 变量以外的成员**，对象正在销毁；不要在 dealloc 里做耗时、异步操作
- dealloc 调用后，内存已经释放，属于野指针

## 八、内存布局：iOS 进程内存分区
一个进程地址空间大致分为：
1. **代码段 Text**：只读，可执行指令（Mach-O）
2. **数据段 Data**：全局变量、静态变量、常量字符串
3. **堆 Heap**：malloc / alloc 分配，向上增长，OC 对象在这里（除 TaggedPointer）
4. **栈 Stack**：函数局部变量、函数帧，向下增长；栈内存自动回收，大小很小（主线程栈几MB）
5. 共享库、内核区域

> 栈溢出：递归太深、超大局部数组；堆溢出：越界写 malloc 内存。

## 九、常见坑 & 面试高频问答梳理
1. Q：ARC 下还存在引用计数吗？
A：存在，ARC 只是编译器自动插代码，运行时引用计数逻辑和 MRC 完全一致。

2. Q：weak 的实现原理？
A：SideTable 的 weak_table，对象销毁时遍历弱引用链表，把所有 weak 指针置 nil。

3. Q：为什么 weak 不能修饰局部变量？语法上可以，但局部变量出作用域就销毁；weak 主要解决循环引用。

4. Q：autoreleasepool 什么时候释放？Runloop 休眠前 drain、@autoreleasepool 结束 drain；子线程无 runloop 必须手动加池。

5. Q：TaggedPointer 为什么线程安全？
A：没有堆对象，没有引用计数，不需要修改共享数据，无锁。

6. Q：isa 里面一定存引用计数吗？
A：NONPOINTER_ISA 下，计数小的时候存在 isa；溢出后放到 SideTable 的 RefcountMap。TaggedPointer 没有 isa。

7. Q：关联对象什么时候释放？
A：在对象 dealloc 的 objc_destructInstance 里面统一清除，不是跟着属性生命周期走。

8. Q：Block 循环引用：为什么 weakSelf 之后还要加 strongSelf？
A：weakSelf 随时可能 nil；在 block 内部 strongSelf 一下，保证 block 执行过程中对象不会中途释放，执行完自动 release。

## 十、总结
> alloc → 堆上开辟 objc_object → isa（NONPOINTER_ISA存类信息+少量rc）→ retain 增加引用计数，溢出后存入 SideTable.RefcountMap；
> weak 指针注册到 SideTable.weak_table；
> autorelease 将对象加入 AutoreleasePoolPage 链表；
> 引用计数到0 → rootDealloc → object_dispose → 析构C++、清理关联对象、清空weak指针 → free 堆内存。
