# 编译流程总览：从源码到机器码
> 一句话：**编译器把源程序依次经过词法分析、语法分析、语义分析、中间表示、优化、代码生成、汇编与链接，最终变成可执行文件；前端负责理解语言，后端负责适配硬件，IR 是两者的分界线。**
> 定位：讲通用编译流水线与核心概念，不绑定某一种语言；示例以类 C 语法和 LLVM 风格为主。

## 一、全景流水线
```
源码
 │
 ├─ 词法分析 Lexer      → Token 流
 ├─ 语法分析 Parser     → 语法树 CST/AST
 ├─ 语义分析 Sema       → 带类型与符号信息的 AST
 ├─ 中间表示 IR         → 三地址码 / SSA / LLVM IR
 ├─ 优化 Optimizer      → 等价的更优 IR
 ├─ 代码生成 Codegen    → 目标机器指令 / 汇编
 ├─ 汇编 Assembler      → 目标文件 .o
 └─ 链接 Linker         → 可执行文件 / 动态库
```
| 阶段 | 输入 | 输出 | 典型问题 |
|---|---|---|---|
| 词法 | 字符流 | Token | 非法字符、字符串未闭合 |
| 语法 | Token | AST | 缺分号、括号不匹配 |
| 语义 | AST | 带类型 AST | 未定义变量、类型不匹配 |
| IR | AST | 三地址码/SSA | 控制流复杂、优化机会 |
| 优化 | IR | 更优 IR | 保守与激进的取舍 |
| 代码生成 | IR | 汇编 | 寄存器不足、指令选择 |
| 链接 | 目标文件 | 可执行文件 | 符号未定义、重复定义 |

> 解释器省略「代码生成之后的机器码」；JIT 在运行时做「IR → 机器码」；AOT 在构建期完成整条流水线。

## 二、词法分析：字符 → Token
词法分析器（Lexer/Scanner）把字符流切成有意义的单元：
```
let x = a + 12;
```
```
KEYWORD(let)  IDENT(x)  ASSIGN(=)  IDENT(a)  PLUS(+)  NUMBER(12)  SEMI(;)
```
### 1. 实现方式
- **手写**：状态机 + 循环，易控制错误位置与特殊规则（大多数生产编译器）；
- **正则 → NFA → DFA**：用正则描述 Token，自动生成状态机；
- **工具**：flex/lex、re2c、Ragel。

### 2. 关键规则
- **最长匹配（maximal munch）**：`>=` 不能被切成 `>` 和 `=`；
- 关键字通常在识别出标识符后再查表；
- 保留注释、行列号、文件位置，方便报错；
- 字符串、数字字面量、转义、Unicode 标识符是词法层的主要复杂度。

> Token 一般包含：类型、原始文本、值、位置区间。位置信息贯穿后续所有阶段。

## 三、语法分析：Token → AST
### 1. 文法
用上下文无关文法（CFG）描述语言结构：
```
expr   → term (("+" | "-") term)*
term   → factor (("*" | "/") factor)*
factor → NUMBER | IDENT | "(" expr ")"
```
- 终结符：`+`、`NUMBER` 等；
- 非终结符：`expr`、`term` 等；
- 产生式描述「如何展开」。

### 2. 语法树 vs 抽象语法树
- **CST（具体语法树）**：保留所有 Token，包括括号、分号；
- **AST（抽象语法树）**：只保留语义结构，丢弃冗余符号；
- 后续阶段通常只操作 AST。

`a + b * 12` 的 AST：
```
    +
   / \
  a   *
     / \
    b   12
```
### 3. 解析算法
| 方法 | 特点 | 代表 |
|---|---|---|
| 递归下降 | 手写、直观、易报错 | Clang、Go、大多数现代语言 |
| Pratt / 算符优先 | 处理表达式优先级 | 表达式解析、配置语言 |
| LL(1) | 自顶向下、看一个 Token | 教学、简单 DSL |
| LR(1)/LALR | 自底向上、表达力强 | yacc/bison、老式编译器 |
| PEG / Packrat | 回溯、易写 | 部分 DSL、解析库 |

### 4. 常见难点
- **歧义**：悬空 else、运算符优先级；用优先级/结合性声明或改写文法解决；
- **左递归**：自顶向下解析需要消除左递归；
- **错误恢复**：同步到分号/右括号，尽量继续解析而不是只报第一个错；
- **增量解析**：编辑器需要局部重解析（tree-sitter 等）。

## 四、语义分析：AST → 带语义的 AST
语法正确不代表程序合法。语义分析负责：
1. **符号表与作用域**：变量、函数、类型、模块的可见性；
2. **名称解析**：这个 `foo` 是局部变量、全局变量还是函数？
3. **类型检查**：赋值兼容、函数参数、返回值、泛型约束；
4. **类型推断**：`let x = 1` 推断为 `Int`；HM 算法用于 ML/Haskell/Rust 的部分场景；
5. **控制流检查**：未初始化变量、不可达代码、返回路径；
6. **所有权/借用检查**：Rust 的 borrow checker 属于语义分析的一部分；
7. **常量求值**：编译期计算 `const` 表达式。

输出通常是**带类型注解的 AST**，并可能生成诊断信息（warning/error）与源码位置。

## 五、中间表示 IR
### 1. 为什么需要 IR
- 把「语言相关」与「硬件相关」解耦；
- 同一前端可以接多个后端（x86、ARM、RISC-V、WASM）；
- 优化在 IR 上做一次，所有目标平台受益；
- 便于分析：数据流、控制流、依赖关系。

### 2. 常见形式
| 形式 | 特点 |
|---|---|
| 三地址码 TAC | 每条指令最多一个运算，易读易优化 |
| SSA | 每个变量只赋值一次，便于数据流分析 |
| 基本块 + CFG | 控制流图，优化与调度的基础 |
| LLVM IR | 强类型、SSA、模块化，生态成熟 |
| 字节码 | 栈式/寄存器式，JVM、Python、WASM |

`a + b * 12` 的三地址码：
```
t1 = b * 12
t2 = a + t1
```
SSA 形式：
```
t1 = b * 12
t2 = a + t1
```
（没有分支时与 TAC 相同；有分支时每个赋值点使用新版本 `x1`、`x2`。）

### 3. 基本块与控制流图
- **基本块**：顺序执行、只有一个入口和一个出口的指令序列；
- **CFG**：节点是基本块，边是跳转关系；
- 大多数优化都在 CFG/SSA 上做：到达定义、活跃变量、支配关系。

## 六、优化：等价的程序变换
### 1. 局部优化
| 优化 | 例子 |
|---|---|
| 常量折叠 | `3 * 4` → `12` |
| 常量传播 | `x = 3; y = x + 1` → `y = 4` |
| 代数化简 | `x * 1` → `x`，`x + 0` → `x` |
| 公共子表达式消除 CSE | 重复计算 `a * b` 只算一次 |
| 死代码消除 DCE | 删除无副作用且结果未使用的代码 |

### 2. 全局/循环优化
- **内联**：把小函数展开，减少调用开销、暴露更多优化；
- **循环不变量外提**：把循环内不变的计算移到循环外；
- **强度削弱**：`x * 2` → `x << 1`，`x % 2` → `x & 1`；
- **循环展开**：减少分支、提高指令级并行；
- **向量化**：把标量循环变成 SIMD；
- **尾调用优化**：复用栈帧，避免递归爆栈（取决于语言/编译器）。

### 3. 寄存器分配
- 目标机器寄存器有限，IR 中虚拟寄存器可能成百上千；
- **图着色**：变量是节点，冲突是边，颜色是寄存器；
- **线性扫描**：按活跃区间分配，速度快，JIT 常用；
- 寄存器不够时**溢出（spill）**到栈，性能下降。

### 4. 优化的边界
- 优化必须保持**可观察行为**一致；
- 未定义行为（UB）给了编译器很大自由度，也带来「优化后行为诡异」；
- `-O0/-O1/-O2/-O3/-Os` 是取舍，不是越高越快（代码膨胀、缓存失效）；
- 现代编译器还会做 PGO（profile-guided optimization）与 LTO（链接时优化）。

## 七、代码生成、汇编与链接
### 1. 代码生成
- 指令选择：用树覆盖/模式匹配把 IR 映射到目标指令；
- 寄存器分配：把虚拟寄存器映射到物理寄存器；
- 指令调度：重排指令，隐藏延迟；
- ABI：参数放在哪些寄存器、返回值、栈对齐、调用者/被调用者保存；
- 栈帧：局部变量、溢出槽、返回地址、canary。

### 2. 汇编与目标文件
汇编器把汇编转成目标文件：

| 段 | 内容 |
|---|---|
| `.text` | 机器指令 |
| `.data` | 已初始化全局/静态变量 |
| `.bss` | 未初始化全局/静态变量（不占文件空间） |
| `.rodata` | 只读常量、字符串 |

目标文件还包含：
- **符号表**：导出/未定义符号；
- **重定位表**：链接时需要修补的地址；
- 调试信息（DWARF）、异常表。

### 3. 链接
- **静态链接**：把库代码复制进可执行文件，部署简单、体积大；
- **动态链接**：运行时加载 `.so/.dylib/.dll`，共享内存、体积小，但依赖环境；
- **PLT/GOT**：位置无关代码（PIC）下，通过跳转表调用外部函数；
- 常见错误：`undefined symbol`、`duplicate symbol`、ABI 不兼容、库版本冲突。

## 八、执行模型：AOT、JIT、解释器
| 模型 | 编译时机 | 优点 | 缺点 |
|---|---|---|---|
| 解释器 | 运行时逐条解释 | 启动快、实现简单 | 执行慢 |
| AOT | 构建期编译 | 启动快、性能稳定 | 无法利用运行时信息 |
| JIT | 运行时编译 | 可做 Profile 优化、去虚拟化 | 启动预热、内存开销 |
| 混合 | 解释 + JIT 分层 | 兼顾启动与峰值 | 实现复杂 |

JIT 常见分层：
1. 解释器/模板 JIT：快速启动；
2. 基线 JIT：简单编译；
3. 优化 JIT：基于热点与类型反馈做激进优化；
4. 去优化（deopt）：假设失效时回退到解释器。

> WebAssembly 是「可移植的编译目标」：C/C++/Rust 先编译到 WASM，再由浏览器/运行时编译执行。

## 九、一个最小例子
源码：
```c
int f(int a, int b) {
    return a + b * 12;
}
```
Token：
```
INT IDENT(f) LPAREN INT IDENT(a) COMMA INT IDENT(b) RPAREN LBRACE
RETURN IDENT(a) PLUS IDENT(b) STAR NUMBER(12) SEMI RBRACE
```
AST：
```
Return
  Binary(+)
    Ident(a)
    Binary(*)
      Ident(b)
      Literal(12)
```
三地址码：
```
t1 = b * 12
t2 = a + t1
return t2
```
优化后（强度削弱）：
```
t1 = b << 3      // 8b
t2 = b << 2      // 4b
t3 = t1 + t2     // 12b
t4 = a + t3
return t4
```
伪汇编（x86-64 风格）：
```
f:
    lea  eax, [rsi + rsi*2]   ; b * 3
    lea  eax, [rdi + rax*4]   ; a + b*12
    ret
```
> 真实编译器会根据目标架构、寄存器压力、指令延迟选择不同实现，这里只示意「AST → IR → 机器码」的映射关系。

## 十、工具与实践
| 工具 | 用途 |
|---|---|
| `clang -E` | 只看预处理 |
| `clang -S -emit-llvm` | 输出 LLVM IR |
| `clang -S` | 输出汇编 |
| `clang -c` | 输出目标文件 |
| `llc` | LLVM IR → 汇编 |
| `objdump -d` | 反汇编 |
| `nm` / `readelf` | 查看符号与段 |
| flex/bison、ANTLR | 词法/语法生成器 |
| tree-sitter | 增量解析（编辑器） |
| LLVM、Cranelift、QBE | 后端/IR 框架 |

学习路径建议：
1. 写一个只支持整数四则运算的解释器；
2. 加变量、作用域、函数调用；
3. 生成三地址码，做常量折叠与 DCE；
4. 生成简单栈式字节码或 WASM；
5. 最后再研究 SSA、寄存器分配与 JIT。

## 十一、常见误区
1. ❌ 编译器一定比解释器快：短脚本、启动敏感场景解释器更合适；
2. ❌ AST 就是语法树：AST 是抽象后的结构，CST 才保留全部语法细节；
3. ❌ 优化越多越好：可能增加编译时间、代码体积，甚至降低缓存命中率；
4. ❌ 类型检查都在编译期：动态语言、JIT、运行时反射都会做类型检查；
5. ❌ 链接器不属于编译流程：它决定了最终可执行文件能否生成；
6. ❌ JIT 就是解释器：JIT 会生成机器码，解释器不会；
7. ❌ 未定义行为只是「结果不确定」：编译器可以基于 UB 做激进优化，行为可能完全出乎意料；
8. ❌ 前端/后端只是叫法：前端贴近语言，后端贴近硬件，IR 是两者的契约。

## 十二、总结
- 编译器的核心是**分阶段降低抽象**：字符 → Token → 树 → IR → 指令 → 可执行文件；
- 前端保证「程序合法」，中端保证「程序更优」，后端保证「程序能跑」；
- IR、CFG、SSA 是现代优化与代码生成的共同语言；
- 理解流水线，比背某个编译器的参数更有用。
