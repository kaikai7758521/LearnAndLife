# 自建RAG系统
> 整体思路：**先离线建索引，再在线做问答；Demo优先最小可用，再逐步加优化组件**

## 前置认知
自建RAG本质就是搭建两条流水线：**离线索引流水线（一次性/增量更新文档）**、**在线问答流水线（用户提问时执行）**
RAG Demo最简组件清单（跑通最小版本必备）：
1. 文档加载器：读取PDF/md/txt
2. 文本切分器（Chunker）
3. Embedding模型（把文字转向量）
4. 向量数据库（存向量+原文）
5. LLM（生成回答，可以用OpenAI/通义千问/LLama本地模型）
6. 调用胶水代码（Python为主，LangChain/LlamaIndex简化开发，也可以原生手写）

> 重要提醒：Demo一般是 **Naive RAG**；等Naive跑通，再叠加Query改写、BM25、Rerank升级到Advanced RAG。

# 离线阶段：构建知识库索引
## 步骤1：准备原始文档 & 文档加载
✅ 目标：把非结构化文件提取成干净文本
✅ 原理：PDF、Word、Markdown本身是富格式，里面有图片、表格、页眉页脚；加载器负责解析，提取纯文本流，给后续切分使用。
✅ Demo常用工具
- Markdown / txt：直接Python读取
- PDF：PyPDF2（简单）、pdfplumber（更好，保留表格文本）、Unstructured
✅ 注意事项 & 细节
1. ❌ 不要直接用扫描版PDF！扫描PDF是图片，文字不能直接提取，需要OCR（pytesseract/PaddleOCR），Demo阶段尽量只用**可复制文字的电子PDF**，降低难度；
2. 过滤噪声：页眉、页脚、页码、广告、重复标题、空白行；噪声会变成chunk，后续检索大量垃圾召回；
3. 保留元数据：记录文档名称、页码、章节，后面做引用溯源；
4. 表格是大坑：简易加载器经常把表格拆成乱序文字，Demo可以先避开复杂表格。

## 步骤2：文本切分 Chunking（RAG最容易翻车的环节）
✅ 目标：把超长文本切成小段Chunk，适配Embedding模型输入上限，同时尽量保证单块语义完整
✅ 原理：Embedding模型有最大token限制；全文直接向量化会超限；切分后每一块是独立检索单元。检索时召回chunk，而不是整篇文档。
✅ Demo最常用：**固定大小滑动窗口切分**（RecursiveCharacterTextSplitter）
参数：`chunk_size` 块大小、`chunk_overlap` 重叠长度
✅ 注意事项 & 细节
1. chunk_size不是越大越好，也不是越小越好：
    - 太小：语义断裂，单块信息不全，检索回来的片段缺少上下文
    - 太大：里面混杂多个无关主题，向量语义混杂，召回精度下降
    - Demo经验值：英文约500~1000token；中文建议300~600字
2. overlap（重叠）非常关键：避免一句话、一个知识点被切在两块中间，上下文断裂；一般设置为chunk_size的10%~20%；
3. 固定切分缺点：会把标题和正文、段落中间一刀切断；这也是Naive RAG天生短板；Advanced RAG会换成语义切分、按标题切分；
4. 优先按换行、句号、分号递归切，而不是粗暴按字符硬切（递归切分器优势）。

## 步骤3：Embedding 向量化
✅ 目标：文本chunk → 稠密向量，语义相近的文本向量距离更近
✅ 原理：Embedding模型是预训练文本表征模型，输入文本，输出固定维度浮点数向量；向量空间里距离越近=语义越相似；后续向量数据库靠距离做相似度检索。
✅ Demo选型
- 在线API：bge、text-embedding、通义embedding（简单，不用显卡）
- 本地：BGE系列（bge-small-zh，中文友好，推荐Demo用）
✅ 注意事项 & 细节
1. **查询和文档必须用同一个Embedding模型！** 致命坑：文档用A模型编码，用户query用B模型编码，向量空间完全不匹配，召回彻底失效；
2. Embedding也有输入上限，chunk不能超过embedding模型最大上下文；
3. 中文不要用英文embedding模型，表征效果极差；
4. 向量维度固定，比如BGE-small-zh是512维，存入向量库时维度不能乱改；
5. 成本：在线embedding按token计费，本地模型免费但是吃显存。

## 步骤4：写入向量数据库，建立索引
✅ 目标：存储【向量 + 原始chunk文本 + 元数据】，支持快速相似度检索
✅ 原理：向量数据库底层是近似最近邻搜索ANN（HNSW等索引）；暴力遍历太慢，ANN牺牲一点点精度换取百万级向量毫秒检索；
✅ Demo推荐轻量向量库（不用单独部署服务，嵌入式）
- Chroma（最简单，首选demo）
- FAISS（Meta，速度快，纯本地，无持久化需要自己存）
- Qdrant也有嵌入式模式
> 生产一般是Milvus、Qdrant服务端；Demo不要上重服务。
✅ 注意事项 & 细节
1. 持久化：Chroma可以本地磁盘保存，重启程序索引不丢；FAISS默认只在内存，要手动save/load；
2. 索引类型：Demo直接默认HNSW就行，不用调索引参数；
3. 不要存重复chunk：入库前简单去重，避免重复召回；
4. 元数据一起存：文件名、页码，后面回答可以输出来源。

> ✅ 到这里，**离线阶段结束**。文档已经变成向量索引，后续不需要重复跑（新增文档才需要增量入库）

# 在线问答阶段（用户提问链路，每次提问都会跑一遍）
## 步骤5：用户Query预处理
✅ 目标：把用户原始问句处理成适合检索的查询
✅ 原理：用户问题口语化、简短、有歧义；朴素RAG直接拿去检索；高级RAG在这里做改写、扩展、HyDE。
✅ Naive Demo做法：直接使用原query
✅ 注意事项 & 细节
1. 清理多余符号、表情、无关闲聊；
2. 多轮对话场景：要把历史对话摘要合并进query，不然用户追问时检索缺少上下文（Demo可以先做单轮，简化）；
3. 坑：问句很短（比如“流程？”）语义模糊，向量召回很容易跑偏，这是Naive RAG经典短板。

## 步骤6：检索召回 Retrieval
✅ 目标：用query向量，在向量库中找到Top-K最相似的chunk
✅ 原理：query经过同一个embedding模型转为向量，在向量库计算距离，返回距离最近K个片段
✅ Demo参数：Top-K，一般取3~6
✅ 注意事项 & 细节
1. Top-K不是越大越好：召回越多，塞进LLM上下文的噪声越多，token变贵、模型更容易被无关内容干扰；
2. 相似度 ≠ 相关性！向量只是语义相似，不代表内容能回答问题（这就是为什么后面会加Rerank）；
3. Naive RAG这里只有稠密向量检索；Advanced在这里加入BM25关键词检索多路召回。

## 步骤7：（可选，Demo一般省略）Rerank重排
> Naive Demo可以跳过，这一步属于Advanced RAG优化项
✅ 原理：召回出来的候选chunk交给Rerank交叉编码器，输入`query + chunk`成对打分，重新排序，过滤低分无关片段；Rerank模型比embedding区分相关性能力强很多。
✅ 注意事项：重排会增加延迟、额外调用成本；Demo跑通后再加。

## 步骤8：Prompt组装（把问题+检索片段打包喂给LLM）
✅ 目标：构造约束Prompt，告诉LLM**只能基于给的参考材料回答，不能编造**
✅ 原理：LLM本身不知道外部文档，我们把证据片段塞进上下文窗口，加上指令约束，实现接地（grounding）。
✅ Demo参考Prompt模板
```
你是文档问答助手，请严格根据下面提供的参考材料回答用户问题。
如果参考材料里面没有对应信息，请直接说“知识库中没有找到相关内容”，不要编造、不要自己发挥。
参考材料：
{retrieved_chunks}

用户问题：{user_query}
```
✅ 注意事项 & 细节
1. 上下文窗口上限！所有chunk+prompt+问题总token不能超过LLM最大窗口；召回多了会截断，截断会丢证据；
2. 约束词一定要写，不然LLM会无视材料，调用自身参数知识乱编（幻觉）；
3. chunk之间加分隔符（---），方便LLM区分不同片段；
4. 不要一次性塞几十段材料，LLM容易忽略其中部分内容。

## 步骤9：LLM生成答案，返回结果 + 来源
✅ 目标：LLM阅读prompt，输出答案；附带引用来源
✅ 原理：标准自回归生成；LLM在这里只做阅读理解、摘要、整合，不再凭空调用训练知识。
✅ 注意事项 & 细节
1. 即使加了约束，依然会幻觉！RAG不能彻底消灭幻觉；
2. 输出时带上元数据（文档名、页码）方便核验；
3. 可以增加后校验：让LLm自查答案是否和参考材料冲突（高级玩法，Demo不用）。

# 最简Demo技术栈推荐（开箱就能写）
Python + LangChain + Chroma + BGE Embedding + 任意LLM
```
# 极简依赖
langchain
langchain-chroma
sentence-transformers  # 本地BGE embedding
pdfplumber
openai / dashscope
```
> 不想部署本地模型：直接用LLM在线API，Demo开发速度最快。

# Demo开发顺序建议（避坑路线）
1. 先写文档加载+文本切分，打印输出chunk，肉眼检查切分效果（很多人直接跳到向量入库，后面发现chunk切得一团糟）
2. 单独测试Embedding：输入两段文本，打印向量，测试相似度是否符合预期
3. 单独测试向量库检索：手动写几个query，看召回的chunk对不对；**检索环节单独调通，再接入LLM**
    > 超级重要：RAG80%的问题都出在召回，不是LLM生成；很多人LLM换了一圈效果还是差，根源是召回垃圾
4. 接入LLM、写prompt模板，完成问答闭环
5. 加评估：拿已知答案的测试问题，看召回、回答是否正确
6. 迭代升级：再加Rerank、BM25混合检索，升级Advanced RAG

# 高频坑速查表（面试+实操都很有用）
1. Embedding模型不一致：文档用A，query用B → 召回完全乱掉
2. Chunk切得太大/太小、没有重叠 → 信息断裂、召回无效
3. 噪声没有清理（页眉页脚水印）→ 大量无效chunk入库
4. Prompt没有强约束 → LLM脱离材料自由发挥，幻觉严重
5. Top-K设置过大 → 噪声灌入上下文
6. 混淆“语义相似”和“事实相关”：向量召回只是相似，不是一定能回答问题
7. 直接上复杂长PDF带大量表格图片，在Demo阶段给自己增加难度
8. 忘记元数据，回答无法溯源，出问题不知道是哪一段文档导致

# 拓展升级路线（从Naive → Advanced → Modular）
- Naive Demo（当前）：固定切分、纯向量召回、无改写无rerank
- 升级Advanced：增加Query Rewrite / HyDE、BM25+向量混合召回、Rerank、父文档检索
- 升级Modular：增加Router规划器，判断是否检索、选择不同检索源（向量库/数据库/联网搜索），此时就变成可以给Agent调用的复合Skill
