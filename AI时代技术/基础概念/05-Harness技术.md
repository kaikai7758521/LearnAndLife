# 大模型 Harness 技术
> 说明：本文的 Harness 特指 **LLM Test/Evaluation Harness（大模型评测 Harness）**，区别于传统单元测试、嵌入式仿真的测试 harness。核心一句话：**大模型 Harness 是一套标准化的执行脚手架，用来封装大模型、数据集、评测指标、环境与判分逻辑，自动完成样本加载、推理调用、结果采集、打分、异常捕获与现场留存，保证评测过程可复现、可对比，消除人工评测、零散脚本带来的不一致问题**。

## 一、产生历程
1. **早期零散评测阶段（大模型刚兴起时）**
早期评测大多是研究者手写独立脚本：单独写脚本跑 MMLU、单独写脚本跑 GSM8K，每个数据集一套调用逻辑、一套解析代码。不同人写的脚本提示词格式不一样、后处理逻辑不一样、采样参数（temperature、top_p）不统一。同模型、同数据集，不同脚本跑出来分数对不上，结果很难横向对比，论文里的指标难以复现。此时大家意识到，需要统一外壳来约束评测流程，就是 LLM harness 的雏形。

2. **开源基准评测框架普及阶段**
随着 MMLU、GSM8K、HumanEval、TruthfulQA 等基准数据集大量涌现，出现了第一批通用评测 harness（如 EleutherAI LM Evaluation Harness）。它把数据集加载、prompt 模板构造、模型接入、输出提取、答案校验、指标计算封装成统一流程。用户只需要接入模型，指定任务名称，就能复用成熟的评测逻辑，不再为每个数据集重复写解析、判分代码。
这个阶段的核心目标：**统一基准评测的标准，让不同模型的分数具备可比性**。

3. **对齐、安全、能力细粒度评测阶段（RLHF 之后）**
随着模型走向对齐、安全、Agent 能力、工具调用，单纯选择题/数学题基准不够用了。评测场景新增对话式评测、多轮交互、工具调用、偏见/幻觉、越狱测试。Harness 随之扩展：不再只是单次问答，支持多轮会话状态维护、工具回调编排、人工评审接入、偏好打分（Pairwise 两两对比、MT-Bench），增加了裁判模型（Judge LLM）自动判分能力。

4. **工业落地、持续回归评测阶段（当前）**
企业内部大模型迭代速度很快：每周甚至每日微调、SFT、权重版本更新。需要在每次模型版本变更后自动跑一套回归评测，防止能力退化（regression）。此时 LLM harness 融入 CI/CD，自动调度 GPU、管理模型版本、保存评测快照、生成对比报表；同时支持私有业务数据集、内部场景题，不再只依赖公开学术基准，形成面向业务的私有评测 harness。

> 演进主线：**零散独立评测脚本 → 统一公开基准评测脚手架 → 支持多轮、裁判模型、工具调用的通用评测框架 → 企业内部持续回归、业务定制化评测底座**。

## 二、大模型 Harness 的作用
1. **统一评测范式，保证分数可对比、可复现**
固定 prompt 模板、推理超参、答案提取规则、判分逻辑。同一个模型、同一个数据集，无论什么时候、谁去跑，流程一致，结果稳定，方便对比不同版本、不同基座、不同微调策略的差异。
2. **屏蔽模型接入差异**
对接不同后端：原生 HuggingFace、vLLM、OpenAI API、自研推理服务、TGI 等。harness 对外提供统一接口，评测任务代码不需要为每个推理后端改写。
3. **自动化批量评测，降低人力成本**
自动加载数据集、批量构造 prompt、调用推理、提取回答、计算指标；支持批量跑几十个任务，跑完自动汇总，替代大量人工标注打分。
4. **支持复杂评测范式**
支持单轮问答、多轮对话、Agent 工具调用、偏好对比（pairwise）、红蓝对抗安全测试、长上下文评测；可以接入 Judge LLM 做开放式主观题打分，弥补客观题正则匹配判分的短板。
5. **异常捕获与现场留存**
捕获推理超时、输出截断、服务报错、格式解析失败；自动保存失败样本、原始输入、模型原始输出、日志，方便定位幻觉、格式错误、服务稳定性问题。
6. **支撑模型回归与版本管控**
嵌入模型迭代流水线，每次微调、权重更新自动跑评测，及时发现能力下跌、幻觉增多、安全能力退化，作为版本上线的门禁。

> 容易混淆概念区分：
> - 数据集（MMLU/GSM8K）：评测的题目集合；
> - Judge LLM：用来给开放式回答打分的裁判模型，是 harness 里的一个组件；
> - LLM Harness：把模型、数据集、prompt、判分器、调度、报告串起来的整套执行外壳。

## 三、原理：大模型 Harness 的典型执行流程
同样遵循生命周期：**Setup → Execute → Validate & Score → Teardown**，但和传统测试 harness 的核心差异在于：被测对象是概率生成模型，输出非确定性，判分方式分为规则判分 + LLM 裁判判分两类。

1. **Setup（准备阶段）**
    - 加载指定模型/推理后端，初始化推理服务（加载权重、连接API、设置vLLM等推理参数）；
    - 加载评测数据集，加载对应任务的 Prompt 模板、格式约束；
    - 初始化评测配置：temperature、max_new_tokens、top_p、是否采样、few-shot示例数量；
    - 初始化判分器：正则匹配、代码执行器（HumanEval）、Judge 裁判模型、偏好对比配置；
    - 分配GPU资源、初始化结果存储目录。
2. **Execute（推理执行阶段）**
    - 遍历样本，按照模板拼接输入（few-shot、系统提示、用户问题）；
    - 调用推理接口获取模型生成文本；
    - 对工具调用类任务：harness 负责解析模型输出的工具调用指令、执行工具、把工具返回结果塞回对话上下文，形成闭环多轮交互；
    - 增加保护策略：单样本超时、输出长度限制、速率限流，防止推理服务卡死。
3. **Validate & Score（校验打分阶段）**
    - 客观任务（选择题、数学题、代码题）：正则提取答案、代码运行校验，得到 pass/true/false；
    - 开放主观任务（写作、摘要、对话质量、幻觉检测）：把【问题+模型回答+参考答案】送入 Judge LLM，输出分数/偏好；
    - Pairwise 对比模式：同一个问题同时送入 A/B 两个模型，交给裁判选出更好的一个；
    - 统计汇总指标：准确率、pass@k、胜率、幻觉率、MT-Bench 平均分等；
    - 保存原始样本、原始输出、打分理由。
4. **Teardown（收尾清理阶段）**
    - 释放GPU显存、关闭推理服务/API连接；
    - 整理结构化评测报告（JSON/表格/可视化看板数据）；
    - 可选：清理临时缓存、回收资源；保留失败样本用于后续复现。

核心组件清单：
- Model Adapter：模型接入层，兼容各种推理后端；
- Task Registry：任务注册表，管理各个数据集对应的 prompt、后处理、打分逻辑；
- Prompt Builder：按模板构造输入，支持 few-shot、system prompt；
- Sampler：控制推理采样参数；
- Scorer / Judge Client：打分模块（规则判分、裁判模型）；
- Agent Runtime（可选）：工具调用执行沙箱；
- Result Store & Reporter：结果存储、指标汇总、报告输出。

## 四、自建一套大模型 Harness，需要重点注意的事项
> 核心原则：LLM harness 最大痛点来自**生成的不确定性、prompt 敏感性、判分偏差**；自建优先保证“评测流程稳定、参数可追溯、结果可复现”，不要过早堆砌大量花哨评测任务。

### 1. 严格区分：harness 负责流程，业务评测逻辑下沉到 Task
Harness 内核只做调度、模型调用、结果存储；**每个任务的 prompt、答案提取正则、judge 提示词、打分规则，全部封装在独立 Task 里**。
不要把某个数据集的特殊解析逻辑硬写在 harness 主流程，否则新增一个任务就要改核心代码，极易引入bug。

### 2. 重视“复现性”，把所有影响分数的参数全部版本化、记录下来
大模型分数对参数极其敏感：few-shot数量、prompt措辞、temperature、max_new_tokens、stop词、是否开启beam search、推理框架（vLLM/transformers）都会改变结果。
✅ 所有参数必须随评测结果一起持久化保存；
✅ 做基准对比时，必须锁定全部超参，不能只对比模型权重；
✅ 想要确定性评测：优先设置 temperature=0（贪心解码），否则同模型多次跑分数会波动。

### 3. 合理设计判分体系，警惕 Judge LLM 的打分偏差
- 客观题优先规则/代码校验，成本低、稳定；
- 主观题依赖 Judge 时，要固定裁判模型版本、裁判prompt；Judge本身有偏好，会带来系统性偏差；
- 增加校验：少量样本引入人工标注作为金标，定期校准 Judge，防止裁判漂移；
- Pairwise 对比比绝对打分更稳定，但成本更高。

### 4. 模型接入层做适配隔离，兼容多种推理后端
用适配器模式抽象推理接口，统一入参出参。后端可以是 huggingface 本地推理、vLLM、OpenAI兼容接口、自研RPC推理服务。
好处：基座切换、部署架构变更时，整套评测任务不需要改动。

### 5. 资源、超时、沙箱安全（Agent/工具调用场景重中之重）
- 推理超时控制：单样本超时、整体任务超时，避免某个慢推理卡住整个评测队列；
- GPU资源管理：支持排队、并发控制，防止批量评测抢占全部显存；
- 如果支持工具调用、代码执行：**代码必须跑在隔离沙箱中**，禁止直接在宿主机执行任意生成代码，防止注入、命令执行风险；
- 限流策略：调用第三方API评测时做好QPS控制，避免触发服务商风控。

### 6. 样本隔离，处理长上下文、多轮会话状态
多轮对话评测时，harness 需要独立维护每个样本的对话上下文，样本之间状态隔离，不能串会话；
长上下文评测需要单独管理窗口截断、位置编码、上下文窗口边界，避免 harness 本身的拼接逻辑引入额外误差。

### 7. 结果存储设计，方便对比回归
原始输出不能丢弃：不仅存最终分数，**原始prompt、模型原始输出、打分理由、失败标记全部落盘**；
数据格式推荐标准化JSON，方便后续脚本做版本 diff：对比 v1 和 v2 模型，看哪些样本从答对变成答错（退化case）。

### 8. harness 自身也要做自检
harness 本身也会有bug（正则写错、prompt拼接错误、judge调用失败、结果统计公式错误）。
- 准备一套“黄金小测试集”：已知固定分数，每次改动 harness 后先跑这个小集合，验证打分逻辑不变；
- 做对照：用公开模型（如 Llama 2、Qwen）跑公开基准，和官方公布分数对标，验证你的 harness 和社区主流 harness 对齐。

### 9. 不要一开始追求“全任务大而全”
优先搭建最小可用版本：支持一个推理后端、1~2个基础任务（比如GSM8K、MMLU），验证打分稳定、可复现；再逐步增加对话、pairwise、安全评测、私有业务数据集。很多自研 harness 烂尾的原因是一开始想把学术基准、业务场景、安全对抗全部塞进去，复杂度失控。

## 五、大模型 Harness 的典型应用场景
1. **学术基准评测**
跑 MMLU、GSM8K、HumanEval、TruthfulQA、CMMLU 等公开数据集，得到标准化指标，用于论文、模型卡的能力汇报，和社区主流模型横向对比。
2. **模型迭代回归评测（工业最常用）**
SFT、DPO、微调、LoRA 迭代后自动跑回归集，监控准确率、幻觉率、指令遵循能力是否下跌，作为上线门禁，防止新版本退化。
3. **对齐与偏好评测**
Pairwise 两两对比、MT-Bench 类多轮对话打分，评估模型对话质量、 helpfulness、无害性，用于RLHF、DPO效果验证。
4. **安全与红队评测**
批量执行越狱提示、偏见、隐私、有害提问测试集，自动统计拒绝率、风险输出比例，做模型安全基线巡检。
5. **Agent & 工具调用评测**
评测模型调用搜索、计算器、API、代码解释器的能力；harness 维护工具运行时，闭环执行工具动作，判断是否正确完成任务。
6. **私有业务场景评测**
加载企业内部专属数据集：行业问答、文档摘要、客服话术、代码开发、合同抽取等业务考题，评测模型在垂直场景的落地效果，这是公开基准无法替代的。
7. **长上下文能力评测**
针对 RAG、长文档摘要、长代码理解任务，构造超长输入，评测模型在不同上下文窗口下的召回、理解、信息提取能力。
8. **评测方案本身的消融实验**
用 harness 批量控制变量：对比不同 prompt、不同 few-shot、不同裁判模型、不同解码策略对最终分数的影响，做评测方法本身的消融研究。
