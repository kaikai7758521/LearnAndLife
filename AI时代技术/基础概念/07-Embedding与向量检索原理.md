# Embedding 与向量检索原理
> 一句话：**Embedding 把文本压成一个固定维度的稠密向量，让「语义相近」变成「空间距离近」；向量检索就是用近似最近邻索引，在海量向量里快速找出与查询最接近的那几条。**
> 定位：它是 RAG 的召回模块，负责「找得准」；生成质量仍取决于 LLM 与上下文组装。

## 一、Embedding 到底做了什么
### 1. 从文本到向量
```
文本 → Tokenizer 分词 → Transformer 编码 → 池化（CLS / 均值）→ L2 归一化 → 向量 [0.013, -0.204, ...]
```
- 输出是**固定维度**的浮点数组，常见 384 / 512 / 768 / 1024 / 1536 / 3072 维；
- 向量本身没有可读含义，每一维不是「主题」「情感」，而是模型训练出来的隐式特征组合；
- **语义相近 ≠ 字面相近**：「电脑坏了」和「笔记本无法开机」会被编码到相近位置，即使没有一个共同关键词。

### 2. 双塔结构与对比学习
Embedding 模型通常是**双塔（bi-encoder）**：
- 查询塔、文档塔共享或对称的编码器，**分别独立编码**；
- 好处：文档向量可以**离线预计算**，在线只编码 query，一次向量比较即可，复杂度低；
- 代价：query 和 doc 在编码阶段**看不到彼此**，细粒度匹配能力弱于交叉编码器。

训练目标是对比学习（以 InfoNCE 为代表）：
1. 一个 batch 里，`(query, 正样本)` 是配对，其余文档都是负样本（in-batch negatives）；
2. 拉近正样本相似度、推远负样本相似度，温度系数 τ 控制分布锐度；
3. 关键在**难负样本挖掘**：随机负样本太容易，模型学不到区分「语义像但不相关」的能力，这正是 RAG 召回噪声的根源。

> 这就是为什么 **Embedding 负责「粗召回」，Rerank 负责「精排序」**：双塔追求可预计算的速度，交叉编码器追求 query-doc 逐词交互的精度，两者分工不同。

### 3. 对称检索 vs 非对称检索
| 类型 | query 与 doc 关系 | 例子 | 注意 |
|---|---|---|---|
| 对称 | 长度、形态相近 | 「如何重置密码」找「密码怎么重置」 | 普通句向量模型即可 |
| 非对称 | 短 query 找长文档 | 「退款政策」找 3000 字条款 | 需要带**指令前缀**的模型 |

不少模型训练时用了指令前缀，例如 E5 系列要求：
```
query: 退款政策
passage: 用户在签收后 7 天内可申请无理由退款……
```
**推理时漏掉前缀，效果会明显下降**，而且不会报错，属于典型的静默失效。

## 二、相似度度量
| 度量 | 公式直觉 | 特点 |
|---|---|---|
| **余弦相似度** | 两向量夹角 | 只看方向、不看长度，最常用 |
| **内积（dot）** | 方向 + 长度 | 向量已归一化时与余弦**完全等价** |
| **欧氏距离** | 直线距离 | 归一化后与余弦单调对应，可互相换算 |

工程要点：
1. **入库前是否归一化，查询时必须保持一致**。一边归一化一边不归一化，分数会整体漂移，Top-K 直接错乱；
2. 归一化后可直接用内积，省一次除法，向量库通常默认这么做；
3. 不同模型的最优度量不同，以模型卡说明为准，不要默认余弦万能；
4. 相似度分数**没有跨模型可比性**，0.82 在 A 模型算高、在 B 模型可能只是中等，阈值必须按模型重新标定。

## 三、主流模型与选型维度
### 1. 常见系列
- **BGE / bge-m3**：中文生态成熟，多语言、多粒度；
- **E5 / multilingual-e5**：指令前缀规范明确，检索任务表现稳定；
- **GTE**：中文与长文本支持较好；
- **text-embedding-3 系列**：API 调用方便，支持维度截断；
- **Jina / Cohere Embed**：长上下文、多语言场景常用。

### 2. 选型看什么
1. **语言与领域**：中文场景优先中文或多语言模型，英文模型直接用于中文会显著掉点；
2. **最大输入长度**：512 / 8192 Token 差别巨大，超过上限会被截断且不报错；
3. **维度与成本**：维度越高，存储与检索越贵。100 万条 1536 维 float32 ≈ 5.7 GB，还没算索引开销；
4. **MTEB / C-MTEB 榜单**：只能作参考，最终必须用**自己的业务 query 集**评测；
5. **是否支持 Matryoshka（MRL）**：训练时按嵌套维度优化，可把 1024 维截断到 256 维仍保留大部分效果，用来换存储成本；
6. **部署形态**：API 免运维但按 Token 计费、有网络延迟；本地模型免费但吃显存、要自己扩缩容。

### 3. 模型升级的隐藏成本
换 Embedding 模型 = **整个向量库必须全量重建**：
- 旧库是 A 模型的向量空间，新 query 用 B 模型编码，两个空间不可比，召回等于随机；
- 期间要双写/双索引，或停机重建；
- 所以选型时要把「未来换模型的迁移成本」算进去，元数据里保留原文，方便重跑。

## 四、向量检索：从暴力扫描到 ANN
### 1. 为什么必须用近似算法
100 万条 768 维向量，一次暴力比较就是 7.68 亿次浮点运算，且随数据量线性增长。**ANN（Approximate Nearest Neighbor）** 用少量召回率换取数量级的速度提升。

### 2. 三类主流索引
| 索引 | 原理 | 优点 | 缺点 | 关键参数 |
|---|---|---|---|---|
| **HNSW** | 多层可导航小世界图，上层稀疏做粗跳转，底层稠密做精搜索 | 召回高、延迟低，工业默认 | 内存占用大、构建慢、删除麻烦 | `M`（每层邻居数）、`efConstruction`（建图深度）、`efSearch`（查询深度） |
| **IVF** | 先聚类成 `nlist` 个簇，查询时只扫最近的 `nprobe` 个簇 | 内存友好、适合超大规模 | 需要训练、边界样本易漏 | `nlist`、`nprobe` |
| **PQ** | 把向量切成 `m` 段，每段用码本量化成 1 字节 | 压缩 10~30 倍 | 精度损失明显，常与 IVF 组合成 IVF-PQ | `m`、`nbits` |

调参直觉：
- `efSearch` 调大 → 召回升、延迟升，是最常用的效果/性能旋钮；
- `M` 调大 → 图更连通、召回更好，但内存和构建时间上涨；
- `nprobe` 调大 → 扫更多簇、召回升、变慢；
- **没有一套参数通吃**，必须用真实数据测 Recall@K 与 P99 延迟。

### 3. 元数据过滤的陷阱
业务检索常带过滤条件（租户、时间、文档类型）。两种做法：
- **后过滤（post-filter）**：先 ANN 取 Top-K，再按条件筛。条件苛刻时可能筛完只剩 1 条，甚至 0 条；
- **前过滤（pre-filter）**：先筛子集再检索。子集太小会破坏 HNSW 图连通性，退化成暴力扫描。

成熟方案是**分区索引 / 带过滤的图搜索**（按租户分 collection、或用支持 filtered HNSW 的引擎），而不是在应用层硬凑。

### 4. 其他压缩手段
- **float16 / int8 量化**：省 2~4 倍内存，通常只掉极少量召回；
- **二值化（binary embedding）**：用汉明距离，内存降 32 倍，适合粗筛 + 精排两段式；
- **磁盘索引（DiskANN）**：内存放不下时的选择，用 SSD 换内存。

## 五、怎么评估检索质量
不要只看「感觉搜得还行」，要有离线指标：
1. **Recall@K**：标准答案所在文档是否出现在前 K 条，最直观；
2. **MRR**：第一条正确结果排名的倒数均值，衡量排序头部质量；
3. **nDCG@K**：考虑多条相关结果与分级相关性，适合多答案场景；
4. **端到端指标**：最终答案正确率 / 引用命中率，才是业务真正关心的。

做法：
- 从真实日志里抽 100~300 条 query，人工标注正确文档，构成**黄金评测集**；
- 换模型、改 chunk、调 `efSearch` 都跑同一套集合，避免凭感觉调参；
- 同时记录**延迟与成本**，召回率提升往往伴随延迟上涨，要做权衡。

## 六、工程坑清单
1. **query 与 doc 必须同模型、同版本、同归一化方式**，任何一项不一致都会静默降质；
2. **超长文本被截断不报错**：chunk 必须小于模型最大输入，且要预留指令前缀的长度；
3. **短 query 语义稀薄**：「流程？」这类查询向量信息量极低，需要改写或结合上下文；
4. **否定与数量关系是弱项**：「不含防腐剂的食品」很容易召回「含防腐剂」的内容，向量对否定不敏感；
5. **领域漂移**：通用模型在医疗、法律、工艺术语上表现差，优先选领域微调过的模型；
6. **重复入库**：同一文档多次导入会挤占 Top-K，入库前要做去重；
7. **维度混用**：一个 collection 里混入不同维度的向量，多数引擎直接报错，少数会静默截断；
8. **删除与更新**：HNSW 的删除多为标记删除，长期只增不删会导致索引膨胀，需要定期重建；
9. **相似 ≠ 相关**：向量只保证语义接近，不保证能回答问题，这是必须加 Rerank 的根本原因。

## 七、常见误区
1. ❌ 维度越高越好：高维提升有限，存储和检索成本线性上涨，MRL 截断往往更划算；
2. ❌ 向量库就是数据库：它是索引 + 元数据存储，事务、关联查询、强一致并非其强项；
3. ❌ 余弦相似度永远最优：归一化后与内积等价，未归一化时行为不同，要看模型训练方式；
4. ❌ 换个更强的 Embedding 模型就一定涨点：不重建索引、不改 chunk、不重标阈值，很可能反而下降；
5. ❌ 召回分数可以跨模型设阈值：分数分布随模型变化，阈值必须重新标定；
6. ❌ ANN 近似可以忽略：`efSearch` 太低会稳定漏掉正确结果，且不会给出任何警告；
7. ❌ Embedding 能理解逻辑：它擅长语义相似，不擅长否定、比较、因果、数值推理，这些要靠 Rerank 或 LLM。

## 八、和 RAG 其他环节的分工
| 环节 | 职责 | 失败表现 |
|---|---|---|
| 分块 | 决定检索的最小语义单元 | 切碎语义，召回片段答非所问 |
| **Embedding + 向量检索** | 从海量文档中粗召回候选 | 正确文档根本没进候选集 |
| Rerank | 对候选做 query-doc 精细打分 | 候选里有正确答案但排到后面 |
| 上下文组装 | 控制送入 LLM 的片段与顺序 | 噪声挤占窗口，模型被干扰 |
| LLM 生成 | 基于证据作答 | 有证据仍编造，属于生成侧问题 |

> 排查 RAG 效果差，先定位是**没召回到**（Embedding/索引问题）还是**召回到了没用上**（Rerank/Prompt 问题），不要一上来就换大模型。
