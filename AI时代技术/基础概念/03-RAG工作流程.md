# RAG 工作流程

## 前置
> - Naive RAG：基础检索Tool
> - Advanced RAG：优化后的检索Skill
> - Modular RAG：带内部规划、多数据源路由的复合Skill，可以直接给Agent调用
- **Naive RAG（朴素RAG）**：最简原型，只有「分块→向量化→向量召回→拼prompt」，链路短、好上手，但召回质量不稳定。
- **Advanced RAG（增强RAG / 高级RAG）**：在朴素RAG上加各类优化模块（重排、查询改写、多检索融合、过滤），**不改变主链路结构**，是在原有流水线里插增强环节。
- **Modular RAG（模块化RAG）**：把RAG拆成大量可插拔、可路由的独立模块，增加调度器/规划器，**动态选择检索策略、检索源、后处理逻辑**，和Agent思想高度融合。

# 一、RAG 完整工作流程（分离线阶段 + 在线推理阶段）
RAG整体分为两大阶段：**索引构建阶段（离线，只跑一次/增量更新）** 和 **问答推理阶段（在线，用户每问一次就跑一次）**

## 阶段1：离线索引流水线（文档入库）
```
原始文档 → 文档加载 & 清洗 → 文档切分(Chunking) → 向量化(Embedding) → 写入向量库 + 元数据存储
```
1. **文档加载 & 清洗**
    读取PDF/Markdown/Word/网页等，提取纯文本；去除水印、页眉页脚、乱码、重复广告、无关注释。
2. **Chunk 分块（切片）**
    把长文本切成小段，是RAG非常关键的一步。
    - 朴素RAG：固定长度切（比如1000token，重叠50token）
    - 高级RAG：语义分块、按标题/章节边界切、基于LLM做语义边界切分
    > 目的：控制单块长度，适配Embedding模型输入上限，同时保证一块内语义尽量完整。
3. **Embedding 向量化**
    使用Embedding模型，把文本块转为稠密向量（vector），语义相近的文本向量距离更近。
4. **入库**
    向量存入向量数据库（Chroma、Milvus、Qdrant等）；同时保存原文chunk、文档名、页码、时间等元数据。
    > 很多工程实现会同时保留原始文本，向量仅用于相似度检索。

> 离线阶段**不调用生成式LLM**，只用到Embedding模型。

## 阶段2：在线问答流水线（用户提问，核心链路）
```
用户Query → 查询预处理 → 检索（召回）→ 筛选/重排 → 上下文组装 → LLM生成 → 后校验/溯源输出
```
逐环节拆解：
1. **Query 查询预处理**
    对用户原始问题做处理：清理无效字符、改写、扩展子问题。
    - Naive：直接拿原句去检索
    - Advanced：Query Rewrite（查询改写）、Query Expansion（多视角生成多个子query）、Hyde（假设文档）
2. **检索召回（Retrieval）**
    把处理后的query向量化，在向量库做相似度Top-K召回；也可以融合BM25关键词检索（稀疏检索）。
    输出：一批候选文档片段（候选集）。
3. **重排（Rerank，高级RAG标志性模块）**
    召回出来的Top-K里面，依然有很多语义相近但不相关的碎片。
    Rerank模型（如BGE-Reranker、Cohere Rerank）接收【query + 候选chunk】成对打分，重新排序，过滤低分片段，压缩送入LLM的上下文。
    > 朴素RAG一般没有重排，直接拿向量召回结果喂给LLM。
4. **上下文Prompt组装**
    将用户问题 + 筛选后的参考片段 + 约束指令（要求引用、禁止编造）拼接成Prompt。
5. **LLM生成答案**
    LLM读取prompt，基于给的参考材料生成回答。
6. **后校验 & 输出**
    可选：事实校验、幻觉检测、引用标注、过滤敏感内容，返回答案+来源链接/页码。

# 二、Naive RAG / Advanced RAG / Modular RAG 详细对比
## 1. Naive RAG 朴素RAG
### 链路结构
离线：固定分块 → embedding → 向量入库
在线：原query直接向量化 → 向量召回TopK → 直接拼接进prompt → LLM输出
**无改写、无重排、无路由、无多检索源融合**

### 特点
✅ 优点
- 实现最简单、上手快、代码量少，适合demo、小知识库、内部简单文档问答
- 延迟低、组件少、运维成本低

❌ 缺点
- 对歧义query、复杂问题、跨文档问题效果很差
- 向量相似度 ≠ 事实相关性，容易召回“语义像但无关”的内容
- 固定分块策略容易切断语义，出现上下文断裂
- 没有过滤机制，噪声直接灌给LLM，幻觉高发

### 典型场景
课程Demo、小体量知识库（几十篇文档以内）、验证想法原型。

## 2. Advanced RAG 高级RAG
> 业界常说的Advanced RAG，**流水线顺序不变，在原有节点上增加增强插件**，整体还是一条线性流水线，没有动态分支路由。
### 常见增强组件（可选组合）
- Query侧：Query Rewrite、Query Expansion、HyDE（Hypothetical Document Embedding，先生成假想答案再检索）、多轮query记忆
- 检索侧：稀疏+稠密混合检索（BM25 + 向量）、多路召回
- 后检索侧：Rerank重排、去重、过滤低质量chunk、摘要压缩（Context Compression）
- Chunk侧：语义分块、分层摘要索引（Parent-Document Retrieval父文档检索）

### 链路
Query → Query增强 → 多路召回 → Rerank筛选 → 压缩上下文 → 组装Prompt → LLM生成

### 特点
✅ 优点
- 在大多数企业文档场景收益非常明显，是工业落地最主流方案
- 可控，模块可逐步加：先加重排，再加Hyde，再加BM25，迭代成本低
- 不需要引入复杂规划/Agent调度，成本可控

❌ 缺点
- **还是固定流水线**：不管什么问题，都走同一套检索逻辑，一刀切
    比如简单问题、复杂推理问题、需要查数据库的问题，都强行走文档向量检索
- 当问题类型差异巨大、需要跨不同数据源（文档库/数据库/API）时，瓶颈明显

### 典型场景
企业知识库客服、产品手册问答、法务文档检索问答，绝大多数RAG生产项目都停在这一层。

## 3. Modular RAG 模块化RAG
> 核心思想：**把RAG拆成一堆独立能力模块，增加一个Router/Planner调度器，由大模型判断该用哪些模块、以什么顺序执行**，本质上RAG向Agent靠拢。
> Modular RAG = RAG能力集 + 智能路由规划器
### 可插拔模块举例
- 检索模块：向量检索模块、BM25检索模块、SQL数据库查询模块、网页搜索模块
- Query模块：改写模块、拆分模块、摘要模块
- 后处理模块：重排模块、校验模块、对比模块
- 拒绝回答模块：判断问题不在知识库范围内，直接拒答

### 执行流程
用户Query → Planner/Router（LLM判断问题类型）
1. 判断：这个问题要不要检索？
2. 判断：用哪一种检索源？向量库 / 数据库 / 联网搜索？
3. 判断：是否需要先拆成多个子问题，并行检索？
4. 调用对应模块拿到结果 → 合并证据 → 生成答案

> 例子：
> 用户问：“2025和2026年公司营收对比，同时列出营收口径文档说明”
> Router规划：①调用SQL模块查营收数据表；②调用向量RAG模块查口径文档；③合并两份证据再生成回答。

### 特点
✅ 优点
- 弹性极强，不同类型问题自动匹配最合适的检索方式
- 天然支持异构数据源：文档向量库、结构化数据库、搜索引擎、API
- 可以避免“所有问题都无脑向量化检索”带来的浪费和错误
- 和Agent体系无缝对接：Modular RAG本身就可以直接作为一个复杂Skill接入Agent

❌ 缺点
- 系统复杂度显著上升，需要维护Router提示词、模块路由逻辑、失败回退策略
- Router本身会出错：规划错了，选错检索模块，直接导致答案失败
- Token消耗、延迟更高，调试、评估难度变大

### 典型场景
复杂企业问答（同时涉及文档+报表+业务数据库）、多源知识库、智能客服中台。

# 三、三者对比总表
| 维度 | Naive RAG | Advanced RAG | Modular RAG |
|---|---|---|---|
| 核心架构 | 单一线性固定链路 | 单一线性链路 + 增强插件 | 模块池 + Router规划调度，动态分支 |
| Query处理 | 原query直接检索 | 支持改写、扩展、HyDE | 由规划器决定要不要改写、拆分子问题 |
| 检索方式 | 仅稠密向量检索 | 混合检索（BM25+向量）多路召回 | 可自选检索源：向量/BM25/SQL/联网搜索 |
| 重排Rerank | 一般无 | 标配高频使用 | 可选，由路由决定是否启用 |
| 适用问题 | 简单、单文档、语义清晰 | 大部分普通文档问答 | 异构数据源、跨类型复杂问题 |
| 和Agent关系 | 独立简单检索工具 | 增强版检索Skill | 自带规划能力的复合Skill，边界和Agent模糊 |
| 实现难度 | 低 | 中等 | 高 |
| 幻觉控制 | 弱 | 较强 | 强，但路由错误会引入新风险 |

# 四、补充
1. Advanced RAG ≠ Modular RAG
Advanced RAG只是**给流水线加buff**，流程顺序不变；Modular RAG是**改变调度逻辑，动态选择路径**。
2. Modular RAG 已经很接近轻量Agent
区分边界：Modular RAG目标依然是**检索+问答**，任务目标单一；通用Agent可以执行任意Tool、跨多类任务（读写文件、发邮件、编码、检索）。
3. 不是越高级越好
很多内部知识库，一个Advanced RAG（向量+BM25+Rerank）就足够稳定；盲目上Modular会徒增运维成本。
