# 大模型推理与部署
> 一句话：**推理分为 prefill 和 decode 两个阶段：prefill 吃算力，decode 吃显存带宽；部署的核心是在 TTFT、TPOT、吞吐和显存之间做调度与取舍。**
> 定位：讲模型上线后的 serving 问题（KV Cache、批处理、量化、并行、指标），Token 计费与上下文窗口的基础概念见 `04-Token是怎么被消耗的.md`。

## 一、推理和训练有什么不同
| 维度 | 训练 | 推理 |
|---|---|---|
| 计算 | 前向 + 反向 + 优化器 | 只做前向 |
| 显存大头 | 权重、梯度、优化器状态、激活 | 权重、KV Cache、少量激活 |
| 瓶颈 | 算力、通信 | 显存带宽、显存容量、调度 |
| 批处理 | 大 batch 提升吞吐 | 受延迟 SLO 约束，不能无限加 batch |
| 精度 | FP16/BF16/FP8 训练 | 可量化到 INT8/INT4，需评估精度 |

> 训练追求「多久训完」，推理追求「多快响应、多少并发、每 token 成本多少」。

## 二、Prefill 与 Decode
### 1. 两个阶段
```
Prompt: "请解释一下 KV Cache"
Prefill：一次性并行处理全部输入 Token，生成 KV Cache
Decode：基于 KV Cache 自回归逐个生成输出 Token
```
| 阶段 | 计算特征 | 瓶颈 | 影响指标 |
|---|---|---|---|
| Prefill | 矩阵乘为主，可并行 | GPU 算力 | TTFT（首 token 延迟） |
| Decode | 每步只生成 1 个 Token | 显存带宽 | TPOT/ITL（每 token 延迟） |

### 2. 为什么 decode 是带宽瓶颈
生成每个 Token，都要把**全部模型权重**读一遍，再和 KV Cache 做注意力：
```
7B 模型 FP16 权重约 14GB
显存带宽 1TB/s → 理论约 70 token/s（单请求、无批处理）
```
这就是为什么：
- 单请求 decode 很难跑满 GPU 算力；
- **增大 batch** 可以摊薄权重读取成本，提高吞吐，但会增加排队与显存压力；
- 量化权重能直接提升 decode 速度（读得更少）。

### 3. 算力估算
```
Prefill FLOPs ≈ 2 × 参数量 × 输入 Token 数
Decode  FLOPs ≈ 2 × 参数量 × 输出 Token 数
```
实际还要算注意力部分，长上下文时注意力占比显著上升。

## 三、KV Cache：推理显存的核心
### 1. 为什么需要
自回归生成时，前面 Token 的 Key/Value 可以复用；否则每生成一个 Token 都要重算全部历史，复杂度爆炸。

### 2. 显存公式
```
KV bytes = 2（K 和 V）
         × 层数
         × KV 头数
         × head_dim
         × 序列长度
         × batch
         × 每元素字节数
```
以 Llama-2 7B（32 层、32 头、head_dim 128、FP16）为例：
```
每 Token KV = 2 × 32 × 32 × 128 × 2B = 0.5 MiB
4K 上下文 ≈ 2 GiB / 条
```
GQA（分组查询注意力）把 KV 头数从 32 降到 8，KV Cache 直接降到 1/4；这是长上下文模型普遍采用 GQA 的原因。

### 3. 优化手段
| 手段 | 原理 | 效果 |
|---|---|---|
| GQA / MQA | 多个 Query 头共享 KV 头 | GQA 常见降至 1/4 ~ 1/8，MQA 可到 1/32 |
| KV 量化 | KV 存成 FP8/INT8 | 显存减半，精度略降 |
| PagedAttention | KV 按块管理，类似虚拟内存分页 | 减少碎片，支持前缀共享 |
| Prefix Caching | 相同系统提示/文档复用 KV | 降低重复 prefill |
| 抢占/换出 | 显存不足时换到 CPU/重算 | 保吞吐，牺牲延迟 |

PagedAttention（vLLM 的核心）把 KV 切成固定大小的 block，用 block table 映射逻辑位置到物理块：
- 不需要为每个请求预分配最大长度的连续显存；
- 内存浪费从「按最大长度预留」降到「按实际块分配」；
- 相同前缀的请求可以共享 block（Copy-on-Write）。

## 四、批处理与调度
### 1. 静态批处理 vs 连续批处理
| 方式 | 行为 | 问题 |
|---|---|---|
| 静态 batch | 凑齐一批一起跑，等最慢的结束 | 短请求被长请求拖住，GPU 空转 |
| 连续批处理（Continuous Batching） | 每步都重新组 batch，完成的请求立刻退出、新请求立刻加入 | 实现复杂，但吞吐与延迟都更好 |

连续批处理（iteration-level scheduling）是 vLLM、TGI、TensorRT-LLM 的标配。

### 2. Chunked Prefill
长 Prompt 的 prefill 会占满 GPU，导致正在 decode 的请求卡顿。把 prefill 切成小块，与 decode 交错执行：
- 降低 TPOT 抖动；
- 代价是单个长请求的 TTFT 略增；
- 适合长文档/RAG 场景。

### 3. Prefill 与 Decode 的干扰
- Prefill 是算力型，Decode 是带宽型，混在一起会互相拖累；
- 高级方案把 prefill 和 decode 拆到不同 GPU 池（Disaggregated Prefill/Decode），分别扩缩容；
- 简单方案用 chunked prefill + 调度权重。

### 4. 调度策略
- 按优先级：付费用户/核心接口优先；
- 按剩余 token 预算：避免超长请求饿死其他请求；
- 超时与取消：客户端断开要及时释放 KV；
- 公平性：多租户要限制单租户并发与 token 配额。

## 五、量化：用精度换显存与带宽
| 类型 | 说明 | 适用 |
|---|---|---|
| Weight-only INT8 | 只量化权重，激活仍 FP16 | 显存紧张、decode 为主 |
| Weight-only INT4（GPTQ/AWQ） | 4bit 权重，需校准数据 | 单卡部署大模型 |
| W8A8 | 权重和激活都 INT8 | 有量化校准、追求吞吐 |
| FP8 | H100/L40S 等支持，精度损失小 | 新卡首选 |
| KV Cache 量化 | KV 存 FP8/INT8 | 长上下文、高并发 |

注意：
- **decode 是带宽瓶颈，量化权重通常直接加速**；prefill 是算力瓶颈，INT4 反量化可能抵消收益；
- 量化对数学、代码、长链推理的影响要单独评测，不能只看通用 benchmark；
- 校准数据要覆盖真实业务分布；
- 量化后仍要留显存给 KV Cache 和激活。

## 六、并行与加速
### 1. 并行方式
| 方式 | 切分对象 | 通信 | 场景 |
|---|---|---|---|
| 数据并行 DP | 不同请求分到不同副本 | 无（推理） | 扩容吞吐 |
| 张量并行 TP | 单层权重切到多卡 | 每层 AllReduce，NVLink 最佳 | 单机多卡 |
| 流水并行 PP | 按层切分到多卡 | 激活传递 | 跨机大模型 |
| 专家并行 EP | MoE 专家分片 | All-to-All | MoE 模型 |

> 单请求的 TP 不是越多越快：通信开销会吃掉收益；通常优先用 TP 塞进单机 NVLink，再考虑跨机。

### 2. 投机解码（Speculative Decoding）
```
小模型/草稿模型先猜 K 个 Token
  → 大模型一次前向并行验证
  → 接受前缀，拒绝后重新采样
```
- 在小 batch、decode 带宽受限时收益明显（常见 1.5~2x）；
- 大 batch 时大模型本身已接近算力瓶颈，投机可能反而变慢；
- 接受率取决于草稿模型与目标任务；也可以用 n-gram/检索草稿、Medusa 多头。

### 3. 其他手段
- FlashAttention / PagedAttention / 融合算子：减少显存读写；
- CUDA Graphs：减少小算子启动开销；
- TensorRT-LLM：针对 NVIDIA 编译优化；
- 前缀缓存：系统提示、RAG 文档、few-shot 示例复用；
- 多 LoRA：共享基座，按请求切换适配器，适合多租户定制。

## 七、显存预算：先算清楚再上线
```
总显存 = 权重
       + KV Cache
       + 激活/临时 workspace
       + 框架开销/碎片
       + 安全余量（10%~20%）
```
示例：

| 模型 | 权重 FP16 | 权重 INT4 | 4K KV（示意） | 单卡 24GB 可行性 |
|---|---|---|---|---|
| 7B MHA | ~14GB | ~4GB | ~2GB/条 | FP16 可跑，并发有限 |
| 7B GQA（8 KV 头） | ~14GB | ~4GB | ~0.5GB/条 | 可跑，并发更好 |
| 13B MHA | ~26GB | ~7GB | ~3GB/条 | 需 2×24GB 或 INT4 |
| 70B GQA（8 KV 头） | ~140GB | ~35GB | ~1.3GB/条 | 需多卡；INT4 也需 ≥48GB 单卡 |

> 权重只是下限，**长上下文与高并发会把 KV Cache 变成主要矛盾**。上线前必须按「最大上下文 × 最大并发」算峰值。

## 八、指标：别只看 tokens/s
| 指标 | 含义 | 关注点 |
|---|---|---|
| TTFT | 请求到首 Token 的时间 | 交互体验，受 prefill/排队影响 |
| TPOT / ITL | 每个输出 Token 的间隔 | 流式输出的流畅度 |
| E2E Latency | 端到端完成时间 | 受输出长度影响 |
| Throughput | 每秒总 Token 数 | 成本与容量 |
| Goodput | 满足 SLO 的有效吞吐 | 比裸吞吐更有意义 |
| Queue Time | 排队等待时间 | 扩容信号 |
| GPU 利用率 | SM/显存带宽利用率 | 高不一定高效 |
| KV Cache 使用率 | 已用块/总块 | 接近 100% 会抢占/拒绝 |
| 抢占/重算次数 | 显存不足触发 | 延迟抖动来源 |

> 优化目标不是「GPU 100%」，而是「在 SLO 内最大化 goodput」。

## 九、部署架构
```
Client → API Gateway（鉴权/限流/计费）
       → Router（按模型/租户/负载路由）
       → Serving 实例（vLLM/TensorRT-LLM/SGLang）
       → GPU 池
       ↑
Model Registry / 配置中心 / 监控告警 / 自动扩缩容
```
关键设计：
1. **OpenAI 兼容 API**：`/v1/chat/completions`、SSE 流式返回，降低客户端迁移成本；
2. **路由**：按模型、LoRA、上下文长度、租户配额分流；
3. **自动扩缩容**：看队列长度、TTFT、KV 使用率，不要只看 CPU/GPU；
4. **冷启动**：模型加载可能几十秒到几分钟，保留 warm pool；
5. **灰度**：新模型/新量化版本按比例放量，比较 TTFT、错误率、人工评分；
6. **降级**：过载时缩短最大输出、关闭非核心功能、切换到小模型；
7. **安全**：鉴权、配额、Prompt 注入防护、输出审核、日志脱敏；
8. **多租户**：并发隔离、token 配额、LoRA 隔离、优先级队列。

## 十、推理框架选型
| 框架 | 特点 | 适合 |
|---|---|---|
| **vLLM** | PagedAttention、连续批处理、OpenAI API、多 LoRA | 通用 GPU 服务，社区活跃 |
| **TensorRT-LLM** | NVIDIA 深度优化、编译式部署 | 追求极致性能、固定模型 |
| **SGLang** | RadixAttention 前缀缓存、结构化输出 | 多轮/Agent/RAG 场景 |
| **TGI** | Hugging Face 生态、部署简单 | HF 模型快速上线 |
| **llama.cpp / Ollama** | CPU/Metal/边缘、GGUF 量化 | 本地、端侧、低并发 |
| **Triton Inference Server** | 多框架统一 serving | 企业多模型平台 |

> 选型先看「模型支持、量化格式、并发能力、运维成本」，再看 benchmark；纸面吞吐不等于业务 goodput。

## 十一、常见误区
1. ❌ 显存够放权重就能跑：长上下文/高并发的 KV Cache 往往才是瓶颈；
2. ❌ batch 越大越好：吞吐上升但 TTFT/TPOT 变差，要按 SLO 找平衡；
3. ❌ 量化一定更快：decode 受益明显，prefill 可能被反量化拖慢；
4. ❌ 只看 tokens/s：不看 TTFT、TPOT、错误率，用户体验可能更差；
5. ❌ 上下文长度只影响 prefill：KV Cache 随长度增长，decode 也会变慢、显存更紧张；
6. ❌ GPU 利用率 100% 就是好：可能是无效重算或调度低效；
7. ❌ 多卡一定加速单请求：TP 通信开销可能让单请求更慢，但吞吐更高；
8. ❌ 投机解码万能：高 batch、算力受限时收益有限甚至为负；
9. ❌ temperature=0 就完全确定：硬件/算子非确定性、并行归约仍可能带来细微差异；
10. ❌ 部署完就不管：模型、流量、上下文分布都会变，必须持续监控与压测。

## 十二、总结
- 推理优化围绕四个量：**TTFT、TPOT、吞吐、显存**；
- prefill 算力密集，decode 带宽密集，批处理与 KV 管理决定成本；
- PagedAttention + 连续批处理 + 量化 + 前缀缓存，是当前 serving 的基本盘；
- 先算显存与 SLO，再选框架与并行策略，最后用 goodput 验证，而不是只盯 GPU 利用率。
