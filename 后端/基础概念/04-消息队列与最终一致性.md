# 消息队列与最终一致性
> 一句话：**MQ 把同步调用变成异步事件，用「至少一次投递 + 幂等消费」换解耦与削峰；它带来的不是实时一致，而是可控的最终一致。**
> 定位：讲消息队列的模型、可靠性、顺序、事务消息与一致性落地，不绑定某一个中间件的全部 API。

## 一、为什么用消息队列
| 目的 | 说明 | 例子 |
|---|---|---|
| 解耦 | 生产者不关心谁消费、怎么消费 | 下单后发事件，积分/库存/通知各自订阅 |
| 异步 | 主链路只做核心动作，慢操作后置 | 注册成功先返回，再发欢迎邮件 |
| 削峰 | 把突发流量放进队列，按能力消费 | 秒杀、日志、埋点 |
| 广播 | 一个事件多个消费方 | 配置变更、缓存失效 |
| 数据管道 | 日志/变更流进入数仓 | binlog → Kafka → Flink |

代价同样明显：
- 系统从「一次 RPC」变成「生产者 + Broker + 消费者 + 重试 + 死信」；
- 消息会重复、会乱序、会积压；
- 排查问题需要跨三个组件看链路；
- 运维多了一套高可用存储。

> 只有同步调用、低流量、强一致的场景，不要为了「架构好看」上 MQ。

## 二、两种基本模型
### 1. 队列模型（RabbitMQ）
```
Producer → Exchange → Queue → Consumer（ack 后删除）
```
- 消息被消费并 ack 后从队列删除；
- 支持复杂路由（direct/fanout/topic/headers）；
- 单条消息延迟低，适合任务分发、业务事件；
- 吞吐量中等，堆积能力受内存/磁盘限制。

### 2. 日志模型（Kafka）
```
Producer → Topic/Partition（追加写）→ Consumer Group（按 offset 消费）
```
- 消息按 partition 追加，**不因消费而删除**，按时间/大小保留；
- 消费者维护 offset，可以重置、重放；
- 顺序只在 partition 内保证；
- 高吞吐，适合日志、流处理、事件溯源。

### 3. 其他形态
- **RocketMQ**：CommitLog + ConsumeQueue，支持事务消息、延迟消息、重试队列；
- **Pulsar**：存储与计算分离，多租户、分层存储；
- **云消息服务**：SQS/SNS、Pub/Sub，运维托管但能力有边界。

| 维度 | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| 模型 | 队列 | 分区日志 | 日志 + 队列索引 |
| 吞吐 | 中 | 很高 | 高 |
| 延迟 | 低 | 较低（批量时更高） | 低 |
| 顺序 | 单队列 | 单分区 | 单队列 |
| 重放 | 难 | 原生支持 | 支持 |
| 事务消息 | 不支持 | 事务生产者（限定范围） | 原生事务消息 |
| 典型场景 | 业务任务、复杂路由 | 日志、流计算 | 电商交易、订单 |

## 三、核心概念
| 概念 | 含义 |
|---|---|
| Producer | 发送方，负责分区选择、重试、批量 |
| Broker | 存储与转发节点 |
| Topic | 逻辑分类 |
| Partition / Queue | 并行与顺序的基本单位 |
| Consumer Group | 一组消费者共同消费一个 topic，组内分区不重复分配 |
| Offset | 消费者在分区中的位置 |
| Ack | 消费确认，决定消息何时可删除/提交位点 |
| Retention | 消息保留时间/大小 |
| Rebalance | 消费者增减导致分区重新分配 |

**并行度的上限由分区数决定**：一个分区在同一消费者组内只能被一个消费者消费，加机器超过分区数没有意义。

## 四、投递语义
| 语义 | 行为 | 风险 |
|---|---|---|
| At-most-once | 最多一次，可能丢 | 先 ack 后处理、网络丢失 |
| At-least-once | 至少一次，可能重复 | 处理成功但 ack 失败、重试 |
| Exactly-once | 恰好一次 | 只在特定边界内可实现 |

现实结论：
- **绝大多数业务用 At-least-once + 幂等消费**；
- Kafka 的 Exactly-once 依赖事务生产者、`read_committed` 与「读-处理-写」都在 Kafka 内闭环；
- 只要下游是数据库/HTTP 接口，端到端 Exactly-once 就必须靠**业务幂等**，没有免费的午餐。

## 五、生产者可靠性
### 1. 确认与重试
```properties
# Kafka 生产者关键配置
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
min.insync.replicas=2
delivery.timeout.ms=120000
```
- `acks=0`：发出即认为成功，可能丢；
- `acks=1`：leader 写入即成功，leader 宕机可能丢；
- `acks=all`：所有 ISR 确认，最安全；
- `enable.idempotence=true`：Broker 侧去重，避免重试导致重复；
- `max.in.flight` 与幂等配合，才能在不乱序的前提下提高吞吐。

### 2. 分区与顺序
- 相同 key 进入同一分区，才能保证该 key 的消息有序；
- 分区数增加会改变 key 的映射，**已存在的 key 顺序可能被打断**；
- 无 key 时轮询/粘性分区，顺序无保证。

### 3. 不要「双写」
```java
// 错误：数据库和 MQ 无法在同一个本地事务里
db.insert(order);
mq.send("order-created", order);  // 可能发送成功但事务回滚
```
两种结果都可能出错：
- DB 成功、MQ 失败 → 下游永远收不到；
- MQ 成功、DB 回滚 → 下游收到不存在的订单。

正确方案见第八节：**本地消息表（Outbox）** 或 **事务消息**。

## 六、消费者可靠性
### 1. 什么时候 ack
```
拉取消息 → 执行业务 → 提交本地事务 → ack / 提交 offset
```
- 先 ack 后处理：进程崩溃会丢消息；
- 处理完再 ack：可能重复消费（ack 失败/超时），需要幂等；
- RabbitMQ 用 `basic.ack`，Kafka 关闭自动提交后手动 `commitSync`。

### 2. 幂等消费
重复消息不可避免，消费端必须做到「同一消息执行多次，结果一致」：
```java
@Transactional
public void consume(OrderPaidEvent event) {
    // 唯一索引：message_id 或业务唯一键
    if (!dedupMapper.tryInsert(event.getMessageId())) {
        return;  // 已处理，直接忽略
    }
    orderMapper.markPaid(event.getOrderId());
    pointService.addPoint(event.getUserId(), event.getAmount());
}
```
常用手段：

| 手段 | 说明 |
|---|---|
| 唯一索引 | 最可靠，冲突即视为重复 |
| 去重表 | 记录 messageId + 处理时间，定期清理 |
| 状态机 | 只允许合法状态跃迁（待支付 → 已支付） |
| 版本号 | 更新时带上版本，旧事件不生效 |
| 天然幂等 | `SET status = 'PAID'` 而不是 `balance = balance + 1` |

### 3. 重试与死信
- 失败重试要**指数退避 + 随机抖动**，避免同一时刻重试风暴；
- 设置最大重试次数，超过进入 **DLQ（死信队列）**；
- 毒消息（反序列化失败、逻辑永远失败）不能无限重试，阻塞分区；
- DLQ 要有告警、查看、重放工具。

```java
// 重试主题分级（示意）
int attempt = headers.getAttempt();
if (attempt < 5) {
    publish("order-paid-retry-" + (attempt + 1), msg, backoff(attempt));
} else {
    publish("order-paid-dlq", msg);
}
```

### 4. Rebalance
- 消费者加入/离开/心跳超时会触发分区重新分配；
- 重平衡期间消费暂停，频繁重平衡会显著降低吞吐；
- Kafka 关注 `session.timeout.ms`、`heartbeat.interval.ms`、`max.poll.interval.ms`；
- 处理单批时间过长会超过 `max.poll.interval`，被踢出组；
- 使用 cooperative sticky 分配可减少全量暂停。

## 七、顺序问题
| 需求 | 方案 | 代价 |
|---|---|---|
| 全局有序 | 单分区/单队列，单消费者 | 吞吐受限 |
| 按业务键有序 | key hash 到同一分区 | 热点 key 可能倾斜 |
| 无序 | 多分区并行 | 最快，但业务要能接受乱序 |

容易破坏顺序的操作：
- 消费失败后重试，后一条先成功；
- 多个消费者消费同一业务键；
- 生产端重试且未开幂等；
- 分区扩容后 key 重新映射。

需要严格顺序时，消费端还要用**序列号/版本号**做校验，不能只依赖 MQ。

## 八、事务消息与 Outbox
### 1. 本地消息表（Outbox）
```
业务表 + outbox 表在同一个本地事务中写入
        ↓
中继器（定时任务 / CDC）读取 outbox 并发送到 MQ
        ↓
消费者幂等处理
```
```sql
CREATE TABLE outbox (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  aggregate_id BIGINT NOT NULL,
  event_type VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,  -- 0 待发送 1 已发送
  created_at DATETIME NOT NULL,
  INDEX idx_status_created (status, created_at)
);
```
```java
@Transactional
public void pay(long orderId) {
    orderMapper.markPaid(orderId);
    outboxMapper.insert(new OutboxEvent(orderId, "OrderPaid", payload));
}
```
中继器两种实现：
- **轮询**：`SELECT ... WHERE status = 0 LIMIT 100`，发送后更新状态；多实例中继要用 `FOR UPDATE SKIP LOCKED` 或抢占标记，避免同一批消息被重复发送；
- **CDC**：Debezium/Canal 读 binlog，直接投递，延迟更低。

优点：不依赖 MQ 事务，数据库是唯一事实源；缺点：至少一次投递，消费端必须幂等。

### 2. RocketMQ 事务消息
```
发送半消息（对消费者不可见）
  → 执行本地事务
  → 提交/回滚半消息
  → Broker 定时回查本地事务状态
```
适合「本地事务 + 发消息」强绑定场景；仍然需要消费端幂等。

### 3. Kafka 事务
```java
producer.initTransactions();
producer.beginTransaction();
producer.send(record1);
producer.send(record2);
producer.sendOffsetsToTransaction(offsets, groupId);
producer.commitTransaction();
```
保证「多个分区写入 + offset 提交」原子，但**不包含数据库事务**。

### 4. Saga
跨多个服务的长事务：
- 每个服务执行本地事务并发布事件；
- 失败时执行补偿动作（退款、释放库存）；
- 编排式（有中心协调者）或协同式（事件驱动）；
- 必须接受中间状态，并提供对账与人工修复。

## 九、最终一致性怎么落地
1. **定义一致性窗口**：允许几秒/几分钟不一致，超过就告警；
2. **幂等 + 重试 + 死信**：保证消息不丢、不重复生效；
3. **状态可见**：前端展示「处理中」，避免用户误以为失败；
4. **对账**：定时比较源与目标（订单 vs 积分流水），修复差异；
5. **版本/序列号**：旧事件不能覆盖新状态；
6. **可重放**：保留事件与 offset，出问题能重放修复；
7. **降级**：下游长时间不可用时，暂停消费或转人工，不要无限重试打爆下游。

> 最终一致不是「不管了」，而是「有明确窗口、有补偿、有对账」。

## 十、监控与运维
| 指标 | 说明 | 告警建议 |
|---|---|---|
| Consumer Lag | 未消费消息数/延迟 | 持续增长即告警 |
| 生产/消费速率 | 是否失衡 | 消费 < 生产持续 N 分钟 |
| 端到端延迟 | 生产时间 → 消费完成 | 超过 SLO |
| 重试次数 | 失败比例 | 突增说明下游异常 |
| DLQ 数量 | 死信堆积 | >0 就关注 |
| Rebalance 次数 | 频繁重平衡 | 突增影响吞吐 |
| 分区倾斜 | 单分区流量过高 | 热点 key |
| 磁盘/保留 | 存储水位 | 接近上限 |
| ISR/副本 | 副本同步状态 | 副本落后 |

其他运维点：
- 消息体建议 < 1MB，大文件放对象存储，消息只传 URL；
- 开启压缩（lz4/zstd）降低带宽；
- Schema 演进要兼容（Avro/Protobuf，向后/向前兼容）；
- 权限：TLS、认证、Topic 级 ACL；
- 容量：分区数、副本数、保留时间共同决定磁盘。

## 十一、选型建议
| 场景 | 推荐 | 原因 |
|---|---|---|
| 业务事件、任务分发、复杂路由 | RabbitMQ | 路由灵活、延迟低 |
| 日志、埋点、流计算、需要重放 | Kafka | 高吞吐、分区日志 |
| 电商交易、事务消息、延迟消息 | RocketMQ | 事务/延迟消息原生支持 |
| 多租户、分层存储 | Pulsar | 存算分离 |
| 不想运维 | 云 MQ | 托管，但注意配额与锁定期 |

> 不要用 Redis List 当核心 MQ：没有可靠 ack、重试、死信、堆积监控，丢消息时很难查。

## 十二、常见误区
1. ❌ 用了 MQ 就不会丢消息：acks、手动 ack、副本、DLQ 缺一不可；
2. ❌ Exactly-once 开箱即用：只在特定边界内成立，端到端仍要幂等；
3. ❌ 自动 ack 更简单：进程崩溃就丢消息；
4. ❌ 失败一直重试就行：毒消息会阻塞分区，必须有上限与死信；
5. ❌ 全局顺序很重要：绝大多数业务只需要按业务键有序；
6. ❌ 分区越多越好：增加重平衡、文件句柄、元数据开销，且顺序会受影响；
7. ❌ MQ 可以当数据库：保留期有限，不是长期存储；
8. ❌ 消费者可以无限扩容：并行度受分区数限制；
9. ❌ 最终一致等于不一致：需要窗口、补偿、对账；
10. ❌ 双写 DB 和 MQ 没问题：没有本地事务保证，必须用 Outbox/事务消息。

## 十三、总结
- MQ 的价值是**解耦、异步、削峰、重放**，代价是复杂度与最终一致；
- 可靠性公式：**生产端确认 + 持久化副本 + 消费端手动 ack + 幂等 + 重试上限 + 死信**；
- 顺序只在分区/队列内保证，跨 key 的全局顺序要付出吞吐代价；
- 跨服务一致性优先用 **Outbox / 事务消息 + 幂等消费 + 对账**，不要幻想端到端 Exactly-once。
