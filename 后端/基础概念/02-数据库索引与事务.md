# 数据库索引与事务
> 一句话：**索引决定「查得快不快」，事务决定「改得对不对」；前者是数据结构与查询优化问题，后者是并发控制与一致性模型问题。**
> 主线：以 MySQL InnoDB 为例，结论同样适用于大多数关系型数据库。

## 一、索引的本质：减少扫描的数据量
### 1. 为什么是 B+ 树
- 磁盘按页读取（InnoDB 默认 16KB），一次 I/O 的成本远高于内存比较；
- B+ 树**矮胖**：非叶子节点只存键和指针，一页能放上千个键，千万级数据通常只有 3~4 层；
- **所有数据都在叶子节点**，叶子之间用双向链表连接，范围查询只需顺序扫描；
- 对比：

| 结构 | 等值查询 | 范围查询 | 问题 |
|---|---|---|---|
| 哈希 | O(1) | ❌ 不支持 | 无法排序、范围扫描 |
| 二叉搜索树 | O(log n) | 一般 | 树太高，I/O 次数多 |
| B 树 | O(log n) | 一般 | 非叶子也存数据，扇出小 |
| **B+ 树** | O(log n) | ✅ 叶子链表 | 写入维护成本、页分裂 |

### 2. InnoDB 的聚簇索引
```
主键索引（聚簇索引）叶子节点： [主键值 | 整行数据]
二级索引叶子节点：           [索引列 | 主键值]  → 再回表查整行
```
- 表就是按主键组织的 B+ 树，**没有主键时用隐藏 row_id**；
- 二级索引只存主键，查完整行需要**回表**；
- 因此主键要短且有序：自增 bigint 优于随机 UUID（随机主键会导致页分裂与缓存命中率下降）。

> 覆盖索引（Covering Index）：查询需要的列都在索引里，无需回表。`EXPLAIN` 的 `Extra` 出现 `Using index`。

## 二、索引类型与设计
### 1. 常见类型
| 类型 | 说明 | 场景 |
|---|---|---|
| 主键索引 | 聚簇索引，唯一且非空 | 每张表必备 |
| 唯一索引 | 约束 + 查询 | 幂等键、业务唯一编号 |
| 普通索引 | 加速查询 | 高频过滤/排序字段 |
| 联合索引 | 多列组合 | 多条件查询、覆盖索引 |
| 前缀索引 | 只索引字符串前 N 位 | 长 URL、邮箱，节省空间 |
| 全文索引 | 分词检索 | 简单文本搜索（复杂场景用 ES） |

### 2. 联合索引与最左前缀
```sql
ALTER TABLE orders ADD INDEX idx_user_status_time (user_id, status, created_at);
```
能用到索引的查询：
```sql
WHERE user_id = 1                                  -- 用 user_id
WHERE user_id = 1 AND status = 2                   -- 用 user_id + status
WHERE user_id = 1 AND status = 2 AND created_at > '2026-01-01'
                                                   -- 三列都用上
WHERE user_id = 1 ORDER BY status, created_at      -- 排序也可利用索引
```
用不上的情况：
```sql
WHERE status = 2                                   -- ❌ 跳过最左列
WHERE user_id = 1 AND created_at > '2026-01-01'    -- ⚠️ 只能用 user_id
WHERE user_id = 1 AND status > 2 AND created_at > '2026-01-01'
                                                   -- ⚠️ status 是范围，created_at 只能靠 ICP 过滤，无法继续缩小索引范围
```
设计口诀：
1. **等值条件放前面，范围条件放后面**；
2. 排序、分组字段尽量接在等值条件之后；
3. 区分度高的列不一定必须放最左，**要看查询模式**；
4. 一个联合索引可以服务多个最左前缀查询，不要为每个组合建一条。

### 3. 选择性
```sql
-- 区分度 = 不重复值 / 总行数，越接近 1 越好
SELECT COUNT(DISTINCT status) / COUNT(*) FROM orders;
```
- 性别、状态这类低区分度列单独建索引，优化器往往仍选择全表扫描；
- 但低区分度列放在联合索引里，配合高区分度列，仍能发挥作用；
- 前缀索引要选足够长的前缀，使区分度接近完整列。

## 三、EXPLAIN：看懂执行计划
```sql
EXPLAIN ANALYZE
SELECT id, amount FROM orders
WHERE user_id = 42 AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```
| 字段 | 关注点 |
|---|---|
| `type` | 访问类型，性能从好到差：`system > const > eq_ref > ref > range > index > ALL` |
| `key` | 实际使用的索引，`NULL` 表示没走索引 |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 扫描后剩余比例，过低说明索引过滤能力差 |
| `Extra` | `Using index`（覆盖）、`Using index condition`（ICP）、`Using filesort`、`Using temporary` |

需要警惕的信号：
- `type=ALL` + `rows` 很大：全表扫描；
- `Using filesort`：无法利用索引排序，数据量大时非常慢；
- `Using temporary`：分组/去重用了临时表；
- `rows` 与实际差距巨大：统计信息过期，可 `ANALYZE TABLE`。

> `EXPLAIN` 是预估，`EXPLAIN ANALYZE`（MySQL 8.0.18+）会真实执行并给出实际行数与耗时，更适合定位慢查询。

## 四、索引失效的常见原因
| 写法 | 为什么失效 | 改法 |
|---|---|---|
| `WHERE DATE(created_at) = '2026-01-01'` | 列上做函数运算 | 改成范围：`>= 当天 AND < 次日` |
| `WHERE phone = 13800000000`（phone 是 varchar） | 隐式类型转换 | 参数用字符串 |
| `WHERE name LIKE '%张%'` | 前导通配符 | 前缀匹配、全文索引、ES |
| `WHERE a = 1 OR b = 2`（b 无索引） | 无法同时走索引 | 分别查询合并，或补索引 |
| `WHERE status != 1` | 优化器判断扫描比例高 | 改成枚举范围或补联合索引 |
| `WHERE a + 1 = 10` | 列参与运算 | 把运算移到右侧 |
| 联合索引跳过最左列 | 不满足最左前缀 | 调整索引或查询 |

补充：
- `IS NULL` 可以使用索引，`NULL` 在 InnoDB 中是被索引的；
- `ORDER BY` 使用索引的前提是排序顺序与索引顺序一致，且前面列是等值条件；
- 索引不是越多越好：每个索引都会增加写入成本、占用 buffer pool、拖慢 DDL。

## 五、写入路径：一次 UPDATE 发生了什么
```
1. 从 buffer pool 找页，找不到就从磁盘读入
2. 修改页内容（脏页）
3. 写 undo log（回滚 + MVCC）
4. 写 redo log（WAL，保证崩溃恢复）
5. 事务提交：redo 刷盘（可配置）+ 写 binlog
6. 后台线程异步把脏页刷回磁盘
```
### 1. WAL 的意义
- 随机写页 → 顺序写日志，大幅降低提交延迟；
- 崩溃后用 redo 重放已提交事务，用 undo 回滚未提交事务；
- `innodb_flush_log_at_trx_commit`：

| 值 | 行为 | 安全性 |
|---|---|---|
| 1 | 每次提交刷盘 | 最安全，性能最低 |
| 2 | 写 OS cache，每秒刷盘 | 宕机可能丢 1 秒 |
| 0 | 每秒写并刷盘 | 可能丢 1 秒以上 |

### 2. binlog 与两阶段提交
- binlog 是逻辑日志，用于主从复制与数据恢复；
- redo 与 binlog 通过**两阶段提交**保证一致：redo prepare → 写 binlog → redo commit；
- `sync_binlog=1` 保证每次提交都刷 binlog，金融级场景常用；
- 大事务会放大 redo、锁、主从延迟，必须拆分。

### 3. 其他关键机制
- **undo log**：回滚 + MVCC 版本链；
- **change buffer**：二级索引页不在内存时先缓存变更，减少随机读；
- **doublewrite**：防止页写入过程中断电导致半页损坏。

## 六、事务与隔离级别
### 1. ACID
| 特性 | 含义 | InnoDB 实现 |
|---|---|---|
| 原子性 Atomicity | 要么全成功，要么全失败 | undo log |
| 一致性 Consistency | 约束、外键、业务规则不被破坏 | 由数据库与应用共同保证 |
| 隔离性 Isolation | 并发事务互不干扰 | 锁 + MVCC |
| 持久性 Durability | 提交后不丢 | redo log + 刷盘 |

### 2. 三种读异常
- **脏读**：读到其他事务未提交的数据；
- **不可重复读**：同一事务内两次读同一行，结果不同（别人改了）；
- **幻读**：同一事务内两次范围查询，行数不同（别人插入了）。

### 3. 隔离级别
| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| READ UNCOMMITTED | ✅ 可能 | ✅ | ✅ | 几乎不用 |
| READ COMMITTED | ❌ | ✅ | ✅ | 每条语句一个新快照 |
| REPEATABLE READ | ❌ | ❌ | ⚠️ 快照读不会，当前读靠锁 | MySQL 默认 |
| SERIALIZABLE | ❌ | ❌ | ❌ | 全部加锁，并发最差 |

> PostgreSQL 默认是 READ COMMITTED；MySQL 默认 REPEATABLE READ。跨库迁移时不要假设默认级别一致。

### 4. MVCC：快照读为什么不需要加锁
InnoDB 每行有隐藏列：
- `DB_TRX_ID`：最后修改该行的事务 ID；
- `DB_ROLL_PTR`：指向 undo 版本链。

事务第一次快照读时生成 **Read View**，记录当前活跃事务 ID 集合。读取时沿版本链找到「对当前事务可见」的版本：
- 版本事务 ID < 最小活跃 ID：已提交，可见；
- 版本事务 ID 在活跃集合中：未提交，不可见；
- 版本事务 ID ≥ 下一个事务 ID：在本事务之后开启，不可见。

| 读类型 | 语句 | 是否加锁 | 读什么 |
|---|---|---|---|
| 快照读 | 普通 `SELECT` | 否 | Read View 对应的历史版本 |
| 当前读 | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` | 是 | 最新已提交版本 + 锁 |

### 5. RR 下的幻读
- **快照读**：一致性视图固定，看不到新插入的行，不会幻读；
- **当前读**：用 **next-key lock（记录锁 + 间隙锁）** 锁住范围，阻止其他事务在间隙插入；
- 因此「RR 完全解决幻读」不准确，准确说法是「快照读靠 MVCC，当前读靠锁」。

`READ COMMITTED` 下一般不加间隙锁（外键、唯一性检查除外），并发更高，但可能出现幻读，很多互联网业务会主动选择 RC。

### 6. 锁的类型
| 锁 | 作用 |
|---|---|
| 记录锁 Record Lock | 锁住某一行索引记录 |
| 间隙锁 Gap Lock | 锁住索引记录之间的间隙，阻止插入 |
| Next-Key Lock | 记录锁 + 间隙锁，RR 范围查询默认 |
| 插入意向锁 | 插入前申请，和间隙锁冲突 |
| 自增锁 | 自增主键分配 |

> 锁是加在**索引**上的。如果查询没走索引，可能锁住大量行甚至全表，这是「更新变慢、死锁变多」的常见原因。

## 七、死锁：如何产生、如何减少
```sql
-- 事务 A
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 事务 B（相反顺序）
UPDATE accounts SET balance = balance - 100 WHERE id = 2;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
```
两个事务各持有一把锁、等待对方释放，形成环。InnoDB 会检测死锁并回滚其中一个事务（`Deadlock found when trying to get lock`）。

减少死锁：
1. **固定加锁顺序**（按主键升序更新）；
2. 事务尽量短，减少持锁时间；
3. 更新走主键或唯一索引，缩小锁范围；
4. 避免大范围 `UPDATE ... WHERE status = ?`；
5. 应用层捕获死锁异常并**有限次重试**；
6. 必要时降低隔离级别到 RC，减少间隙锁。

## 八、事务最佳实践
1. **短事务**：不要在事务里做 RPC、发消息、等用户输入；
2. **小批量**：大批量更新拆成多批，避免长事务与主从延迟；
3. **固定顺序**：多表/多行更新按统一顺序加锁；
4. **幂等**：重试与消息消费都要有唯一键或状态机；
5. **合理隔离级别**：默认 RR 足够，读多写多且能接受幻读时可用 RC；
6. **避免 `SELECT *`**：减少回表与网络传输；
7. **监控锁等待**：`innodb_lock_wait_timeout`、`SHOW ENGINE INNODB STATUS`；
8. **主从延迟**：写后立即读走主库，或使用 GTID/位点等待。

## 九、容量与扩展
- `innodb_buffer_pool_size` 通常设为物理内存的 60%~75%（专用数据库）；
- 连接数不是越多越好，应用侧连接池与数据库 `max_connections` 要匹配；
- 单表过大时先考虑归档、分区，最后才分库分表；
- 分库分表会带来跨分片事务、聚合查询、扩容迁移成本，不要过早引入；
- 主从复制：

| 模式 | 特点 | 风险 |
|---|---|---|
| 异步复制 | 主库提交即返回 | 主库宕机可能丢数据 |
| 半同步复制 | 至少一个从库确认 | 延迟升高 |
| 组复制 / MGR | 多数派提交 | 运维复杂 |

## 十、常见误区
1. ❌ 索引越多越好：写放大、空间占用、优化器选择困难；
2. ❌ 联合索引列顺序无所谓：最左前缀与范围条件直接决定能否用上；
3. ❌ `LIKE '%x%'` 也能走索引：前导通配符基本等于全表扫描；
4. ❌ 隐式类型转换没关系：字符串列传数字会退化为全表扫描；
5. ❌ RR 完全没有幻读：快照读没有，当前读靠间隙锁；
6. ❌ 事务越长越安全：锁持有久、undo 膨胀、主从延迟变大；
7. ❌ 主从一定强一致：异步复制有延迟，读从库可能读到旧数据；
8. ❌ `NULL` 不能建索引：InnoDB 会索引 `NULL`，`IS NULL` 也可能走索引；
9. ❌ `count(*)` 一定比 `count(1)` 慢：InnoDB 三者近似，都会扫描；
10. ❌ 分库分表能解决所有性能问题：索引与 SQL 写不好，分片只会让问题更复杂。

## 十一、总结
- 索引的核心是**用空间换 I/O**：B+ 树、最左前缀、覆盖索引、回表；
- 事务的核心是**用锁与版本控制换一致性**：隔离级别、MVCC、next-key lock；
- 慢查询先看执行计划，死锁先看加锁顺序，主从问题先看延迟；
- 设计表时就想好查询模式，比事后加索引有效得多。
