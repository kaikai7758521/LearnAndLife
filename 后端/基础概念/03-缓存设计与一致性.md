# 缓存设计与一致性
> 一句话：**缓存是用「可控的旧数据」换延迟与吞吐**；难点从来不是把数据放进去，而是决定它什么时候失效、失效时系统还能不能活。
> 定位：讲应用层缓存的设计模式与一致性策略，以本地缓存 + Redis 为主，不展开某个中间件的全部命令。

## 一、缓存为什么有效，又为什么危险
### 1. 延迟差距
| 访问 | 量级 |
|---|---|
| L1 缓存 | ~1ns |
| 内存 | ~100ns |
| SSD 随机读 | ~100µs |
| 同机房网络 RTT | ~0.5ms |
| 数据库一次索引查询 | ~1~10ms |
| 跨机房 RTT | ~30ms+ |

一次数据库查询可能是内存访问的几万倍。把热点数据放进内存，QPS 和延迟都会有数量级改善。

### 2. 收益与代价
| 收益 | 代价 |
|---|---|
| 降低延迟 | 数据可能过期 |
| 提升吞吐 | 多一层故障点 |
| 保护数据库 | 内存与运维成本 |
| 削峰 | 缓存击穿时反而压垮 DB |

缓存适合：**读多写少、热点集中、能接受短暂不一致**。
不适合：强一致交易、写多读少、命中率极低、数据量远超内存。

## 二、缓存放在哪：分层
```
浏览器缓存 → CDN → 网关缓存 → 本地缓存（进程内）→ Redis → 数据库 Buffer Pool
```
| 层级 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 本地缓存 | Caffeine、Guava、Go sync.Map | 纳秒级、无网络 | 多实例不一致、容量受限 |
| 分布式缓存 | Redis、Memcached | 共享、容量大 | 多一次网络往返、需高可用 |
| CDN | 边缘节点 | 就近访问 | 动态内容难缓存、刷新慢 |

多级缓存的典型组合：**本地缓存扛热点 + Redis 扛共享**。
本地缓存的失效要靠：
- 短 TTL（接受短暂不一致）；
- 发布订阅广播失效消息；
- 版本号写进 key，读时校验。

## 三、五种缓存模式
| 模式 | 读 | 写 | 特点 |
|---|---|---|---|
| **Cache-Aside（旁路）** | 应用先读缓存，未命中查 DB 并回填 | 更新 DB，删除缓存 | 最常用，逻辑由应用控制 |
| Read-Through | 应用只读缓存，缓存负责回源 | — | 需要缓存层支持加载器 |
| Write-Through | — | 同步写缓存 + DB | 一致性好，写延迟高 |
| Write-Behind | — | 写缓存，异步刷 DB | 写快，宕机可能丢数据 |
| Write-Around | — | 直接写 DB，不碰缓存 | 适合写后不怎么读的数据 |

### Cache-Aside 标准写法
```java
// 读
public User getUser(long id) {
    String key = "user:" + id;
    User cached = redis.get(key);
    if (cached != null) return cached;

    User user = db.selectById(id);
    if (user == null) {
        redis.set(key, NULL_MARKER, 60);      // 空值缓存，防穿透
        return null;
    }
    redis.set(key, user, 300 + random(0, 60)); // TTL 加随机，防雪崩
    return user;
}

// 写
public void updateUser(User user) {
    db.update(user);
    redis.delete("user:" + user.getId());      // 删除而不是更新
}
```
> 为什么写时**删除**而不是更新缓存：两个并发写可能以错误顺序落到缓存，导致旧值覆盖新值。删除最多造成一次 miss，更新却可能留下长期脏数据。

## 四、一致性：缓存与数据库怎么同步
### 1. 先更新数据库，再删除缓存
这是工程上的默认方案：
```
写：UPDATE DB → DELETE cache
读：GET cache → miss → SELECT DB → SET cache
```
仍然存在一个经典竞态：
```
读请求 miss → 查 DB 得到旧值
写请求 UPDATE DB 为新值 → DELETE cache
读请求把旧值 SET 进缓存   ← 脏数据
```
发生概率不高，但高并发下会真实出现。常见缓解手段：

| 手段 | 做法 | 效果 |
|---|---|---|
| TTL | 所有缓存都设置过期时间 | 最终一致，兜底 |
| 延迟双删 | 提交后删一次，延迟 500ms~1s 再删一次 | 覆盖大部分竞态窗口 |
| 订阅 binlog | Canal/Debezium 监听变更，异步删缓存 | 不依赖业务代码，较可靠 |
| 版本号 | value 带 version，写时校验 | 能识别旧值 |
| 强一致读 | 关键读走主库，不读缓存 | 牺牲性能换正确 |

### 2. 延迟双删
```java
db.update(user);
redis.delete(key);
executor.schedule(() -> redis.delete(key), 800, MILLISECONDS);
```
延迟时间要覆盖「读请求回填旧值」的窗口，通常取主从同步延迟 + 业务读耗时。它不是银弹，只是降低概率。

### 3. 基于 binlog 的最终一致
```
MySQL binlog → Canal/Debezium → MQ（按主键分区）→ 消费端删除/刷新缓存
```
优点：
- 业务代码不需要关心缓存；
- 数据库是唯一事实源，缓存只是投影；
- 按 key 分区可保证同一行的变更有序。

代价：链路更长、需要处理 MQ 重复与延迟。

### 4. 读己之写
用户写完立刻读，可能读到旧缓存：
- 写后短时间读主库；
- 写成功后主动设置新值（带版本）；
- 前端把新值直接带回，减少一次读。

> 强一致场景不要硬扛缓存：要么不缓存，要么用「数据库 + 版本号 + 读主库」保证。

## 五、缓存的三个经典问题
### 1. 穿透（Penetration）
**问题**：查询根本不存在的数据，缓存永远不命中，每次都打到 DB。
**解法**：
1. **空值缓存**：查不到也缓存 `NULL`，TTL 短（30~60 秒）；
2. **布隆过滤器**：启动时把存在的 key 放进过滤器，不存在直接拒绝；
3. **参数校验与限流**：非法 ID、超长 key 直接拦截；
4. **异步回填**：对可疑 key 做合并查询。

```java
if (!bloom.mightContain(key)) return null;  // 一定不存在
```

### 2. 击穿（Breakdown）
**问题**：某个热点 key 过期瞬间，大量请求同时回源 DB。
**解法**：
1. **互斥重建**：只允许一个请求回源，其他等待；
2. **逻辑过期**：value 里存 `expireAt`，过期后异步刷新，其他请求先返回旧值；
3. **永不过期 + 后台刷新**：适合极热点数据；
4. **单飞（singleflight）**：同一进程内合并相同 key 的请求。

```java
// 互斥重建（示意）
if (redis.set("lock:" + key, "1", "NX", "PX", 3000)) {
    try {
        User user = db.selectById(id);
        redis.set(key, user, ttl);
    } finally {
        redis.delete("lock:" + key);
    }
} else {
    Thread.sleep(50);
    return getUser(id);   // 重试读缓存
}
```

### 3. 雪崩（Avalanche）
**问题**：大量 key 同时过期，或 Redis 集群整体故障，流量瞬间压到 DB。
**解法**：
1. **TTL 加随机**：`ttl = base + random(0, base * 0.2)`；
2. **多级缓存**：本地缓存兜底；
3. **高可用**：哨兵/集群、主从切换、多副本；
4. **熔断降级**：缓存不可用时限制回源 QPS，返回默认值；
5. **预热**：发布/重启后先加载热点，避免冷启动打穿。

### 4. 热点 Key 与大 Key
| 问题 | 表现 | 处理 |
|---|---|---|
| 热点 Key | 单分片 CPU/带宽打满 | 本地缓存、key 拆分、读写分离 |
| 大 Key | 单次操作慢、网络阻塞、删除卡顿 | 拆分为多个 key、压缩、限制集合大小 |
| 大集合遍历 | `HGETALL`/`SMEMBERS` 阻塞 | 用 `HSCAN`/`SSCAN` 分批 |

经验阈值：字符串 value 超过 10KB、集合元素超过 5000，就要考虑拆分。检测工具：
```bash
redis-cli --bigkeys
redis-cli --hotkeys          # 需要 LFU 策略
redis-cli MEMORY USAGE key
```

## 六、Redis 关键机制
### 1. 单线程与快命令
- Redis 的命令执行是**单线程**的（6.0+ 的网络读写可用 IO 线程），一条慢命令会阻塞所有请求；
- 禁止在生产执行 `KEYS *`、`FLUSHALL`、大 key 的 `HGETALL`、超长 Lua 脚本；
- `SCAN` 是渐进式遍历，但可能重复、不保证一致。

### 2. Pipeline、事务与 Lua
| 方式 | 原子性 | 用途 |
|---|---|---|
| Pipeline | ❌ 不保证 | 批量发送，减少 RTT |
| MULTI/EXEC | ⚠️ 命令入队，运行时错误不回滚 | 简单事务 |
| Lua | ✅ 整体原子 | 复杂原子逻辑，但要短 |

> Pipeline 只是把多条命令打包发送，中间可能插入其他客户端的命令；需要原子性时用 Lua。

### 3. 集群
- Redis Cluster 有 **16384 个哈希槽**，key 通过 CRC16 映射；
- 多 key 操作要求在同一槽，可用 `{tag}` 指定 hash tag；
- 跨槽事务、跨槽 Lua 不支持；
- 扩容需要迁移槽，客户端要能处理 `MOVED`/`ASK` 重定向。

### 4. 淘汰策略
| 策略 | 行为 |
|---|---|
| `noeviction` | 内存满时写入报错（默认） |
| `allkeys-lru` | 所有 key 按近似 LRU 淘汰 |
| `volatile-lru` | 只淘汰设置了 TTL 的 key |
| `allkeys-lfu` | 按访问频率淘汰，适合热点稳定场景 |
| `volatile-ttl` | 优先淘汰快过期的 key |
| `random` | 随机淘汰 |

> LRU 是**近似实现**（采样若干 key），不是精确链表；缓存命中率异常时先看淘汰策略与 `maxmemory`。

### 5. 持久化
| 方式 | 原理 | 优点 | 风险 |
|---|---|---|---|
| RDB | fork 子进程生成快照 | 文件小、恢复快 | 可能丢最后一次快照后的数据 |
| AOF | 追加写命令，`everysec` 刷盘 | 丢数据少 | 文件大、恢复慢 |
| 混合 | RDB + AOF | 兼顾 | 运维复杂 |

> Redis 持久化不等于数据库级持久性：fork 阻塞、COW 可能显著增加内存占用、AOF 刷盘延迟都要纳入容量设计。

### 6. 内存与碎片
- 关注 `used_memory`、`used_memory_rss`、`mem_fragmentation_ratio`；
- 大量删除后碎片率高，可开启 `activedefrag` 或重启迁移；
- 对象编码（listpack/ziplist、intset）影响内存，集合过大时会转成哈希表。

## 七、分布式锁
### 1. 正确姿势
```bash
# 加锁：唯一 value + 过期时间，必须原子
SET lock:order:123 "uuid-xxx" NX PX 30000
```
```lua
-- 释放：只能删自己的锁
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```
要点：
1. value 必须是唯一标识，防止误删别人的锁；
2. 必须设置过期时间，防止死锁；
3. 业务时间可能超过 TTL 时，需要**看门狗续期**；
4. 续期与业务线程绑定，进程崩溃后锁自然过期；
5. 对正确性要求极高时，加 **fencing token**（单调递增版本），让下游拒绝旧持有者的写。

### 2. 不要神话分布式锁
- Redis 主从异步复制，主库宕机可能丢锁；
- RedLock 依赖时钟与多节点，学界对安全性有争议；
- 能用数据库唯一索引、乐观锁、状态机解决的，优先用数据库；
- 分布式锁适合「尽量避免重复执行」，不适合「绝对不允许重复」。

## 八、缓存治理
### 1. 指标
| 指标 | 说明 |
|---|---|
| 命中率 | `hits / (hits + misses)`，低于预期先查 key 设计与 TTL |
| 延迟 p99 | 是否被慢命令/大 key 拖累 |
| 内存使用率 | 接近 `maxmemory` 会频繁淘汰 |
| 淘汰数 | 突增说明容量不足 |
| 连接数 | 连接泄漏或客户端池过大 |
| 慢日志 | `SLOWLOG GET`，关注 >10ms 的命令 |
| 热 key / 大 key | 定期扫描，提前拆分 |

### 2. Key 设计
```
业务:对象:ID:版本
user:1001:v3
```
- 加业务前缀，避免多业务共用实例时冲突；
- 不要直接把用户输入拼进 key，防注入与超长 key；
- 版本号可用于「换 key 即失效」，比逐个删除更安全；
- 控制 key 长度，过长浪费内存。

### 3. 容量与预热
- 估算：`key 数 × (value 大小 + key 开销 + 对象头)`，再留 30%~50% 余量；
- 发布/扩容后按热点列表预热，避免冷启动打穿；
- 大促前做压测，重点看**缓存失效瞬间**的 DB 承压。

### 4. 降级
- 缓存集群故障时，不能把全部流量放给 DB：
  - 本地缓存兜底；
  - 限制回源 QPS；
  - 返回默认值/旧值；
  - 非核心功能直接关闭。
- 降级开关要能灰度、可回滚。

## 九、典型场景
| 场景 | 方案 | 注意 |
|---|---|---|
| 会话 | Redis Hash + TTL | 续期、登出即删 |
| 排行榜 | ZSet | 分数相同按 member 排序 |
| 计数器/限流 | INCR + 过期，或 Lua | 原子性、时钟 |
| 分布式锁 | SET NX PX + Lua 释放 | 续期、fencing |
| 热点详情页 | 本地 + Redis 两级 | 失效广播 |
| 去重 | Set / 布隆过滤器 | 布隆有误判、难删除 |
| 简单队列 | List / Stream | 可靠性不如专业 MQ |

> 不要把 Redis 当主数据库：它的持久化与一致性模型服务于缓存场景，不是事务型存储。

## 十、常见误区
1. ❌ 缓存就是数据库：缓存可丢，数据库不可丢；
2. ❌ 写时更新缓存比删除更好：并发写下容易旧值覆盖新值；
3. ❌ TTL 越短越一致：DB 压力越大，击穿风险越高；
4. ❌ 缓存挂了只是变慢：流量瞬间打到 DB，可能直接雪崩；
5. ❌ 大 key 只占内存：它会阻塞单线程、拖慢整个实例；
6. ❌ 生产可以用 `KEYS *`：O(n) 阻塞，必须用 `SCAN`；
7. ❌ Redis 单线程就没有并发问题：单条命令原子，多命令组合仍有竞态；
8. ❌ 分布式锁绝对安全：主从切换、时钟漂移、续期失败都会破坏互斥；
9. ❌ LRU 是精确的：Redis 是采样近似，命中率要实测；
10. ❌ RDB/AOF 让 Redis 变成可靠数据库：持久化有丢失窗口与恢复成本。

## 十一、总结
- 缓存的收益来自**热点与读多写少**，代价是**一致性窗口与故障放大**；
- 默认方案：Cache-Aside + 更新 DB 后删缓存 + TTL 兜底；
- 三个必答题：穿透、击穿、雪崩，分别用空值/布隆、互斥/逻辑过期、TTL 随机/多级/降级；
- 把缓存当「可丢失的投影」，数据库才是事实源，系统才能在缓存故障时活下去。
