# 一次 HTTP 请求的后端旅程
> 一句话：一次请求的耗时 = **接入层 + 排队 + 应用处理 + 存储 + 序列化**，任何一段的超时、重试、锁等待都会被放大成用户可见的延迟；后端优化的本质，是给每一段建立预算，并让失败可控。
> 视角：从客户端发出请求，到响应回到客户端，沿途每个组件在做什么、会在哪里出问题。

## 一、全景图
```
Client
  │ DNS / CDN
  ▼
L4 负载均衡（TCP）
  ▼
L7 网关（Nginx / Envoy）
  │ TLS 终止、路由、限流、鉴权
  ▼
应用服务（线程 / 协程 / 事件循环）
  ├─ 中间件：Trace → 日志 → 鉴权 → 限流 → 参数校验
  ├─ 业务逻辑
  ├─ 本地缓存 → Redis
  ├─ 数据库连接池 → MySQL
  ├─ RPC / 消息队列
  └─ 序列化 → 响应
```
| 阶段 | 典型耗时（内网） | 主要风险 |
|---|---|---|
| DNS / TLS | 10~200ms（首次） | 解析慢、证书链不全、握手失败 |
| L4 / L7 转发 | 0.1~2ms | 连接打满、队列堆积、超时配置错误 |
| 应用排队 | 0~数百 ms | 线程池/连接池耗尽 |
| 业务处理 | 1~100ms | 锁、慢查询、同步 RPC、GC |
| 存储访问 | 0.2~50ms | 索引缺失、连接池不足、主从延迟 |
| 序列化/网络 | 1~50ms | 大响应体、压缩开销、带宽 |

> 延迟不是「平均值」问题，而是**尾延迟**问题：p99 往往由排队、锁等待、GC、重试决定。

## 二、接入层：请求先到哪里
### 1. DNS 与 CDN
- DNS 决定用户连到哪个机房/IP，TTL 过长会导致故障切换慢，过短会放大解析压力；
- CDN 承担静态资源、图片、视频，缓存键设计错误会导致「更新不生效」或「命中率低」；
- 动态请求一般回源到网关，注意 `X-Forwarded-For`、`X-Forwarded-Proto` 的信任链，避免伪造 IP。

### 2. L4 与 L7
| 层 | 代表 | 看什么 | 典型能力 |
|---|---|---|---|
| L4 | LVS、云 CLB、F5 | IP/端口 | 四层转发、DSR、连接保持 |
| L7 | Nginx、Envoy、网关 | HTTP 头/路径 | 路由、TLS、限流、鉴权、灰度 |

L7 网关通常负责：
- TLS 终止（证书、会话复用、OCSP）；
- 路由与灰度（按 header、cookie、权重）；
- 限流、熔断、WAF；
- 请求头清洗、body 大小限制、压缩；
- 访问日志与 trace 注入。

### 3. 连接复用
- HTTP/1.1 默认 keep-alive，但同一连接上请求**串行**，存在队头阻塞；
- HTTP/2 多路复用解决应用层队头阻塞，但 TCP 层丢包仍会阻塞所有流；
- HTTP/3 基于 QUIC（UDP），减少握手与队头阻塞，适合弱网；
- 网关到上游必须配置**连接池 + keep-alive**，否则每次请求都要 TCP/TLS 握手，延迟直接翻倍。

```nginx
upstream app_backend {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    keepalive 64;                 # 与上游保持长连接
}

location /api/ {
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_connect_timeout 1s;     # 建连超时要短
    proxy_read_timeout 5s;        # 必须小于客户端超时
    proxy_next_upstream error timeout http_502;
    proxy_next_upstream_tries 2;
}
```
> `proxy_next_upstream` 的重试只对**幂等请求**安全；POST 重试可能造成重复下单。重试策略要和业务幂等一起设计。

## 三、应用层：请求如何被处理
### 1. 处理模型
| 模型 | 代表 | 优点 | 代价 |
|---|---|---|---|
| 线程 per request | Tomcat、Spring MVC | 编程简单、阻塞调用直观 | 线程昂贵，池满即排队 |
| 协程 | Go、Kotlin Coroutine | 轻量、高并发 | 需要全链路非阻塞 |
| 事件循环 | Node.js、Nginx、Redis | 单线程高吞吐 | 一个阻塞调用卡死全进程 |
| 虚拟线程 | Java 21+ | 阻塞写法 + 高并发 | 仍需注意锁与池化资源 |

无论哪种模型，**线程/协程池都是有限资源**：一旦下游变慢，请求会堆在池队列里，表现为「CPU 不高但延迟暴涨」。

### 2. 中间件顺序
推荐顺序（越靠前越便宜、越全局）：
```
Trace/RequestId → 访问日志 → 鉴权 → 限流 → 参数校验 → 业务 → 响应包装
```
- Trace 必须最先注入，保证后续所有日志、RPC、SQL 都能带上 traceId；
- 鉴权放在限流之前还是之后取决于成本：JWT 校验便宜可前置，查库鉴权应后置；
- 参数校验要限制 body 大小、数组长度、分页大小，防止内存与慢查询攻击。

### 3. 请求上下文
一个请求应携带：
- `traceId` / `spanId`：全链路追踪；
- `userId` / `tenantId`：权限与多租户隔离；
- `deadline`：剩余可用时间，向下游传递；
- `idempotencyKey`：写请求防重。

> 无状态服务把 session 放 Redis 或 JWT，但**不要把大对象塞进 JWT**，它每个请求都要传输与解析。

## 四、业务处理：最容易出事的地方
### 1. 事务边界
```java
// 错误：事务里做 RPC / 发消息 / 等锁
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);
    inventoryClient.deduct(order.getSkuId());  // 远程调用可能超时
    mqProducer.send("order-created", order);   // 消息可能成功、事务可能回滚
}
```
正确做法：
- 事务只包住数据库写操作，保持短小；
- 跨服务一致性用 **本地消息表 / Outbox** 或事务消息；
- 远程调用失败要能补偿，不能假设「一定成功」。

### 2. 并发控制
| 方案 | 适用 | 注意 |
|---|---|---|
| 乐观锁（version/CAS） | 冲突少的更新 | 失败要重试，重试次数有限 |
| 悲观锁（`SELECT ... FOR UPDATE`） | 冲突高、强一致 | 锁范围要小，避免死锁 |
| 分布式锁 | 跨实例互斥 | 有租约与续期问题，不能替代数据库约束 |
| 唯一索引 | 幂等、防重 | 最可靠，冲突时捕获并处理 |

### 3. 幂等
写接口至少要做到「同一请求重复到达，结果一致」：
- 客户端生成 `idempotencyKey`，服务端唯一索引落库；
- 状态机只允许合法跃迁（待支付 → 已支付，不能反向）；
- 消息消费用「业务唯一键 + 去重表」；
- 更新用「设置目标状态」而不是「增量累加」，避免重复加库存。

## 五、存储访问：延迟与并发的集中点
### 1. 连接池
连接池不是越大越好：
```
pool_size ≈ CPU 核数 × 2 ~ 4（SSD 场景）
```
- 池太大 → 数据库线程上下文切换、锁竞争加剧；
- 池太小 → 请求排队，`connection timeout`；
- 连接池等待时间要单独监控，它和慢查询是两类问题。

### 2. 查询
- 先看执行计划，再看索引，最后才考虑缓存；
- 避免 N+1：列表页批量查关联数据；
- 深分页用游标（`WHERE id > ? ORDER BY id LIMIT ?`），不要 `LIMIT 100000, 20`；
- 大事务会持有 undo、锁、连接，尽量拆小；
- 读写分离要接受主从延迟，强一致读走主库。

### 3. 缓存
- 缓存命中率高才有意义，先测命中率再加缓存；
- 缓存穿透、击穿、雪崩的处理方式见缓存专题；
- **缓存不是数据源**，数据库才是最终事实。

## 六、响应：最后一公里
- 序列化：JSON 通用但体积大，内部 RPC 可用 Protobuf/Thrift；
- 压缩：gzip/br 省带宽但耗 CPU，小响应不值得压缩；
- 分页：返回 `hasMore`/`nextCursor`，不要返回总数导致全表 count；
- 状态码语义要正确：

| 状态码 | 含义 | 常见误用 |
|---|---|---|
| 200 | 成功 | 业务失败也返回 200 |
| 201 | 已创建 | 创建接口返回 200 |
| 204 | 无内容 | 返回空 JSON |
| 400 | 参数错误 | 用 500 表示参数错误 |
| 401/403 | 未认证/无权限 | 混用两者 |
| 409 | 冲突 | 重复创建返回 500 |
| 429 | 限流 | 限流返回 503 |
| 502/503/504 | 网关/不可用/超时 | 全部笼统报 500 |

- 错误响应不要带堆栈、SQL、内部 IP；对外用稳定错误码。

## 七、可观测性：怎么知道慢在哪
| 信号 | 关键内容 | 工具 |
|---|---|---|
| Trace | 每个 span 的耗时、状态、下游 | OpenTelemetry、Jaeger、SkyWalking |
| Metrics | QPS、错误率、p50/p95/p99、饱和度 | Prometheus、Grafana |
| Logs | 结构化、traceId、错误上下文 | ELK、Loki |
| Profile | CPU、内存、锁、GC | pprof、async-profiler、Arthas |

排查顺序：
1. 看入口 QPS 与错误率是否突变；
2. 看 p99 与下游 span，定位是应用、DB、缓存还是 RPC；
3. 看线程池/连接池队列、GC、CPU、锁等待；
4. 最后才看单条慢 SQL 或代码。

## 八、延迟预算：给每一段设上限
假设接口目标 p99 < 800ms：

| 环节 | 预算 |
|---|---|
| 网关 | 30ms |
| 应用排队 + 处理 | 100ms |
| 缓存 | 10ms |
| 数据库（2 次） | 80ms |
| 下游 RPC | 200ms |
| 序列化 + 网络 | 80ms |
| 余量 | 300ms |

原则：
- **外层超时 > 内层超时**，否则外层已经放弃，内层还在白干活；
- 超时不是「越大越稳」，超时越大，故障时堆积越多；
- 给下游传递 deadline，剩余时间不足时快速失败；
- 重试预算单独计算，避免「超时 × 重试次数」把故障放大。

## 九、常见故障对照表
| 现象 | 可能原因 | 首先检查 |
|---|---|---|
| 502 Bad Gateway | 上游崩溃、端口不通、协议错误 | 上游进程、健康检查、Nginx error log |
| 504 Gateway Timeout | 上游处理超时 | 网关 read timeout、应用 p99、慢 SQL |
| 499（Nginx） | 客户端主动断开 | 客户端超时、首屏过慢 |
| 429 Too Many Requests | 触发限流 | 限流阈值、突发流量、热点 key |
| 413 Payload Too Large | body 超限 | 网关/框架 body 限制 |
| Connection Reset | 服务重启、TIME_WAIT、内核参数 | 发布记录、`ss -s`、backlog |
| 线程池耗尽 | 下游变慢、同步阻塞 | 池队列长度、下游 RT |
| 连接池超时 | 慢查询、事务过长、池太小 | `SHOW PROCESSLIST`、池指标 |
| 死锁 | 加锁顺序不一致 | `SHOW ENGINE INNODB STATUS` |
| CPU 100% | 死循环、序列化、GC | 火焰图、GC 日志 |
| 内存持续上涨 | 泄漏、缓存无上限、大对象 | heap dump、缓存统计 |

## 十、优化顺序
1. **测量**：先用 trace/metrics 定位瓶颈，不猜；
2. **数据库**：索引、N+1、慢查询、事务范围；
3. **缓存**：热点数据、命中率、失效策略；
4. **异步化**：非核心链路走 MQ，缩短主链路；
5. **资源池**：线程池、连接池、队列容量；
6. **水平扩展**：无状态服务加实例，配合负载均衡；
7. **代码与算法**：最后才做微优化。

> 80% 的后端性能问题，来自「没索引的查询 + 同步远程调用 + 无上限的池/队列」。

## 十一、常见误区
1. ❌ 平均延迟正常就没事：用户感知的是 p99，平均值会掩盖长尾；
2. ❌ 超时设大一点更稳定：故障时只会堆积更多请求，恢复更慢；
3. ❌ 失败就重试：非幂等写重试会重复下单，重试还会放大故障；
4. ❌ 连接池/线程池越大越好：超过数据库与 CPU 承载能力后，只会更慢；
5. ❌ 加了缓存就一定快：命中率低、序列化开销、缓存穿透都会反噬；
6. ❌ HTTP/2 一定比 HTTP/1.1 快：单连接、小并发场景差异不大，弱网丢包时 TCP 仍会阻塞；
7. ❌ 无状态就不需要会话：登录态、幂等键、限流计数仍需要共享存储；
8. ❌ 监控只看 CPU：连接池、队列、GC、下游延迟才是更早的故障信号。

## 十二、总结
- 一次请求穿过接入、应用、存储、异步四层，每层都有独立的容量与失败模式；
- 稳定的后端 = **明确的超时预算 + 有界队列 + 幂等 + 可观测**；
- 优化顺序永远是「先测量，再动数据库，最后才加机器」；
- 把每次故障都沉淀成对照表与告警，系统才会越跑越稳。
