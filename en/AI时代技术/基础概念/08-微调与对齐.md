# Fine-tuning and alignment: SFT / LoRA / RLHF / DPO
> In one sentence: **pre-training makes the model "speak", SFT makes the model "will do things as required", preference alignment makes the model "speak satisfactorily"; LoRA solves the problem of "affordability to change", and DPO/RLHF solves the problem of "correct change".**
> Positioning: Fine-tuning changes the behavior and style of the **model**, and is not a reliable means of knowledge injection - dynamic facts are still given priority to RAG.

## One and three-stage training panorama
```
海量无标注语料                指令-回答数据               偏好对比数据
      │                          │                          │
  预训练 Pretrain  ──────▶  SFT 监督微调  ──────▶  偏好对齐（RLHF / DPO / GRPO）
  next-token 预测            学会遵循指令格式          学会「哪种回答更好」
      │                          │                          │
   基座模型 Base            指令模型 Instruct          对齐模型 Chat / Reasoning
```
| Stage | Data form | Target | Typical cost |
|---|---|---|---|
| Pre-training | Trillion-level Token Plain text | Learn language and world knowledge | Extremely high, usually not done |
| SFT | Ten thousand to one million level `(指令, 回答)` | Learn the task format, tone, and refusal method | Medium |
| Preference alignment | Ten thousand to one hundred thousand level `(问题, 优选, 劣选)` | Improve usefulness, harmlessness, and reasoning quality | Medium to high |
| Continue pre-training CPT | Domain plain text (legal/medical/code) | Inject domain distribution and terminology | High, easy to forget |

> Key cognition: **knowledge enters the parameters in the pre-training stage, and SFT/alignment mainly shapes the behavior**. If you want the model to "know the policy released yesterday", fine-tuning is slow and unreliable, so RAG is the right solution.

## 2. SFT: Supervision and fine-tuning
### 1. Principle
Standard next-token prediction, but **only computes loss** in the answer part:
```
[system] 你是客服助手 [user] 怎么退货？ [assistant] 请在订单页点击……
└──────────── 输入，mask 掉不算 loss ────────────┘└──── 只对这部分算 loss ────┘
```
 If loss is calculated together with prompt, the model will learn to "repeat the user's problem", and the instruction following will become worse.

### 2. Data is more important than algorithm
1. **Quality > Quantity**: Thousands of clean and consistent samples are often better than hundreds of thousands of noisy data;
2. **Diversity**: Task type, length, difficulty, and refusal scenarios must be covered, otherwise the model will collapse on tasks it has never seen before;
3. **Unified format**: The chat template (role tag, BOS/EOS) of the target model must be strictly used. If training and inference are inconsistent, "model will not stop" or "output with role prefix" will appear;
4. **Deduplication and pollution check**: The training set is mixed into the evaluation set, causing falsely high scores. Use n-gram overlap detection to clean;
5. **Be careful with distilled data**: Data generated with a strong model is valid, but will inherit its errors and style, and may violate the terms of service.

### 3. FAQ
- **Catastrophic forgetfulness**: Only trained on a single task, general ability is reduced. Countermeasures: Mix in general instruction data, reduce the learning rate, and train for fewer rounds;
- **Overfitting**: The loss continues to decrease but the evaluation becomes worse. Usually 1~3 epoch is enough, stop early;
- **length offset**: SFT data answers are generally very long, and the model will become verbose;
- **Learn to refuse to answer excessively**: The proportion of safe samples is too high, and normal questions are also rejected.

## 3. LoRA: Make fine-tuning cheap
### 1. Core hypothesis
The change in weight during fine-tuning **ΔW is the low-rank**. There is no need to update the entire matrix, just learn a low-rank decomposition:
```
W' = W + ΔW = W + (α / r) · B · A
W ∈ R^{d_out × d_in}   冻结
A ∈ R^{r × d_in}       随机初始化
B ∈ R^{d_out × r}      零初始化（保证训练起点 ΔW=0）
```
- `r` (rank) is usually 8 / 16 / 32 / 64. The larger the capacity, the stronger the capacity and the easier it is to overfit;
- `α` (lora_alpha) is the scaling coefficient, commonly used `α = 2r`;
The amount of trainable parameters for - is reduced from `d_in × d_out` to `r × (d_in + d_out)`, and the 7B model usually only trains 0.1%~1%;
After - is trained, `BA` can be merged back to the original weight, and **will infer** with zero extra delay; it can also be used without merging, and multiple sets of LoRA can be dynamically mounted for multi-tenancy.

### 2. Which layers to hang?
Experience order: `q_proj, k_proj, v_proj, o_proj` must be installed, if the effect is not enough, add `gate_proj, up_proj, down_proj` (MLP layer). Fully installed + higher rank has the best effect, but the risk of memory and over-fitting increases.

### 3. QLoRA
Quantify the **base model to 4bit** based on LoRA and retrain:
- **NF4 (NormalFloat 4bit)**: quantized according to normal distribution quantile, uniform ratio int4 is more suitable for weight distribution;
- **Dual quantization**: Quantize the quantization constant again to further save video memory;
- **Paged Optimizer**: Swap the optimizer state to the CPU when the memory peaks to avoid OOM;
The - LoRA adapter is still trained with bf16, and gradient accuracy is not affected.

Effect: A single 24GB graphics card can fine-tune 7B~13B models, which is the de facto standard for individuals and small teams.

### 4. Other PEFT solutions
| Method | Idea | Features |
|---|---|---|
| **LoRA** | Low-rank bypass matrix | The best ecology, can be merged, and can be switched between multiple sets |
| **QLoRA** | 4bit base + LoRA | Saves the most memory, slightly slower in training |
| **Adapter** | Insert small bottleneck layer | Inference has extra delay, gradually replaced by LoRA |
| **Prefix / P-Tuning** | Learn a virtual token | The number of parameters is extremely small, but it occupies context and the effect is unstable |
| **Full parameter fine-tuning** | Update all parameters | has the highest upper limit and the highest cost, usually only used when there is sufficient data |

### 5. Key hyperparameters
- learning rate: LoRA commonly used `1e-4 ~ 2e-4`, full parameter `1e-5 ~ 2e-5` (one order of magnitude difference);
- epoch: 1~3, the instruction data is repeated for multiple rounds with diminishing returns;
- batch size: Use gradient accumulation to gather the equivalent batch (such as 32~128);
- Sequence length: Set according to data distribution. If it is too long, it wastes video memory. If it is too short, the sample will be truncated;
- learning rate scheduling: cosine + warmup is the safe default;
- video memory optimization: gradient checkpointing, FlashAttention, DeepSpeed ZeRO / FSDP.

## 4. Preference alignment: RLHF
### 1. Three-stage process
1. **SFT**: First get the initial strategy that can answer normally;
2. **Training reward model RM**: Sample multiple answers to the same question, manually mark the pros and cons, and use the Bradley-Terry model to fit the probability of "A is better than B";
3. **PPO Reinforcement learning**: Policy model generates answers → RM scoring → Update the policy with PPO, and add **KL penalty** constraints not to deviate too far from the SFT model.

### 2. Why is it difficult?
- needs to run **4 models** at the same time: strategy, reference model, reward model, value model (critic), and the video memory is several times that of SFT;
- PPO is sensitive to super parameters, unstable in training, and prone to collapse;
- **Reward Hacking**: The model learns to please and reward the model (piling up clichés, overconfidence, lengthening) rather than actually getting better;
- Artificial preference data is expensive and subject to annotator bias.

## 5. DPO: Bypassing the reward model
### 1. Core idea
Mathematically it can be proved that for the RLHF optimal strategy with KL constraints, there is an implicit reward **corresponding to the log probability ratio of the strategy and the reference model. Therefore, you can skip "training RM + PPO" and directly use preference pairs for classification training:
```
L_DPO = -log σ( β·[log π(y_w|x) - log π_ref(y_w|x)]
                - β·[log π(y_l|x) - log π_ref(y_l|x)] )
```
- `y_w` is the preferred answer, `y_l` is the inferior answer;
- `π_ref` is a frozen reference model (usually the SFT model), **DPO still requires it**;
- `β` controls the degree of deviation allowed from the reference model, commonly used is 0.1~0.5, the smaller the value, the more conservative it is.

### 2. Trade-offs compared to RLHF
| Dimensions | RLHF (PPO) | DPO |
|---|---|---|
| requires reward model | Yes | No |
| requires critic | yes | no |
| Training stability | Poor, difficult to adjust parameters | Good, close to ordinary supervised training |
| Video Memory | High (4 models) | Medium (Strategy + Reference) |
| Upper limit | Higher, can be explored online | Limited by offline preference data |
| Engineering complexity | High | Low |

> DPO It is not a "free lunch": it can only use **'s existing preference data**, and lacks online exploration; scenarios outside the data distribution are prone to over-optimization and "bad habits that are not included in the preference data" appear.

### 3. Subsequent variants
- **ORPO**: Combine SFT and preference optimization in one step, no reference model is needed, and video memory is saved;
- **KTO**: Only "good/bad" binary feedback is required, no pairwise comparison is required;
- **SimPO**: Use the length-normalized average log probability as implicit reward and remove the reference model;
- **GRPO**: Sampling a group of answers to the same question, with the advantage of normalization within the group, **does not require critic**, and combined with verifiable rewards (RLVR), it has outstanding effects on mathematics and coding tasks, and is one of the mainstream solutions for inference model training.

### 4. RLVR: Verifiable Rewards
Mathematics questions have standard answers, and codes have unit tests. For such tasks, the **rule can be used to determine** instead of manual preference:
- Advantages: Objective rewards, unlimited sampling, not easy to be reward hacked;
- Disadvantages: It is only applicable to fields where the results can be verified, and open writing and customer service techniques cannot be directly applied;
- The training signal is sparse (all right or all wrong), and it needs to rely on group relative comparison (GRPO) to provide gradients.

## 6. Fine-tuning or RAG: how to choose
| Requirement | Preferred solution | Reason |
|---|---|---|
| Injects the latest policies and private documents | **RAG** | can be updated in real time, traceable, and does not require retraining |
| Fixed output format (JSON, work order language) | **SFT / LoRA** | The format is behavior, and examples are most effective |
| Unify tone and brand style | **SFT / LoRA** | A small number of high-quality samples are enough |
| Improve domain-specific reasoning | **Domain SFT + RLVR** | Requires behavioral and strategic changes |
| model always answers the wrong simple rules | Prompt + Few-shot | Eliminate prompt word problems first |
| Knowledge changes frequently | RAG + Rebuild index regularly | Fine-tuning update cycle cannot keep up |

Suggested decision-making sequence: **Prompt/Few-shot → RAG → LoRA → Full parameter fine-tuning → Continue to pre-train**. With each lower level, the cost and maintenance difficulty increase significantly.

> RAG and fine-tuning are complementary rather than substitutes: a common combination is "fine-tuning teaches format and words + RAG provides facts".

## 7. Evaluation and launch
1. **set aside**: training/verification/testing are strictly separated to prevent data leakage;
2. **regression evaluation**: After fine-tuning, run through the basic abilities (command following, refusal to answer, safety, long context) to prevent "specialization from becoming strong and general from becoming stupid". For specific evaluation methods, see Harness’ notes;
3. **A/B Comparison with**: The same prompt is used to test the old and new models respectively, manual or referee model blind evaluation;
4. **version can be traced back to**: record the base version, LoRA rank, data version, super parameters, chat template, otherwise it cannot be reproduced;
5. **grayscale online**: small traffic first, monitor hallucination rate, rejection rate, average length, cost;
6. **rollback plan**: Multiple sets of LoRA can coexist. If there is a problem, you can directly switch back to the old adapter, which is much safer than full parameter fine-tuning.

## 8. Common misunderstandings
1. ❌ Fine-tuning can reliably inject new knowledge: the model is easier to "learn to compile with confidence", and fact updates should still go RAG;
2. ❌ The more data, the better: low-quality, repetitive, and single-style data will degrade the model, so quality and diversity are prioritized;
3. ❌ LoRA must not lose its effect: when the rank is too small, only attention is attached, and the data is insufficient, it is obviously weaker than the full parameter;
4. ❌ LoRA must be merged after training: multiple sets can be dynamically loaded without merging, suitable for multi-tenants; merging is just to save trouble in reasoning;
5. ❌ DPO does not require a reference model: `π_ref` is still required to calculate logprob, but RM and critic are omitted;
6. ❌ RLHF is definitely better than DPO: depending on the data and scenarios, DPO has better reproducibility in most teams;
7. ❌ A low loss after SFT indicates a good model: loss only measures the fitting of the training distribution, and does not represent instruction compliance and safety;
8. ❌ Chat template can be changed at will: Inconsistency between training and inference templates is one of the most common reasons for "model becoming stupid";
9. ❌ Fine-tuning can replace prompt word engineering: many problems can be solved with clear instructions + Few-shot, fine-tuning is the last resort.
