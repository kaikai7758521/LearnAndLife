# AI Agent core terminology inventory notes (principle + layering + list of common agents)
> core hierarchical relationship: **Tool (atomic capability) → Skill (encapsulation process) → Harness (running orchestration base) → Agent (complete intelligent body)**
> classic formula: **Agent = LLM brain + Harness operating framework (memory/loop/safety/tool scheduling)**

## 1. Core terms and principle details
### 1. Agent
**defines**: an autonomous system that uses a large model as the core of reasoning, has perception, planning, tool invocation, state memory, autonomous iteration closed loop, and continues to act toward the goal. It is different from ordinary dialogue models of one question and one answer.
**core loop: ReAct (Reason + Act, reasoning-action loop)**
1. Observe: Read user goals, historical memory, tool return results, and environmental information
2. Reasoning (Reason): LLM determines the current status, thinks about the next action, selects tools, and generates calling parameters
3. Action (Act): Leave it to Harness to execute tool calls, code execution, and API requests
4. Feedback (Observe again): Get the execution results and return to reasoning until the goal is completed/failed to terminate
**key components**: LLM inference engine, memory system, planner, tool set, safety guardrail (Guardrail), state machine.
The difference between **and ordinary Chat model**: Chat passively responds to a single round of requests; Agent is goal-driven, multi-step autonomous execution, and can decide whether to continue to call the tool.

### 2. Tool
**defines**: an atomic, minimum-granularity callable function/interface, which is the "hands and feet" of the Agent and is only responsible for executing a single, deterministic action. **itself does not have business logic and planning capabilities**.
**Principle**: Use JSON Schema to describe input parameters and output parameters, and LLM outputs function call instructions that comply with the specifications, which are scheduled and executed by Harness.
**Common Tool examples**: search engine, calculator, database query, file reading and writing, code executor, email sending, API request, browser access.
**Features**: stateless, single responsibility; can be reused by multiple Skills and multiple Agents; after failure, the upper layer will retry or adjust the strategy.

### 3. Skill
**defines**: The encapsulated **reusable task unit** is oriented towards business tasks. It is composed of a set of Tool + fixed process + constraint prompt + verification rules to solve the problem of "repeated writing of complex prompts and unstable process".
**principle**: Package a standardized SOP: pre-verification → call multiple tools in sequence → result verification → exception branch processing → output formatting.
> Simple distinction: Tool = an API; Skill = "use multiple tools to complete a complete business thing"
Example:
- [Financial Report Interpretation Skill]: Call search → Pull financial report PDF → RAG search → Extract indicators → Generate comparison table
- [Work Order Processing Skill]: Query customer information → Generate reply → Send email → Write to the work order system
**Features**: business-friendly, can be updated in grayscale, and can be independently tested; Skills can contain sub-Skills; it is the most commonly used abstraction layer for enterprise landing agents.

### 4. Harness (Agent Harness, agent running base/scaffolding)
**defines**: a complete runtime framework wrapped outside of LLM. **does not belong to the model itself**. It is responsible for driving the entire ReAct cycle and is the "operating system" of the Agent.
A saying in the > industry: If you are not the model, you are the harness. Everything that is not the model is the harness.
**Harness core module (principle details)**
1. loop driver: repeatedly execute LLM call → Tool execution → result backfill
2. state and memory management layer: short-term conversation context, long-term vector memory, task progress snapshot
3. tool scheduling layer: Schema verification, sandbox isolation, permission authentication, concurrency, timeout, retry
4. Guardrail: dangerous operation interception, manual approval node, output filtering, whitelist
5. observable layer: log, trace, time consumption, call record, cost statistics
6. orchestration and delegation: supports splitting sub-agents and task distribution
**Typical Harness**: LangChain, LlamaIndex, Microsoft Agent Framework, Claude Code Harness, Google Antigravity

### 5. LSP (Language Server Protocol, language server protocol)
> Note: It appears frequently in the Agent (especially Coding Agent) ecosystem and is the core standard protocol for the interaction between Coding Agent and code editor. Coding Agents such as Devin, Aider, and Claude Code rely heavily on LSP.
**defines**: The LSP is a standardized JSON-RPC communication protocol between the **editor ↔ language server**, decoupling the editor UI and language analysis capabilities.
**core principle**
1. separates two layers: front-end (editor/Agent client) and back-end (Language Server, language service process);
2. communication is based on JSON-RPC and uses stdio, socket and other channels;
The 3. language server is an independent process, responsible for understanding code AST, symbols, types, references, and diagnostic information;
The 4. client (can be VSCode or encoding agent) sends a request to the server, and the server returns code semantic information.

Capabilities provided by **LSP (encoding agent is very dependent on)**
- symbol search: go-to-definition jump to definition, find-references find all references
- code diagnosis: syntax error, lint alarm
- completion, hover prompt, rename (rename)
- document symbol list, workspace range search symbol

The value of **in the Agent scenario is**
Ordinary Agents can only read original text files; after accessing LSP, Agents no longer just "read strings", but understand the semantic structure of the code and the dependencies between variables, functions, and classes, greatly reducing the illusion of changing code, correcting wrong references, and not understanding the project structure.
> distinction: LSP itself is not an Agent or a Tool; it is a set of **semantic query interface standards**. The encoding agent usually encapsulates an LSP Client as an internal Tool/Skill to read project semantics.
Example: When Aider and Devin analyze a large code base, they will start the LSP Server (gopls, tsserver, copyright, etc.) of the corresponding language and call the LSP interface to obtain symbol information instead of simple full-text search.

### Matching high frequency noun supplement
#### ReAct
The reasoning-action paradigm is the basic cycle of most current agents. It interweaves thinking reasoning and tool invocation to solve the pain points of LLM illusion and inability to obtain real-time information.

#### RAG (retrieval enhancement generation)
It is often used as an internal capability of a Skill to vectorize private documents and provide an external knowledge base for the Agent; RAG itself is not an Agent, but it is almost a standard skill for industry agents.

#### Memory (memory)
Three levels of classic division:
- short-term memory: context window of this round of dialogue
- episodic memory: historical task records, past interactions (vector library)
- Procedural memory: Skill, remember the process of "how to do this"

#### Planner (Planner)
There are two types of planning modules in Agent:
1. large model native planning: LLM outputs the plan by itself (suitable for simple tasks, unstable)
2. hierarchical planning: first split into a sub-task list, and then the sub-tasks are handed over to the sub-Agent/Skill for execution (suitable for long tasks)

#### Sub-Agent / Multi-Agent (multi-agent)
The main agent breaks down complex tasks and delegates them to specialized sub-agents (encoding agent, retrieval agent, review agent) for division of labor and collaboration; Harness is responsible for routing, result merging, and conflict coordination.

#### Guardrail (safety guardrail)
Harness has a built-in verification layer that intercepts high-risk actions before calling tools and after model output: deleting files, high-risk shells, leaking sensitive data, and unauthorized access.

## 2. Common Agent classifications and characteristics
> is divided into two perspectives: classic AI theory classification + current engineering implementation classification in the large model era

### [5 categories of classic AI theory (textbook classification)]
1. **Simple Reflex Agent**
Features: Only respond based on current input + fixed rules, **has no memory, no history perception,**, and no planning.
Limitations: It can only handle deterministic and stateless scenarios. Examples: keyword automatic reply, simple rule robot.

2. **Model-based Reflex Agent**
Features: Maintain an environment state model and remember the last round of state; can handle partial observations and non-immediate feedback scenarios.
Example: Simple monitoring and alarm robot.

3. **Goal-based Agent**
Features: With the goal as the core, it actively searches for multiple action paths, predicts the results, selects a path that can get closer to the goal, and has basic planning.
Suitable for: path planning, task scheduling.

4. **Utility-based Agent**
Features: It not only looks at "whether the goal is achieved", but also introduces a utility function to evaluate the quality of the plan; supports multi-objective conflict trade-offs (cost, speed, risk).
Suitable for: resource allocation, decision-making recommendation, investment assistance.

5. **Learning Agent Learning Agent**
Features: Built-in learning module to improve strategies from historical interactions; can automatically optimize skills and adjust planning strategies.
Limitations: It is difficult to implement. Most of the current LLM Agents are "few-shot learning" rather than continuous online learning.

### [Project Implementation: Mainstream Agent in the LLM Era]
1. **Conversational Agent Conversational Agent**
Representative: Universal dialogue assistant, customer service agent
Features: Mainly interactive, with the goal of Q&A and guidance; light tool capabilities; weak autonomy, relying on the user's continuous guidance; memory mainly focuses on conversation history.

2. **Tool Calling Agent**
Representative: LangChain Basic ReAct Agent
Features: Basic ReAct loop, LLM independently selects tools; suitable for query, calculation, and simple data processing; **does not have the ability to plan long tasks. If the task is too long, it is easy to go off track and the loop diverges**.

3. **Planning Agent Planner Agent**
Representatives: AutoGPT, BabyAGI
Features: First output the complete task plan, split it into a list of sub-tasks, execute them one by one, and review the progress; suitable for long processes and complex goals; Pain points: It is easy to over-plan, hallucinations lead to unfeasible plans, and high resource consumption.

4. **Act-Plan Agent (Action-Planning Agent) [Currently the strongest engineering capability]**
Representatives: Plan-and-Solve, ActPlan, partially improved version of BabyAGI, and also the internal loop paradigm of many coding agents.
Features: **dual branch alternation: planning phase (Plan) + execution phase (Act), which is obviously different from the native ReAct**
- Plan stage: Based on the current full status, update the global task plan, adjust sub-task priorities, and identify failure/blocking points; the plan will be dynamically modified, not hard-coded at once;
- Act stage: Only select the next subtask** in the current plan for **to execute (calling tools, reading and writing environments);
After receiving feedback during - execution, go back to the planning stage to re-evaluate and revise the plan, instead of just thinking about a single step at a time.
Comparison between > and ordinary ReAct: ReAct is "thinking step by step" and prefers local greedy decision-making; Act-Plan explicitly maintains an independent plan and has a stronger global perspective.
Advantages: The stability of long tasks is better, and it is not easy to go around in infinite circles; it is convenient for humans to view, intervene, and modify plans; it is suitable for multi-step projects, large-scale code modifications, and complex surveys.
Shortcomings: Each round of planning consumes additional tokens, which is more costly; the plan itself will still produce hallucinations, and if the plan is wrong, all subsequent executions will go off track.

5. **Coding Agent Coding Agent**
Representatives: Claude Code, Aider, Devin
Features: Strong file system, shell, and git tool set; Harness specializes in sandboxing, code execution, and diff submission; comes with code review and test execution closed loop; integrates a large number of LSP Clients to obtain code semantic symbols; and has extremely high security requirements for the Harness sandbox.

6. **Multi-Agent System**
Representatives: AutoGen, CrewAI
Features: Division of roles (product, development, testing, review); Agents talk to each other, delegate tasks, and verify results; suitable for complex projects, document collaboration, and joint data analysis; difficulties are communication protocols, conflict handling, and cost inflation.

7. **Enterprise Digital Employee Agent (Business Skilled Agent)**
Representatives: Internal RPA+LLM Fusion Agent, Work Order Agent, Financial Reconciliation Agent
Features: Highly bound to business SOP, extensive use of packaged Skills; tools are internal corporate systems (OA, ERP, database); Harness focuses on permission approval, auditing, and traceability; autonomy is controllable, and many nodes require manual confirmation.

8. **Autonomous Agent**
Representative: Early AutoGPT projects
Features: Minimum manual intervention, continuous autonomous circulation after setting goals; highest risk, prone to infinite loops and unauthorized operations; now industrial implementation generally adds manual gates and maximum number of rounds limits.

## 3. Level comparison
| Level | Noun | Positioning in one sentence |
|---|---|---|
| Atomic Power | Tool | Callable function to do a small thing |
| Business unit | Skill | Multiple Tool+ processes to complete a standardized business task |
| Semantic interface standard | LSP | Communication protocol that provides code AST/symbol semantic query for coding agents |
| Running base | Harness | Loop, memory, sandbox, scheduling, security, let LLM move |
| Complete entity | Agent | LLM + Harness + Skill + Tool + Target closed loop |

## 4. Common misunderstandings
1. has Tool call ≠ Agent: many are just prompt workflows with function calls, without autonomous loops and status tracking, and do not belong to Agent;
2. Skill is not a Prompt: Prompt is a one-time instruction, and Skill is a capability package that can be version managed, reusable, and has exception branches;
3. Harness is not the name of the framework SDK: LangChain is the SDK, and the entire set of runtimes you write on LangChain is your Harness;
The more autonomous the 4. Agent is, the better: industrial implementation gives priority to controllability, and high autonomy is generally only used in an isolated sandbox environment;
5. LSP ≠ Code completion: LSP is a protocol, and completion is only a subset of its capabilities; the core purpose of Agent using LSP is to understand code dependencies;
6. Act-Plan ≠ Planner Agent: Classic Planner generates a full plan at once; Act-Plan is **planning-execution alternate iteration, and the plan dynamically updates**.
