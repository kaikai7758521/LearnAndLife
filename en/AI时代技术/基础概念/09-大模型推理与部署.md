# Large model inference and deployment
> In one sentence: **inference is divided into two stages: prefill and decode: prefill consumes computing power, and decode consumes video memory bandwidth; the core of deployment is scheduling and trade-offs between TTFT, TPOT, throughput and video memory.**
> Positioning: Talk about serving issues (KV Cache, batch processing, quantification, parallelism, indicators) after the model is launched. For the basic concepts of Token billing and context window, see `04-Token是怎么被消耗的.md`.

## 1. What is the difference between inference and training?
| Dimension | Training | Inference |
|---|---|---|
| calculation | forward + reverse + optimizer | only does forward |
| Memory head | Weight, gradient, optimizer status, activation | Weight, KV Cache, small amount of activation |
| Bottleneck | Computing power, communication | Video memory bandwidth, video memory capacity, scheduling |
| Batch processing | Large batch improves throughput | is subject to delay SLO constraints and cannot add unlimited batches |
| Accuracy | FP16/BF16/FP8 training | Can be quantified to INT8/INT4, the accuracy needs to be evaluated |

> training pursues "how long it takes to complete the training", and reasoning pursues "how fast the response is, how much concurrency, and how much each token costs".

## 2. Prefill and Decode
### 1. Two stages
```
Prompt: "请解释一下 KV Cache"
Prefill：一次性并行处理全部输入 Token，生成 KV Cache
Decode：基于 KV Cache 自回归逐个生成输出 Token
```
| Stage | Computational characteristics | Bottleneck | Impact indicator |
|---|---|---|---|
| Prefill | Matrix multiplication is main, can be parallelized | GPU computing power | TTFT (first token delay) |
| Decode | Only generate 1 Token per step | Memory bandwidth | TPOT/ITL (per token delay) |

### 2. Why decode is a bandwidth bottleneck
To generate each Token, read all the model weights **and**, and then pay attention to the KV Cache:
```
7B 模型 FP16 权重约 14GB
显存带宽 1TB/s → 理论约 70 token/s（单请求、无批处理）
```
This is why:
- ’s single request decode is difficult to fully satisfy the GPU computing power;
- **Increasing batch** can dilute the weight reading cost and improve throughput, but it will increase queuing and video memory pressure;
- quantization weight can directly improve decoding speed (less reads).

### 3. Computing power estimation
```
Prefill FLOPs ≈ 2 × 参数量 × 输入 Token 数
Decode  FLOPs ≈ 2 × 参数量 × 输出 Token 数
```
 actually also counts the attention part, and the proportion of attention increases significantly when the context is long.

## 3. KV Cache: the core of inference memory
### 1. Why is it needed
When generating autoregressively, the Key/Value of the previous Token can be reused; otherwise, the entire history must be recalculated every time a Token is generated, and the complexity will explode.

### 2. Video memory formula
```
KV bytes = 2（K 和 V）
         × 层数
         × KV 头数
         × head_dim
         × 序列长度
         × batch
         × 每元素字节数
```
 takes Llama-2 7B (32 layers, 32 heads, head_dim 128, FP16) as an example:
```
每 Token KV = 2 × 32 × 32 × 128 × 2B = 0.5 MiB
4K 上下文 ≈ 2 GiB / 条
```
GQA (Group Query Attention) reduces the number of KV heads from 32 to 8, and the KV Cache is directly reduced to 1/4; this is the reason why GQA is commonly used in long context models.

### 3. Optimization means
| means | principle | effect |
|---|---|---|
| GQA / MQA | Multiple Query heads share the KV head | GQA usually drops to 1/4 ~ 1/8, MQA can reach 1/32 |
| KV quantization | KV save into FP8/INT8 | The video memory is halved, the accuracy is slightly reduced |
| PagedAttention | KV is managed by blocks, similar to virtual memory paging | Reduces fragmentation and supports prefix sharing |
| Prefix Caching | Same system prompt/document reuse KV | Reduce duplication prefill |
| Preempt/swap out | Switch to CPU/recalculate when video memory is insufficient | Maintain throughput, sacrifice latency |

PagedAttention (the core of vLLM) cuts KV into fixed-size blocks and uses block table to map logical locations to physical blocks:
- does not need to pre-allocate the maximum length of contiguous video memory for each request;
- memory waste is reduced from "reserved according to the maximum length" to "allocated according to actual blocks";
- Requests with the same prefix can share blocks (Copy-on-Write).

## 4. Batch processing and scheduling
### 1. Static batch processing vs continuous batch processing
| Way | Behavior | Problem |
|---|---|---|
| static batch | Put together a batch and run together, waiting for the slowest one to finish | Short requests are held up by long requests, and the GPU is idling |
| Continuous Batching | The batch is reorganized at each step, completed requests are exited immediately, and new requests are added immediately | The implementation is complex, but the throughput and latency are better |

Continuous batch processing (iteration-level scheduling) is standard for vLLM, TGI, and TensorRT-LLM.

### 2. Chunked Prefill
Long prompt prefills will occupy the GPU, causing requests being decoded to stall. Cut prefill into small pieces and interleave execution with decode:
- reduces TPOT jitter;
The cost of - is a slight increase in TTFT for a single long request;
- is suitable for long document/RAG scenarios.

### 3. Interference between Prefill and Decode
- Prefill is a computing power type, and Decode is a bandwidth type. Mixing them together will drag each other down;
The - advanced solution splits prefill and decode into different GPU pools (Disaggregated Prefill/Decode), and expands and shrinks them respectively;
- simple solution uses chunked prefill + scheduling weight.

### 4. Scheduling strategy
- By priority: paying users/core interfaces first;
- Budget based on remaining token: avoid over-long requests from starving other requests;
- Timeout and cancellation: KV must be released in time when the client disconnects;
- Fairness: Multi-tenancy must limit single-tenant concurrency and token quotas.

## 5. Quantification: Trade precision for memory and bandwidth
| Type | Description | Applicable |
|---|---|---|
| Weight-only INT8 | Only quantizes the weight, still activated FP16 | Memory is tight, decode is the main one |
| Weight-only INT4 (GPTQ/AWQ) | 4bit weight, calibration data required | Single card deployment large model |
| W8A8 | has both weight and activation INT8 | has quantization calibration and pursues throughput |
| FP8 | H100/L40S and other support, small accuracy loss | New card first choice |
| KV Cache quantization | KV memory FP8/INT8 | Long context, high concurrency |

Note:
- **decode is a bandwidth bottleneck, and the quantization weight usually directly accelerates**; prefill is a computing power bottleneck, and INT4 dequantization may offset the benefits;
- The impact of quantification on mathematics, code, and long-chain reasoning must be evaluated separately, and you cannot just look at the general benchmark;
- calibration data must cover real business distribution;
- still needs to leave video memory for KV Cache and activation after quantization.

## 6. Parallelism and acceleration
### 1. Parallel mode
| method | segmentation object | communication | scene |
|---|---|---|---|
| Data parallel DP | Different requests are assigned to different copies | None (inference) | Expansion throughput |
| Tensor parallel TP | Single layer weight switching to multiple cards | Each layer AllReduce, NVLink Best | Single machine multiple cards |
| Pipeline parallel PP | Split to multiple cards by layer | Activation transfer | Cross-machine large model |
| Expert Parallel EP | MoE Expert Sharding | All-to-All | MoE Model |

> The more TPs for a single request, the faster it is not: communication overhead will eat up the benefits; usually, priority is given to using TPs to plug into single-machine NVLink, and then cross-machine consideration is considered.

### 2. Speculative Decoding
```
小模型/草稿模型先猜 K 个 Token
  → 大模型一次前向并行验证
  → 接受前缀，拒绝后重新采样
```
- The benefits are obvious when small batches and decode bandwidth are limited (commonly 1.5~2x);
- When the batch is large, the large model itself is close to the computing power bottleneck, and speculation may slow down;
- acceptance rate depends on draft model and target task; draft, Medusa long can also be retrieved with n-gram/.

### 3. Other means
- FlashAttention / PagedAttention / fusion operator: reduce memory reading and writing;
- CUDA Graphs: Reduce the startup overhead of small operators;
- TensorRT-LLM: compiled and optimized for NVIDIA;
- prefix cache: system prompts, RAG documents, few-shot sample reuse;
- Multi-LoRA: Shared base, switching adapters on request, suitable for multi-tenant customization.

## 7. Video memory budget: Calculate it first before going online
```
总显存 = 权重
       + KV Cache
       + 激活/临时 workspace
       + 框架开销/碎片
       + 安全余量（10%~20%）
```
 example:

| Model | Weight FP16 | Weight INT4 | 4K KV (indicative) | Single card 24GB feasibility |
|---|---|---|---|---|
| 7B MHA | ~14GB | ~4GB | ~2GB/strip | FP16 can run, with limited concurrency |
| 7B GQA (8 KV head) | ~14GB | ~4GB | ~0.5GB/strip | Can run, better concurrency |
| 13B MHA | ~26GB | ~7GB | ~3GB/strip | requires 2×24GB or INT4 |
| 70B GQA (8 KV head) | ~140GB | ~35GB | ~1.3GB/strip | requires multiple cards; INT4 also requires ≥48GB single card |

The weight of > is only the lower limit. The long context and high concurrency of **will turn KV Cache into the main contradiction**. Before going online, the peak value must be calculated based on "maximum context × maximum concurrency".

## 8. Indicators: Don’t just look at tokens/s
| Indicator | Meaning | Focus |
|---|---|---|
| TTFT | Time to request the first Token | Interactive experience, affected by prefill/queuing |
| TPOT / ITL | The interval between each output token | The smoothness of streaming output |
| E2E Latency | End-to-end completion time | Affected by output length |
| Throughput | Total number of tokens per second | Cost and capacity |
| Goodput | Effective throughput that meets SLO | More meaningful than naked throughput |
| Queue Time | Queue waiting time | Capacity expansion signal |
| GPU utilization | SM/memory bandwidth utilization | High may not necessarily be efficient |
| KV Cache usage | Used blocks/total blocks | is close to 100% and will preempt/reject |
| Number of preemptions/recalculations | Triggered by insufficient video memory | Source of delay jitter |

The optimization goal of > is not "GPU 100%", but "maximizing goodput within SLO".

## 9. Deployment architecture
```
Client → API Gateway（鉴权/限流/计费）
       → Router（按模型/租户/负载路由）
       → Serving 实例（vLLM/TensorRT-LLM/SGLang）
       → GPU 池
       ↑
Model Registry / 配置中心 / 监控告警 / 自动扩缩容
```
 key design:
1. **OpenAI is compatible with API**: `/v1/chat/completions`, SSE streaming return, reducing client migration costs;
2. **routing**: diversion by model, LoRA, context length, tenant quota;
3. **Automatic expansion and contraction**: Look at queue length, TTFT, KV usage, don’t just look at CPU/GPU;
4. **Cold start**: Model loading may take tens of seconds to several minutes, and the warm pool is retained;
5. **Grayscale**: The new model/new quantified version is scaled up in proportion, comparing TTFT, error rate, and manual scoring;
6. **Downgrade**: shorten the maximum output when overloaded, turn off non-core functions, and switch to a small model;
7. **Security**: Authentication, quota, Prompt injection protection, output audit, log desensitization;
8. **Multi-tenant**: concurrency isolation, token quota, LoRA isolation, priority queue.

## 10. Inference framework selection
| Frame | Features | Fits |
|---|---|---|
| **vLLM** | PagedAttention, continuous batch processing, OpenAI API, multi-LoRA | Universal GPU service, active community |
| **TensorRT-LLM** | NVIDIA Deep optimization, compiled deployment | Pursuing ultimate performance, fixed model |
| **SGLang** | RadixAttention prefix cache, structured output | Multi-round/Agent/RAG scenario |
| **TGI** | Hugging Face Ecology, simple deployment | HF model quickly goes online |
| **llama.cpp / Ollama** | CPU/Metal/Edge, GGUF quantization | Local, end-side, low concurrency |
| **Triton Inference Server** | Multi-frame unified serving | Enterprise multi-model platform |

When selecting > , first look at "model support, quantification format, concurrency capabilities, and operation and maintenance costs", and then look at benchmarks; paper throughput does not equal business goodput.

## 11. Common misunderstandings
1. ❌ It can run as long as the video memory is enough to put the weight: long context/high concurrency KV Cache is often the bottleneck;
2. ❌ The bigger the batch, the better: throughput increases but TTFT/TPOT becomes worse, so you need to find a balance based on SLO;
3. ❌ Quantization must be faster: decode benefits significantly, and prefill may be slowed down by dequantization;
4. ❌ Only look at tokens/s: without looking at TTFT, TPOT, and error rate, the user experience may be worse;
5. ❌ The context length only affects prefill: as the length of KV Cache increases, decoding will also become slower and the video memory will become tighter;
6. ❌ 100% GPU utilization is good: it may be invalid recalculation or inefficient scheduling;
7. ❌ Multiple cards will definitely speed up a single request: TP communication overhead may make a single request slower, but the throughput is higher;
8. ❌ Speculative decoding is universal: when the batch is high and the computing power is limited, the income is limited or even negative;
9. ❌ temperature=0 is completely certain: hardware/operator non-determinism and parallel reduction may still bring subtle differences;
10. ❌ Leave it alone after deployment: models, traffic, and context distribution will change and must be continuously monitored and stressed.

## 12. Summary
- inference optimization revolves around four quantities: **TTFT, TPOT, throughput, and memory**;
- prefill is computationally intensive, decode bandwidth intensive, and batch processing and KV management determine the cost;
- PagedAttention + continuous batch processing + quantization + prefix cache is the basic disk of the current serving;
- first calculates the video memory and SLO, then selects the framework and parallel strategy, and finally uses goodput to verify, instead of just focusing on GPU utilization.
