Overview of # Compilation process: from source code to machine code
> In one sentence: The **compiler passes the source program through lexical analysis, syntax analysis, semantic analysis, intermediate representation, optimization, code generation, assembly and linking, and finally turns it into an executable file; the front end is responsible for understanding the language, and the back end is responsible for adapting the hardware. IR is the dividing line between the two.**
> Positioning: It talks about the general compilation pipeline and core concepts, and is not bound to a certain language; the examples are mainly C-like syntax and LLVM style.

## 1. Panoramic assembly line
```
源码
 │
 ├─ 词法分析 Lexer      → Token 流
 ├─ 语法分析 Parser     → 语法树 CST/AST
 ├─ 语义分析 Sema       → 带类型与符号信息的 AST
 ├─ 中间表示 IR         → 三地址码 / SSA / LLVM IR
 ├─ 优化 Optimizer      → 等价的更优 IR
 ├─ 代码生成 Codegen    → 目标机器指令 / 汇编
 ├─ 汇编 Assembler      → 目标文件 .o
 └─ 链接 Linker         → 可执行文件 / 动态库
```
| Stage | Input | Output | Typical Problems |
|---|---|---|---|
| Lexical | Character stream | Token | Illegal characters, string is not closed |
| Syntax | Token | AST | Missing semicolon and mismatched brackets |
| Semantics | AST | Typed AST | Undefined variable, type mismatch |
| IR | AST | Three address codes/SSA | Complex control flow, optimization opportunities |
| Optimization | IR | Better IR | The trade-off between conservative and radical |
| Code generation | IR | Assembly | Insufficient registers, instruction selection |
| link | object file | executable file | symbol is undefined and duplicated |

The > interpreter omits "machine code after code generation"; JIT does "IR → machine code" at runtime; AOT completes the entire pipeline during the build period.

## 2. Lexical analysis: Character → Token
Lexical analyzer (Lexer/Scanner) cuts the character stream into meaningful units:
```
let x = a + 12;
```
```
KEYWORD(let)  IDENT(x)  ASSIGN(=)  IDENT(a)  PLUS(+)  NUMBER(12)  SEMI(;)
```
### 1. Implementation method
- **Handwritten**: state machine + loop, easy to control error locations and special rules (most production compilers);
- **Regular → NFA → DFA**: Use regular expressions to describe Token and automatically generate a state machine;
- **Tools**: flex/lex, re2c, Ragel.

### 2. Key rules
- **Longest match (maximal munch)**: `>=` cannot be cut into `>` and `=`;
The - keyword is usually looked up in the table after identifying the identifier;
- retains comments, row and column numbers, and file locations to facilitate error reporting;
- Strings, numeric literals, escapes, Unicode identifiers are the main complexity of the lexical layer.

> Token generally includes: type, original text, value, and location interval. Location information is carried through all subsequent stages.

## 3. Syntax analysis: Token → AST
### 1. Grammar
Use context-free grammar (CFG) to describe language structure:
```
expr   → term (("+" | "-") term)*
term   → factor (("*" | "/") factor)*
factor → NUMBER | IDENT | "(" expr ")"
```
-Terminator: `+`, `NUMBER`, etc.;
- non-terminal symbols: `expr`, `term`, etc.;
- production describes "how to expand".

### 2. Syntax tree vs abstract syntax tree
- **CST (specific syntax tree)**: retain all Tokens, including brackets and semicolons;
- **AST (Abstract Syntax Tree)**: Only retain the semantic structure and discard redundant symbols;
- Subsequent stages usually only operate on the AST.

AST of `a + b * 12`:
```
    +
   / \
  a   *
     / \
    b   12
```
### 3. Analysis algorithm
| Method | Characteristics | Represents |
|---|---|---|
| Recursive descent | Handwritten, intuitive, error-prone | Clang, Go, most modern languages |
| Pratt / Operator priority | Processing expression priority | Expression parsing, configuration language |
| LL(1) | Top-down, look at a Token | Tutorial, simple DSL |
| LR(1)/LALR | Bottom-up, expressive | yacc/bison, old-school compiler |
| PEG / Packrat | Traceability, easy to write | Partial DSL, parsing library |

### 4. Common difficulties
- **Ambiguity**: dangling else, operator priority; use priority/associativity declaration or rewrite the grammar to solve;
- **Left recursion**: Top-down parsing needs to eliminate left recursion;
- **error recovery**: synchronize to semicolon/right bracket, try to continue parsing instead of just reporting the first error;
- **Incremental parsing**: The editor requires partial reparsing (tree-sitter, etc.).

## 4. Semantic analysis: AST → AST with semantics
Correct syntax does not mean the program is legal. Semantic analysis is responsible for:
1. **symbol table and scope**: visibility of variables, functions, types, and modules;
2. **Name analysis**: Is this `foo` a local variable, a global variable or a function?
3. **type check**: assignment compatibility, function parameters, return values, generic constraints;
4. **type inference**: `let x = 1` is inferred as `Int`; HM algorithm is used in some scenarios of ML/Haskell/Rust;
5. **Control flow check**: uninitialized variables, unreachable code, return path;
6. **Ownership/borrow checking**: Rust’s borrow checker is part of semantic analysis;
7. **constant evaluation**: compile-time calculation of `const` expression.

The output is usually **with type annotation AST**, and may generate diagnostic information (warning/error) and source code location.

## 5. Intermediate representation IR
### 1. Why IR is needed
- decouples "language-related" and "hardware-related";
- The same front end can be connected to multiple back ends (x86, ARM, RISC-V, WASM);
- optimization is done once on IR, and all target platforms benefit;
- facilitates analysis: data flow, control flow, dependencies.

### 2. Common forms
| Form | Features |
|---|---|
| Three address code TAC | Each instruction has at most one operation, easy to read and optimize |
| SSA | Each variable is only assigned once, which facilitates data flow analysis |
| basic block + CFG | control flow graph, the basis of optimization and scheduling |
| LLVM IR | Strong type, SSA, modular, mature ecosystem |
| bytecode | stack/register type, JVM, Python, WASM |

Three address codes of `a + b * 12`:
```
t1 = b * 12
t2 = a + t1
```
SSA form:
```
t1 = b * 12
t2 = a + t1
```
 (Same as TAC when there is no branch; when there are branches, use the new version `x1`, `x2` for each assignment point.)

### 3. Basic block and control flow graph
- **basic block**: sequential execution, instruction sequence with only one entry and one exit;
- **CFG**: Nodes are basic blocks and edges are jump relationships;
- Most optimizations are done on CFG/SSA: arrival definitions, active variables, dominance relationships.

## 6. Optimization: equivalent program transformation
### 1. Local optimization
| Optimization | Example |
|---|---|
| constant folding | `3 * 4` → `12` |
| constant propagation | `x = 3; y = x + 1` → `y = 4` |
| Algebraic simplification | `x * 1` → `x`, `x + 0` → `x` |
| Common subexpression elimination CSE | Repeated calculations `a * b` Only counted once |
| Dead Code Elimination DCE | Remove code that has no side effects and results in unused code |

### 2. Global/loop optimization
- **inline**: expand small functions to reduce calling overhead and expose more optimizations;
- **External loop invariants**: Move the invariant calculations inside the loop outside the loop;
- **strength weakens**: `x * 2` → `x << 1`, `x % 2` → `x & 1`;
- **Loop expansion**: reduce branches and improve instruction level parallelism;
- **Vectorization**: Turn scalar loops into SIMD;
- **Tail call optimization**: reuse stack frames to avoid recursive stack explosion (depends on language/compiler).

### 3. Register allocation
- The target machine has limited registers, and the virtual registers in the IR may be hundreds or thousands;
- **Graph coloring**: variables are nodes, conflicts are edges, and colors are registers;
- **linear scan**: allocated according to active intervals, fast, commonly used in JIT;
When - registers are not enough, **overflows (spills)** to the stack, and performance decreases.

### 4. Optimization boundaries
- optimization must keep **observable behavior consistent with**;
- Undefined behavior (UB) gives the compiler a lot of freedom, and also brings "weird behavior after optimization";
- `-O0/-O1/-O2/-O3/-Os` is a trade-off, not higher is faster (code expansion, cache failure);
- Modern compilers also do PGO (profile-guided optimization) and LTO (link-time optimization).

## 7. Code generation, assembly and linking
### 1. Code generation
- instruction selection: map IR to target instructions using tree overlay/pattern matching;
- register allocation: map virtual registers to physical registers;
- instruction scheduling: rearrange instructions, hide delays;
- ABI: Which registers the parameters are placed in, return value, stack alignment, caller/callee storage;
- stack frame: local variables, overflow slot, return address, canary.

### 2. Assembly and object files
The assembler converts the assembly into an object file:

| segment | content |
|---|---|
| `.text` | Machine instruction |
| `.data` | Global/static variables initialized |
| `.bss` | Global/static variables are not initialized (do not occupy file space) |
| `.rodata` | Read-only constant, string |

The target file also contains:
- **symbol table**: exported/undefined symbols;
- **relocation table**: address that needs to be patched during linking;
- debugging information (DWARF), exception table.

### 3. Link
- **static link**: Copy the library code into the executable file, simple deployment and large size;
- **dynamic link**: load `.so/.dylib/.dll` at runtime, shared memory, small size, but dependent on the environment;
- **PLT/GOT**: Under position-independent code (PIC), external functions are called through jump tables;
- Common errors: `undefined symbol`, `duplicate symbol`, ABI incompatibility, library version conflict.

## 8. Execution model: AOT, JIT, interpreter
| Model | Compilation Timing | Advantages | Disadvantages |
|---|---|---|---|
| Interpreter | Explains each item when running | Fast startup, simple implementation | Slow execution |
| AOT | Compiled during build time | Fast startup, stable performance | Unable to use runtime information |
| JIT | Runtime compilation | Can do profile optimization, de-virtualization | Startup preheating, memory overhead |
| Hybrid | explanation + JIT layering | Taking into account startup and peak value | Implementation complexity |

Common JIT layering:
1. interpreter/template JIT: quick start;
2. baseline JIT: simple compilation;
3. Optimization JIT: Radical optimization based on hotspot and type feedback;
4. De-optimization (deopt): Fall back to the interpreter when the hypothesis fails.

> WebAssembly is a "portable compilation target": C/C++/Rust is first compiled to WASM, and then compiled and executed by the browser/runtime.

## 9. A minimal example
Source code:
```c
int f(int a, int b) {
    return a + b * 12;
}
```
Token:
```
INT IDENT(f) LPAREN INT IDENT(a) COMMA INT IDENT(b) RPAREN LBRACE
RETURN IDENT(a) PLUS IDENT(b) STAR NUMBER(12) SEMI RBRACE
```
AST:
```
Return
  Binary(+)
    Ident(a)
    Binary(*)
      Ident(b)
      Literal(12)
```
 three address codes:
After ```
t1 = b * 12
t2 = a + t1
return t2
```
 optimization (strength weakened):
```
t1 = b << 3      // 8b
t2 = b << 2      // 4b
t3 = t1 + t2     // 12b
t4 = a + t3
return t4
```
 pseudo assembly (x86-64 style):
```
f:
    lea  eax, [rsi + rsi*2]   ; b * 3
    lea  eax, [rdi + rax*4]   ; a + b*12
    ret
```
> A real compiler will choose different implementations based on the target architecture, register pressure, and instruction latency. Here we only illustrate the mapping relationship of "AST → IR → machine code".

Suggested learning paths:
1. Write an interpreter that only supports four arithmetic operations on integers;
2. adds variables, scopes, and function calls;
3. generates three address codes, performs constant folding and DCE;
4. generates simple stacked bytecode or WASM;
5. Finally, we will study SSA, register allocation and JIT.

## 11. Common misunderstandings
1. ❌ The compiler must be faster than the interpreter: it is more suitable for short scripts and starting the interpreter for sensitive scenarios;
2. ❌ AST is a syntax tree: AST is an abstract structure, and CST retains all syntax details;
3. ❌ The more optimizations, the better: it may increase compilation time, code size, or even reduce cache hit rate;
4. ❌ Type checking is done at compile time: dynamic languages, JIT, and runtime reflection all do type checking;
5. ❌ The linker is not part of the compilation process: it determines whether the final executable file can be generated;
6. ❌ JIT is the interpreter: JIT will generate machine code, but the interpreter will not;
7. ❌ Undefined behavior is just "the result is uncertain": the compiler can do radical optimization based on UB, and the behavior may be completely unexpected;
8. ❌ Front-end/back-end are just names: the front-end is close to the language, the back-end is close to the hardware, and IR is the contract between the two.

## 12. Summary
The core of the - compiler is **, which reduces the abstraction** in stages: Character → Token → Tree → IR → Instruction → Executable file;
- front-end guarantees "the program is legal", the middle-end guarantees "the program is better", and the back-end guarantees "the program can run";
- IR, CFG, and SSA are common languages for modern optimization and code generation;
- Understanding the pipeline is more useful than memorizing the parameters of a certain compiler.
