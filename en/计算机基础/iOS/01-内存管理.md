# IOS memory management
> front-end: based on Objective-C 2.0, Runtime source code (objc4), does not involve Swift ARC additional logic

## 1. Basic concepts: why memory management is needed
The OC object is allocated in the **heap (Heap)**, and the life cycle is managed by the developer; the memory on the stack is automatically recycled.
Core goal: Ensure that objects are released when not in use, to avoid:
1. Memory leak: No one releases the object and it keeps occupying heap memory
2. Wild pointer: The object has been released, but the pointer still accesses it (EXC_BAD_ACCESS)

OC uses **reference count (Reference Count)** model:
> reference count = how many pointers are "using this object"
> retain: count +1; release: count -1; call dealloc when count == 0 to release the memory

> Note: Reference counting only manages the object life cycle, **does not manage the memory** of the internal members of the object.

Two modes:
- **MRC (manual reference counting)**: manual write retain/release/autorelease
- **ARC (automatic reference counting)**: The compiler automatically inserts retain/release/autorelease during compilation, and the runtime logic is consistent with MRC. **ARC is not a runtime mechanism, but compile-time syntax analysis + code insertion**

## 2. Object memory layout & isa and NONPOINTER_ISA
objc object essential structure (simplified version)
```c
struct objc_object {
    Class isa;
};
```
 In a 64-bit system, isa is a 64bit number and is no longer simply a pointer. Enable **NONPOINTER_ISA** (enabled by default):
The 64-bit bits of isa are split and multiplexed. One part stores the class pointer, and the other part directly stores the reference count, whether it is a weak reference, whether it is being released, whether there is a C++ destructor, etc. Mark** to improve performance and reduce the overhead of accessing SideTable.

64-bit isa bitfield (objc4):
- 0 bit: nonpointer flag bit, 1=enable NONPOINTER_ISA
- 1 bit: has_assoc whether there is an associated object
- 2 bit: has_cxx_dtor Is there a C++ destructor/custom dealloc
- 3 bit: shiftcls class pointer (33bit)
- Other bits: reference count, weakly_referenced, deallocating flag

⚠️ Key points:
The reference count stored in **isa has a limited capacity. After the count value overflows, the reference count no longer exists in isa and is transferred to SideTable for separate maintenance.**
This is a misunderstanding that many people easily fall into: not all objects have reference counts with isa.

## 3. SideTable: the real container of reference counting and weak reference tables
objc internally maintains a SideTable array, multiple SideTables (the number is related to the number of CPU cores), and uses hash tables to disperse objects to solve lock competition and improve concurrency performance.
```c
struct SideTable {
    spinlock_t slock;          // 自旋锁，保护读写
    RefcountMap refcnts;       // 引用计数哈希表（key:对象地址，value:计数值）
    weak_table_t weak_table;   // 弱引用表
};
```
### When to use SideTable’s RefcountMap?
The internal reference count of 1. isa cannot be saved (overflow)
2. TaggedPointer object: **has no isa, no reference count, and does not go to SideTable**
3. class objects, metaclass objects: special treatment, generally do not participate in regular reference counting

### Weak_table_t weak reference table
The weak reference table is a hash structure:
- key: object address
- value: Stores an array of addresses of all weak pointers pointing to this object

When object dealloc:
1. Find all weak pointers corresponding to this object in weak_table
2. sets the value of each weak pointer to `nil`
3. Clear this weak reference record
👉 This is the underlying source of weak automatically setting nil!

> Therefore, when a weak variable is accessed, the object is not read directly, and the weak reference table must be checked every time; weak is safer than __unsafe_unretained, but has overhead.
> __unsafe_unretained: The weak reference table is not added. After the object is destroyed, the pointer becomes a wild pointer and will not be set to nil.

## 4. TaggedPointer: special “pseudo-object”
64-bit iOS introduces TaggedPointer to optimize small numbers and small string objects (NSNumber, NSString).
Features:
1. **does not allocate memory on the heap! No malloc, no free**
The value of the 2. pointer itself directly stores the data + mark bit, not the address pointing to the heap memory.
3. **has no reference count, does not require retain/release, and does not go SideTable**
4. thread-safe, no lock required
5. When the value exceeds the capacity (the string is too long, the number is too large), it automatically changes back to a normal heap object

Identification: The highest bit mark of the pointer address.
Frequent pitfalls in interviews:
```objc
NSString *s1 = @"abc";
NSString *s2 = [NSString stringWithFormat:@"abc"];
// 短字符串有可能是TaggedPointer，打印指针地址能看出特征
```
> TaggedPointer is Apple's huge performance optimization, reducing heap allocation overhead in a large number of small object scenarios.

## 5. AutoreleasePool automatic release pool
### 1. Function
Autorelease does not release immediately, but adds the object **to the automatic release pool**, and releases it uniformly when the pool goes out of scope (drain).
Manual use in the MRC era; compilers under ARC will still insert a large number of autoreleases.

### 2. The underlying structure: not an array, but a doubly linked list
```c
struct AutoreleasePoolPage {
    magic_t magic;
    id *next;          // 下一个可存放autorelease对象的位置
    pthread_t thread;  // 归属线程，autorelease池和线程绑定！
    struct AutoreleasePoolPage *parent;
    struct AutoreleasePoolPage *child;
    // 这里后面紧跟着存放对象指针的内存
};
```
- Each page is 4096 bytes (one memory page size)
- `next` The pointer is similar to the top of the stack. Every time it autoreleases an object, next moves forward and stores the object address.
- When a page is full, create a new child page and string it into a linked list
- `@autoreleasepool {}` inserts a **POOL_BOUNDARY (sentinel mark)** at the bottom layer, not an object

### 3. When is it drained?
1. `@autoreleasepool{}` End of braces: Traverse backward from next until you encounter POOL_BOUNDARY, and issue release to the objects one by one
2. Runloop loop: The main thread Runloop will automatically drain and automatically release the pool before each loop sleeps.
> Therefore: in the main thread, if you do not manually add autoreleasepool, temporary autorelease objects will also be released in the runloop cycle, but creating a large number of temporary objects in a loop will instantly increase the memory!

### 4. Classic scenario: creating a large number of temporary objects in a loop
```objc
// 坏写法，循环产生大量autorelease对象，要等runloop才释放
for (int i=0; i<100000; i++) {
    NSString *str = [NSString stringWithFormat:@"%d", i];
}
// 优化：包一层 @autoreleasepool，每一轮循环结束就释放
for (int i=0; i<100000; i++) {
    @autoreleasepool {
        NSString *str = [NSString stringWithFormat:@"%d", i];
    }
}
```
### 5. Important Rules
- AutoreleasePool **is bound to thread**; if the child thread does not have a Runloop or manual @autoreleasepool, the autorelease object will not be released, resulting in a direct memory leak!
- `autorelease` just adds the object to the pool, and the reference count +1 (the same as retain, but the release timing is delayed)

## 6. The difference between the underlying ARC modifiers (__strong /__weak / __unsafe_unretained /__autoreleasing)
The ARC modifier essentially tells the compiler to insert retain/release/autorelease code at the appropriate location.

| modifier | behavior | underlying |
|---|---|---|
| __strong | By default, the object is held. When the pointer is assigned, the compiler inserts retain; when the pointer leaves the scope, release is inserted. | uses normal reference counting. |
|__weak | is not held, and is added to the SideTable weak reference table; the object is automatically set to nil when destroyed. | Query weak_table, with lock overhead |
| __unsafe_unretained | Not held, not added to the weak reference table; object destruction does not set nil, wild pointer | No additional overhead, unsafe |
|__autoreleasing | stores autorelease objects; generally used to pass parameters to NSError**| objects are added to the autorelease pool |

> NSError**error Why is the parameter __autoreleasing?
> The compiler automatically adds `NSError **` to `NSError * __autoreleasing *`. The error object generated inside the method is placed in the automatic release pool, and the life cycle is managed by the caller's pool.

### Retain Cycle
__strong will have circular references if they hold each other: A has a strong reference to B, and B has a strong reference to A. The reference count of both can never reach 0, and neither can dealloc, resulting in a memory leak.
Solution: Change one end to __weak /__unsafe_unretained.
Common scenarios: Block captures external variables and Delegate.
> Block captures the __strong variable and will retain it; captures__weak and does not retain it.

> Supplement: Block only captures variables on the heap; stack Block does not hold them.

## 7. Object destruction process: dealloc underlying call link
When `refcount == 0`, runtime triggers dealloc:
1. `objc_object::rootDealloc()`
2. Judgment: Is it TaggedPointer? Yes, return directly without processing
3. Determines whether there is C++ destruction, associated objects, and weak references:
   - If none: quick release, free memory directly (fast path, high performance)
   - If yes: follow the slow process `object_dispose()`
4. `object_dispose`：
   - calls objc_destructInstance:
     - executes C++ destructor
     - Clear associated objects (objc_removeAssociatedObjects)
     - Clear the weak reference table: find all weak pointers and set them to nil
5. finally calls free to release the heap memory

⚠️ Key points:
- dealloc is a runtime call, not a manual call by you; MRC manually calling dealloc is a wrong behavior
- **cannot directly access members** other than the __weak variable of self in dealloc. The object is being destroyed; do not perform time-consuming or asynchronous operations in dealloc.
After - dealloc is called, the memory has been released and is a wild pointer.

## 8. Memory layout: iOS process memory partition
A process address space is roughly divided into:
1. **code segment Text**: read-only, executable instructions (Mach-O)
2. **data segment Data**: global variables, static variables, constant strings
3. **Heap Heap**: malloc/alloc allocation, growing upward, OC objects are here (except TaggedPointer)
4. **Stack Stack**: Function local variables and function frames grow downward; the stack memory is automatically recycled and the size is very small (a few MB for the main thread stack)
5. shared library, kernel area

> Stack overflow: recursion is too deep, extremely large local array; heap overflow: malloc memory is written out of bounds.

## 9. Common pitfalls & high-frequency interview questions and answers
1. Q: Does reference counting still exist under ARC?
A: Yes, ARC is just the compiler automatically inserting code, and the runtime reference counting logic is exactly the same as MRC.

2. Q: How is weak implemented?
A: SideTable's weak_table traverses the weak reference list when the object is destroyed and sets all weak pointers to nil.

3. Q: Why cannot weak modify local variables? Syntactically it's OK, but local variables are destroyed when they go out of scope; weak mainly solves circular references.

4. Q: When will autoreleasepool be released? Runloop drains before sleeping, and @autoreleasepool ends drain; if there is no runloop for child threads, the pool must be added manually.

5. Q: Why is TaggedPointer thread safe?
A: There are no heap objects, no reference counting, no need to modify shared data, and no locks.

6. Q: Is the reference count always stored in isa?
A: Under NONPOINTER_ISA, isa exists when the count is small; after overflow, it is placed in RefcountMap of SideTable. TaggedPointer has no isa.

7. Q: When will the associated object be released?
A: Clear them uniformly in objc_destructInstance of object dealloc, instead of following the attribute life cycle.

8. Q: Block circular reference: Why is strongSelf added after weakSelf?
A: weakSelf may be nil at any time; set strongSelf inside the block to ensure that the object will not be released midway during the execution of the block, and will be released automatically after execution.

## 10. Summary
> alloc → open up objc_object on the heap → isa (NONPOINTER_ISA stores class information + a small amount of rc) → retain increases the reference count and stores it in SideTable.RefcountMap after overflow;
The > weak pointer is registered to SideTable.weak_table;
> autorelease adds the object to the AutoreleasePoolPage linked list;
> reference count reaches 0 → rootDealloc → object_dispose → destruct C++, clean up associated objects, clear weak pointers → free heap memory.
