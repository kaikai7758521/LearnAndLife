# Database index and transaction
> In one sentence: **The index determines whether the search is fast or not, and the transaction determines whether the modification is correct; the former is a data structure and query optimization issue, and the latter is a concurrency control and consistency model issue.**
> Main line: Taking MySQL InnoDB as an example, the conclusion also applies to most relational databases.

## 1. The essence of indexing: reducing the amount of data scanned
### 1. Why is it a B+ tree?
- disk reads by page (InnoDB default 16KB), the cost of one I/O is much higher than memory comparison;
- B+ tree **short and fat**: non-leaf nodes only store keys and pointers, one page can hold thousands of keys, and tens of millions of data usually only have 3~4 layers;
All data of - **are in the leaf node**. The leaves are connected using a two-way linked list, and range queries only require sequential scanning;
- comparison:

| Structure | Equivalence query | Range query | Problem |
|---|---|---|---|
| Hash | O(1) | ❌ Not supported | Unable to sort, range scan |
| Binary search tree | O(log n) | General | The tree is too tall and the number of I/Os is too high |
| B tree | O(log n) | General | Non-leaves also store data, with small fan-out |
| **B+ tree** | O(log n) | ✅ Leaf linked list | Write maintenance cost, page splitting |

### 2. InnoDB clustered index
```
主键索引（聚簇索引）叶子节点： [主键值 | 整行数据]
二级索引叶子节点：           [索引列 | 主键值]  → 再回表查整行
```
- table is a B+ tree organized by primary key. When **does not have a primary key, use hidden row_id**;
- The secondary index only stores the primary key. To check the complete row, **is required to return the table**;
- Therefore primary keys should be short and ordered: auto-incrementing bigint is better than random UUID (random primary keys will lead to page splits and cache hit rate decrease).

> Covering Index: The columns required for the query are all in the index, and there is no need to return the table. `Using index` appears in `Extra` of `EXPLAIN`.

## 2. Index type and design
### 1. Common types
| Type | Description | Scenario |
|---|---|---|
| Primary key index | Clustered index, unique and non-empty | Essential for every table |
| unique index | constraint + query | idempotent key, business unique number |
| Ordinary index | Accelerated query | High frequency filtering/sorting field |
| Joint index | Multi-column combination | Multi-condition query, covering index |
| Prefix index | Only indexes the first N digits of the string | Long URL, email, save space |
| Full text index | Word segmentation search | Simple text search (ES for complex scenes) |

### 2. Union index and leftmost prefix
```sql
ALTER TABLE orders ADD INDEX idx_user_status_time (user_id, status, created_at);
```
 can use index queries:
Situations when ```sql
WHERE user_id = 1                                  -- 用 user_id
WHERE user_id = 1 AND status = 2                   -- 用 user_id + status
WHERE user_id = 1 AND status = 2 AND created_at > '2026-01-01'
                                                   -- 三列都用上
WHERE user_id = 1 ORDER BY status, created_at      -- 排序也可利用索引
```
 is not used:
```sql
WHERE status = 2                                   -- ❌ 跳过最左列
WHERE user_id = 1 AND created_at > '2026-01-01'    -- ⚠️ 只能用 user_id
WHERE user_id = 1 AND status > 2 AND created_at > '2026-01-01'
                                                   -- ⚠️ status 是范围，created_at 只能靠 ICP 过滤，无法继续缩小索引范围
```
 design tips:
1. **equivalent conditions are placed in front, and range conditions are placed in the back**;
2. The sorting and grouping fields should be placed after the equivalent conditions as much as possible;
3. The column with high distinction does not necessarily have to be placed at the far left. **depends on the query mode**;
4. A joint index can serve multiple leftmost prefix queries. Do not build one for each combination.

### 3. Selectivity
```sql
-- 区分度 = 不重复值 / 总行数，越接近 1 越好
SELECT COUNT(DISTINCT status) / COUNT(*) FROM orders;
```
- When low-discrimination columns such as gender and status are indexed separately, the optimizer often still chooses a full table scan;
- However, if the low-discrimination columns are placed in the joint index and combined with the high-discrimination columns, they can still play a role;
- Prefix index should choose a long enough prefix to make the distinction close to the complete column.

## 3. EXPLAIN: Understand the execution plan
```sql
EXPLAIN ANALYZE
SELECT id, amount FROM orders
WHERE user_id = 42 AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```
| Field | Focus |
|---|---|
| `type` | Access type, performance from best to worst: `system > const > eq_ref > ref > range > index > ALL` |
| `key` | The actual index used, `NULL` means no index |
| `rows` | Estimated number of scanning lines, the smaller the better |
| `filtered` | Remaining proportion after scanning. If it is too low, it indicates poor index filtering ability. |
| `Extra` | `Using index` (coverage), `Using index condition` (ICP), `Using filesort`, `Using temporary` |

Signs to be wary of:
- `type=ALL` + `rows` is very large: full table scan;
- `Using filesort`: Index sorting cannot be used, and it is very slow when the amount of data is large;
- `Using temporary`: Grouping/dereusing temporary tables;
There is a huge gap between - `rows` and the actual situation: the statistical information is expired and can be `ANALYZE TABLE`.

> `EXPLAIN` is an estimate. `EXPLAIN ANALYZE` (MySQL 8.0.18+) will actually execute and give the actual number of rows and time consumption, which is more suitable for locating slow queries.

## 4. Common causes of index failure
| How to write | Why is it invalid? | Change how to write |
|---|---|---|
| `WHERE DATE(created_at) = '2026-01-01'` | Perform function operation on the column | Change to range: `>= 当天 AND < 次日` |
| `WHERE phone = 13800000000` (phone is varchar) | Implicit type conversion | Parameter string |
| `WHERE name LIKE '%张%'` | Leading wildcard | Prefix matching, full-text index, ES |
| `WHERE a = 1 OR b = 2` (b no index) | Unable to index at the same time | Query and merge separately, or supplement the index |
| `WHERE status != 1` | The optimizer determines that the scan ratio is high | Change to enumeration range or complementary joint index |
| `WHERE a + 1 = 10` | Column participates in the operation | Moves the operation to the right |
| The joint index skips the leftmost column | Does not satisfy the leftmost prefix | Adjust the index or query |

Supplement:
- `IS NULL` can use indexes, `NULL` is indexed in InnoDB;
- `ORDER BY` The prerequisite for using the index is that the sorting order is consistent with the index order, and the preceding columns are equivalent conditions;
- The more indexes, the better: each index will increase the writing cost, occupy the buffer pool, and slow down DDL.

## 5. Writing path: What happened in an UPDATE
```
1. 从 buffer pool 找页，找不到就从磁盘读入
2. 修改页内容（脏页）
3. 写 undo log（回滚 + MVCC）
4. 写 redo log（WAL，保证崩溃恢复）
5. 事务提交：redo 刷盘（可配置）+ 写 binlog
6. 后台线程异步把脏页刷回磁盘
```
### 1. The meaning of WAL
- writes pages randomly → writes logs sequentially, greatly reducing submission delay;
After - crashes, use redo to replay committed transactions, and use undo to roll back uncommitted transactions;
- `innodb_flush_log_at_trx_commit`:

| Value | Behavior | Security |
|---|---|---|
| 1 | Submit brushing every time | is the safest and has the lowest performance |
| 2 | writes OS cache and flushes disks every second | 1 second may be lost due to downtime |
| 0 | Write and flush the disk every second | May lose more than 1 second |

### 2. binlog and two-stage submission
- binlog is a logical log, used for master-slave replication and data recovery;
- redo and binlog are guaranteed to be consistent through **two-stage submission**: redo prepare → write binlog → redo commit;
- `sync_binlog=1` ensures that the binlog is flushed every time it is submitted, which is commonly used in financial-level scenarios;
- Large transactions will amplify redo, locks, and master-slave delays and must be split.

### 3. Other key mechanisms
- **undo log**: rollback + MVCC version chain;
- **change buffer**: Cache changes first when the secondary index page is not in memory to reduce random reads;
- **doublewrite**: Prevent half page damage caused by power outage during page writing.

## 6. Transaction and isolation level
### 1. ACID
| Feature | Meaning | InnoDB Implementation |
|---|---|---|
| Atomicity | Either all success or all failure | undo log |
| Consistency | Constraints, foreign keys, and business rules are not destroyed | Guaranteed by both the database and the application |
| Isolation | Concurrent transactions do not interfere with each other | Lock + MVCC |
| Durability | Not lost after submission | redo log + brush |

### 2. Three types of read exceptions
- **Dirty read**: Read uncommitted data from other transactions;
- **Non-repeatable read**: Read the same row twice in the same transaction, and the results are different (changed by others);
- **Phantom reading**: Two range queries in the same transaction, with different numbers of rows (inserted by others).

### 3. Isolation level
| Level | Dirty read | Non-repeatable read | Phantom read | Description |
|---|---|---|---|---|
| READ UNCOMMITTED | ✅ Possible | ✅ | ✅ | Hardly used |
| READ COMMITTED | ❌ | ✅ | ✅ | One new snapshot per statement |
| REPEATABLE READ | ❌ | ❌ | ⚠️ The snapshot cannot be read, and the current read depends on the lock | MySQL default |
| SERIALIZABLE | ❌ | ❌ | ❌ | All locked, worst concurrency |

> PostgreSQL defaults to READ COMMITTED; MySQL defaults to REPEATABLE READ. Don't assume the default level is consistent when migrating across libraries.

### 4. MVCC: Why does snapshot reading not require locking?
InnoDB has hidden columns per row:
- `DB_TRX_ID`: The transaction ID that last modified the row;
- `DB_ROLL_PTR`: points to the undo version chain.

**Read View** is generated when the transaction reads the first snapshot, recording the current active transaction ID set. When reading, find the version "visible to the current transaction" along the version chain:
- version transaction ID < minimum active ID: committed, visible;
- version transaction ID in active collection: uncommitted, invisible;
- version transaction ID ≥ next transaction ID: opened after this transaction, invisible.

| Read type | statement | Whether to lock | What to read |
|---|---|---|---|
| Snapshot Read | Normal `SELECT` | No | Read View Corresponding historical version |
| currently reads | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` | is the latest committed version of | + lock |

### 5. Phantom reading under RR
- **snapshot read**: The consistency view is fixed, the newly inserted rows cannot be seen, and there will be no phantom reading;
- **currently reads**: Use **next-key lock (record lock + gap lock)** to lock the range to prevent other transactions from being inserted in the gap;
- Therefore, "RR completely solves phantom reading" is not accurate. The accurate statement is "snapshot reading relies on MVCC, and current reading relies on locking."

`READ COMMITTED` generally does not add gap locks (except for foreign keys and uniqueness checks), and the concurrency is higher, but phantom reads may occur, and many Internet businesses will actively choose RC.

### 6. Types of locks
| Lock | Function |
|---|---|
| Record Lock | Lock a certain row of index records |
| Gap Lock | Locks the gap between index records to prevent insertion |
| Next-Key Lock | record lock + gap lock, RR range query default |
| inserts the intention lock | applies before inserting, conflicts with the gap lock |
| Self-increasing lock | Self-increasing primary key allocation |

The > lock is added to the **index**. If the query does not go through the index, a large number of rows or even the entire table may be locked. This is a common reason for "slow updates and more deadlocks".

## 7. Deadlock: how to generate and how to reduce it
```sql
-- 事务 A
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 事务 B（相反顺序）
UPDATE accounts SET balance = balance - 100 WHERE id = 2;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
```
 Each of the two transactions holds a lock and waits for the other to release it, forming a loop. InnoDB detects deadlock and rolls back one of the transactions (`Deadlock found when trying to get lock`).

Reduce deadlocks:
1. **Fixed locking sequence** (updated in ascending order by primary key);
2. transactions should be as short as possible to reduce lock holding time;
3. updates the primary key or unique index to reduce the lock scope;
4. avoid large range `UPDATE ... WHERE status = ?`;
5. The application layer catches the deadlock exception and **retries a limited number of times**;
6. Lower the isolation level to RC if necessary and reduce gap locking.

## 8. Transaction best practices
1. **Short transaction**: Do not do RPC, send messages, or wait for user input in the transaction;
2. **Small batch**: Split large batch updates into multiple batches to avoid long transactions and master-slave delays;
3. **Fixed order**: Multi-table/multi-row updates are locked in a unified order;
4. **Idempotent**: Retries and message consumption require unique keys or state machines;
5. **Reasonable isolation level**: The default RR is sufficient, RC can be used when there are many reads and writes and phantom reads can be accepted;
6. **Avoid `SELECT *`**: Reduce table return and network transmission;
7. **monitoring lock waiting**: `innodb_lock_wait_timeout`, `SHOW ENGINE INNODB STATUS`;
8. **Master-slave delay**: Read the master library immediately after writing, or use GTID/site to wait.

## 9. Capacity and expansion
- `innodb_buffer_pool_size` is usually set to 60%~75% of physical memory (dedicated database);
- The more connections the better, the application side connection pool and database `max_connections` must match;
- When a single table is too large, consider archiving and partitioning first, and finally divide the database into tables;
- Sub-database and sub-table will bring cross-shard transactions, aggregation queries, expansion and migration costs, so do not introduce them too early;
- master-slave replication:

| Mode | Features | Risks |
|---|---|---|
| Asynchronous replication | The main library returns immediately after submission | Data may be lost when the main library is down |
| Semi-synchronous replication | At least one slave library acknowledges | Increased latency |
| Group replication / MGR | Majority submission | Complex operation and maintenance |

## 10. Common misunderstandings
1. ❌ The more indexes, the better: write amplification, space occupation, and difficulty in optimizer selection;
2. ❌ The order of joint index columns does not matter: the leftmost prefix and range conditions directly determine whether they can be used;
3. ❌ `LIKE '%x%'` can also be indexed: the leading wildcard is basically equivalent to a full table scan;
4. ❌ Implicit type conversion does not matter: passing numbers in a string column will degenerate into a full table scan;
5. ❌ RR There is no phantom read at all: there is no snapshot read, and the current read relies on gap lock;
6. ❌ The longer the transaction, the safer it is: long-lasting locks, undo expansion, and master-slave delay increase;
7. ❌ The master-slave must be strongly consistent: there is a delay in asynchronous replication, and the read-slave library may read old data;
8. ❌ `NULL` cannot be indexed: InnoDB will index `NULL`, and `IS NULL` may also be indexed;
9. ❌ `count(*)` must be slower than `count(1)`: InnoDB is similar to the three and will scan;
10. ❌ Splitting databases and tables can solve all performance problems: indexes and SQL cannot be written well, and sharding will only make the problem more complicated.

## 11. Summary
The core of - index is **using space to replace I/O**: B+ tree, leftmost prefix, covering index, table return;
The core of the - transaction is **using locks and version control for consistency**: isolation level, MVCC, next-key lock;
- For slow queries, first look at the execution plan, for deadlocks, first look at the locking sequence, and for master-slave problems, first look at the delay;
- Thinking about the query mode when designing the table is much more effective than adding indexes afterwards.
