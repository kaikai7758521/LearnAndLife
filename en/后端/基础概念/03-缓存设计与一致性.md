# Cache design and consistency
> In a word: **cache uses "controllable old data" in exchange for delay and throughput**; the difficulty is never to put the data in, but to decide when it will fail and whether the system can survive when it fails.
> Positioning: Talk about the design pattern and consistency strategy of application layer cache, mainly local cache + Redis, and do not expand all commands of a certain middleware.

## 1. Why cache is effective and why it is dangerous
### 1. Delay gap
| access | magnitude |
|---|---|
| L1 cache | ~1ns |
| memory | ~100ns |
| SSD random read | ~100µs |
| Same computer room network RTT | ~0.5ms |
| Database index query | ~1~10ms |
| Cross-machine room RTT | ~30ms+ |

A database query may be tens of thousands of times the memory access. Putting hotspot data into memory will improve QPS and latency by orders of magnitude.

### 2. Benefits and considerations
| Income | Consideration |
|---|---|
| Reduce latency | Data may expire |
| Improves throughput | One more layer of fault points |
| Protected database | Memory and operation and maintenance costs |
| Peak clipping | When the cache breaks down, it crushes the DB |

The cache is suitable for: **reads more and writes less, has concentrated hot spots, and can tolerate short-term inconsistencies**.
Not suitable for: Strongly consistent transactions, more writes and less reads, extremely low hit rate, and the amount of data far exceeds the memory.

## 2. Where to place the cache: layered
```
浏览器缓存 → CDN → 网关缓存 → 本地缓存（进程内）→ Redis → 数据库 Buffer Pool
```
| Hierarchy | Represents | Advantages | Disadvantages |
|---|---|---|---|
| Local cache | Caffeine, Guava, Go sync.Map | Nanosecond level, no network | Multiple instances are inconsistent, capacity is limited |
| Distributed cache | Redis, Memcached | Shared, large capacity | One more network round trip, high availability required |
| CDN | Edge node | Nearby access | Dynamic content is difficult to cache and refreshes slowly |

Typical combination of multi-level cache: **local cache carries hot spots + Redis carries shared**.
The invalidation of local cache depends on:
- short TTL (accept transient inconsistencies);
- publish and subscribe broadcast invalidation message;
The - version number is written into the key and verified when reading.

## Three or five cache modes
| Mode | Read | Write | Features |
|---|---|---|---|
| **Cache-Aside (bypass)** | The application reads the cache first, checks the DB on misses and backfills | Updates the DB, deletes the cache | Most commonly used, the logic is controlled by the application |
| Read-Through | applies read-only cache, the cache is responsible for returning to the source | — | requires cache layer support loader |
| Write-Through | — | Synchronous write cache + DB | Good consistency, high write latency |
| Write-Behind | — | write cache, asynchronous DB flushing | fast writing, data may be lost during downtime |
| Write-Around | — | Write directly to DB without touching the cache | Suitable for data that is not read much after writing |

### Cache-Aside standard writing method
```java
// 读
public User getUser(long id) {
    String key = "user:" + id;
    User cached = redis.get(key);
    if (cached != null) return cached;

    User user = db.selectById(id);
    if (user == null) {
        redis.set(key, NULL_MARKER, 60);      // 空值缓存，防穿透
        return null;
    }
    redis.set(key, user, 300 + random(0, 60)); // TTL 加随机，防雪崩
    return user;
}

// 写
public void updateUser(User user) {
    db.update(user);
    redis.delete("user:" + user.getId());      // 删除而不是更新
}
```
> Why write **deletes** instead of updating the cache: Two concurrent writes may fall into the cache in the wrong order, causing the old value to overwrite the new value. Deletion will cause at most one miss, but update may leave long-term dirty data.

## 4. Consistency: How to synchronize cache and database
### 1. Update the database first, then delete the cache
This is the default scheme for projects:
There is still a classic race condition in ```
写：UPDATE DB → DELETE cache
读：GET cache → miss → SELECT DB → SET cache
```
:
The probability of ```
读请求 miss → 查 DB 得到旧值
写请求 UPDATE DB 为新值 → DELETE cache
读请求把旧值 SET 进缓存   ← 脏数据
```
 is not high, but it will actually occur under high concurrency. Common relief methods:

| means | method | effect |
|---|---|---|
| TTL | All caches set expiration time | Eventually consistent, no guarantee |
| Delayed double deletion | Delete once after submission, delay 500ms~1s and delete again | Covers most of the competition window |
| Subscribe to binlog | Canal/Debezium monitors changes and deletes cache asynchronously | Does not rely on business code, more reliable |
| version number | value with version, verified when writing | can identify the old value |
| Strong consistent read | The key is to read the main library and not read the cache | Sacrificing performance for correctness |

### 2. Delayed double deletion
The ```java
db.update(user);
redis.delete(key);
executor.schedule(() -> redis.delete(key), 800, MILLISECONDS);
```
 delay time needs to cover the window of "read request backfilling the old value", usually taking the master-slave synchronization delay + business read time. It's not a silver bullet, it just lowers the probability.

### 3. Final consistency based on binlog
```
MySQL binlog → Canal/Debezium → MQ（按主键分区）→ 消费端删除/刷新缓存
```
 advantages:
- business code does not need to care about caching;
- The database is the only source of truth, the cache is just a projection;
- Partitioning by key ensures that changes in the same row are ordered.

The cost: longer links, need to deal with MQ duplication and latency.

### 4. Read what you have written
The user reads immediately after writing, and may read the old cache:
- reads the main library for a short time after writing;
- automatically sets the new value (with version) after writing successfully;
The - front-end brings back the new value directly, reducing one reading.

> Don’t force caching in strong consistency scenarios: either don’t cache, or use “database + version number + read master library” to ensure it.

## 5. Three classic problems with caching
### 1. Penetration
**Problem**: When querying data that does not exist at all, the cache never hits the cache and hits the DB every time.
**solution**:
1. **Null value cache**: `NULL` cannot be found and cached, TTL is short (30~60 seconds);
2. **Bloom filter**: Put the existing key into the filter when starting, and reject it directly if it does not exist;
3. **Parameter verification and current limiting**: Direct interception of illegal IDs and super long keys;
4. **Asynchronous backfill**: merge query for suspicious keys.

```java
if (!bloom.mightContain(key)) return null;  // 一定不存在
```

### 2. Breakdown
**Problem**: When a hot key expires, a large number of requests are returned to the source DB at the same time.
**solution**:
1. **Mutually exclusive reconstruction**: Only one request is allowed back to the origin, and the others are waiting;
2. **logical expiration**: `expireAt` is stored in value. It will be refreshed asynchronously after expiration. Other requests will return the old value first;
3. **never expires + background refresh**: suitable for extremely hot data;
4. **Single flight (single flight)**: Merge requests with the same key in the same process.

```java
// 互斥重建（示意）
if (redis.set("lock:" + key, "1", "NX", "PX", 3000)) {
    try {
        User user = db.selectById(id);
        redis.set(key, user, ttl);
    } finally {
        redis.delete("lock:" + key);
    }
} else {
    Thread.sleep(50);
    return getUser(id);   // 重试读缓存
}
```

### 3. Avalanche
**Problem**: A large number of keys expire at the same time, or the entire Redis cluster fails, and the traffic is instantly overwhelmed by the DB.
**solution**:
1. **TTL plus random**: `ttl = base + random(0, base * 0.2)`;
2. **Multi-level cache**: Local cache has the bottom line;
3. **High availability**: Sentinel/cluster, master-slave switching, multiple copies;
4. **circuit breaker downgrade**: limit the return-to-origin QPS when the cache is unavailable and return to the default value;
5. **Warm up**: Load hotspots first after release/restart to avoid cold start penetration.

### 4. Hot Key and Big Key
| Problems | Performance | Handling |
|---|---|---|
| Hotspot Key | Single-shard CPU/full bandwidth | Local cache, key splitting, read-write separation |
| Large Key | Slow single operation, network congestion, deletion lag | Split into multiple keys, compress, limit set size |
| Large collection traversal | `HGETALL`/`SMEMBERS` blocking | batching | with `HSCAN`/`SSCAN`

Experience threshold: If the string value exceeds 10KB and the collection elements exceed 5000, splitting must be considered. Detection tools:
```bash
redis-cli --bigkeys
redis-cli --hotkeys          # 需要 LFU 策略
redis-cli MEMORY USAGE key
```

## 6. Redis key mechanism
### 1. Single thread and quick command
- Redis command execution is **single-threaded** (6.0+ network read and write available IO thread), a slow command will block all requests;
- is prohibited from executing `KEYS *`, `FLUSHALL`, and key's `HGETALL`, super long Lua script;
- `SCAN` is a progressive traversal, but it may be repeated and is not guaranteed to be consistent.

### 2. Pipeline, transactions and Lua
| Mode | Atomic | Purpose |
|---|---|---|
| Pipeline | ❌ Not guaranteed to send | in batches, reducing RTT |
| MULTI/EXEC | ⚠️ Commands are queued and runtime errors are not rolled back | Simple transactions |
| Lua | ✅ Overall atom | Complex atomic logic, but shorter |

> Pipeline only packages and sends multiple commands, and may insert commands from other clients in the middle; use Lua when atomicity is required.

### 3. Cluster
- Redis Cluster has **16384 hash slots**, and the key is mapped through CRC16;
- multi-key operations require the same slot, and `{tag}` can be used to specify the hash tag;
- Cross-slot transactions and cross-slot Lua are not supported;
- expansion requires a migration slot, and the client must be able to handle `MOVED`/`ASK` redirection.

### 4. Elimination strategy
| Policy | Behavior |
|---|---|
| `noeviction` | Write error when memory is full (default) |
| `allkeys-lru` | All keys are eliminated by approximate LRU |
| `volatile-lru` | Only the key | with TTL set is eliminated.
| `allkeys-lfu` | Eliminated according to access frequency, suitable for hotspot stable scenarios |
| `volatile-ttl` | Prioritize the elimination of soon-to-expiry keys |
| `random` | Randomly eliminate |

> LRU is **'s approximate implementation of** (sampling several keys), not an exact linked list; when the cache hit rate is abnormal, first look at the elimination strategy and `maxmemory`.

### 5. Persistence
| Method | Principle | Advantages | Risks |
|---|---|---|---|
| RDB | fork the child process to generate a snapshot | The file is small and the recovery is fast | The data after the last snapshot may be lost |
| AOF | Additional write command, `everysec` flash disk | Less data loss | Large file, slow recovery |
| Mixed | RDB + AOF | Taking into account complex operation and maintenance | |

> Redis persistence is not equal to database-level persistence: fork blocking, COW may significantly increase memory usage, and AOF flushing delay must be included in the capacity design.

### 6. Memory and fragmentation
- follows `used_memory`, `used_memory_rss`, `mem_fragmentation_ratio`;
- has a high fragmentation rate after a large number of deletions. You can enable `activedefrag` or restart the migration;
- Object encoding (listpack/ziplist, intset) affects memory, and when the collection is too large, it will be converted into a hash table.

## 7. Distributed lock
### 1. Correct posture
```bash
# 加锁：唯一 value + 过期时间，必须原子
SET lock:order:123 "uuid-xxx" NX PX 30000
```
```lua
-- 释放：只能删自己的锁
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```
 key points:
1. value must be a unique identifier to prevent accidentally deleting other people's locks;
2. The expiration time must be set to prevent deadlock;
When the 3. service time may exceed TTL, **watchdog renewal** is required;
4. renewal is bound to the business thread, and the lock expires naturally after the process crashes;
5. When the accuracy requirements are extremely high, add **fencing token** (monotonically increasing version) to allow the downstream to reject the old holder's write.

### 2. Don’t myth distributed locks
- Redis master-slave asynchronous replication, the main database is down and the lock may be lost;
- RedLock relies on clocks and multiple nodes, and the academic community is controversial about its security;
- If it can be solved by database unique index, optimistic locking, and state machine, the database will be used first;
- distributed lock is suitable for "avoiding repeated execution as much as possible", but not suitable for "absolutely not allowing repetition".

## 8. Cache management
### 1. Indicator
| Indicator | Description |
|---|---|
| hit rate | `hits / (hits + misses)`, lower than expected first check key design and TTL |
| delay p99 Is | dragged down by slow commands/large keys |
| memory usage | is close to `maxmemory` and | will be eliminated frequently
| Elimination number | Sudden increase indicates insufficient capacity |
| Number of connections | Connection leak or client pool too large |
| slow log | `SLOWLOG GET`, pay attention to the command >10ms |
| Hot key / big key | Regular scan, split in advance |

### 2. Key design
```
业务:对象:ID:版本
user:1001:v3
```
- Add business prefix to avoid conflicts when multiple businesses share instances;
- Do not directly spell user input into the key to prevent injection and long keys;
The - version number can be used to "change the key and it will become invalid", which is safer than deleting one by one;
- controls the key length, which wastes memory if it is too long.

### 3. Capacity and preheating
- Estimate: `key 数 × (value 大小 + key 开销 + 对象头)`, leave 30%~50% margin;
After - is released/expanded, preheat according to the hotspot list to avoid cold start breakdown;
Do a stress test before the - big sale, focusing on the DB pressure of** at the moment when the **cache fails.

### 4. Downgrade
- When the cache cluster fails, all traffic cannot be given to DB:
  - local cache takes care of everything;
  - limits return-to-origin QPS;
  - returns default/old value;
  - non-core functions are turned off directly.
- The downgrade switch must be grayscale and rollable.

## 9. Typical scenarios
| Scenario | Solution | Note |
|---|---|---|
| Session | Redis Hash + TTL | Renewal, delete on logout |
| Ranking | ZSet | Sort by member if the scores are the same |
| counter/current limit | INCR + expired, or Lua | atomicity, clock |
| distributed lock | SET NX PX + Lua release | renewal, fencing |
| Hotspot details page | Local + Redis two levels | Failure broadcast |
| Deduplication | Set / Bloom filter | Bloom has misjudgment and is difficult to delete |
| Simple queue | List / Stream | Not as reliable as professional MQ |

> Don’t use Redis as the main database: its persistence and consistency model serves caching scenarios, not transactional storage.

## 10. Common misunderstandings
1. ❌ The cache is the database: the cache can be lost, but the database cannot be lost;
2. ❌ It is better to update the cache when writing than to delete: concurrent writing makes it easy for old values to overwrite new values;
3. ❌ The shorter the TTL, the more consistent it is: the greater the DB pressure, the higher the risk of breakdown;
4. ❌ If the cache is down, it will just slow down: the traffic hits the DB instantly, and may directly cause an avalanche;
5. ❌ A large key only occupies memory: it will block a single thread and slow down the entire instance;
6. ❌ Production can use `KEYS *`: O(n) blocking, must use `SCAN`;
7. ❌ Redis has no concurrency problems with a single thread: a single command is atomic, and multiple command combinations still have race conditions;
8. ❌ Distributed locks are absolutely safe: master-slave switching, clock drift, and renewal failure will destroy mutual exclusion;
9. ❌ LRU is accurate: Redis is a sampling approximation, and the hit rate must be measured in practice;
10. ❌ RDB/AOF makes Redis a reliable database: persistence has loss windows and recovery costs.

## 11. Summary
The gain of - cache comes from **hot spots and more reads and less writes**, at the cost of **consistency window and fault amplification**;
- Default solution: Cache-Aside + delete cache after updating DB + TTL cover;
- Three must-answer questions: penetration, breakdown, and avalanche, respectively using null/Bloom, mutual exclusion/logical expiration, and TTL random/multi-level/downgrade;
- Treat the cache as a "lost projection" and the database is the source of truth so that the system can survive cache failures.
