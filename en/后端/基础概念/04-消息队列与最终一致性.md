# Message queue and eventual consistency
> In one sentence: **MQ turns synchronous calls into asynchronous events, using "at least once delivery + idempotent consumption" for decoupling and peak clipping; what it brings is not real-time consistency, but controllable final consistency.**
> Positioning: Talk about the message queue model, reliability, sequence, transaction messages and consistency implementation, and does not bind all APIs of a certain middleware.

## 1. Why use message queue
| Purpose | Description | Example |
|---|---|---|
| Decoupling | Producers don’t care who consumes and how they consume | Events are sent after the order is placed, and points/inventory/notifications are subscribed separately |
| Asynchronous | The main link only performs core actions, and slow operations are post-processed. | If the registration is successful, return first and then send the welcome email. |
| Peak clipping | Put burst traffic into the queue and consume according to capacity | Flash kill, log, bury points |
| Broadcast | Multiple consumers of one event | Configuration changes, cache invalidation |
| data pipeline | log/change stream enters the data warehouse | binlog → Kafka → Flink |

The cost is equally obvious:
The - system changes from "one RPC" to "producer + broker + consumer + retry + dead letter";
- messages will be repeated, out of order, and backlogged;
- To troubleshoot problems, you need to look at the links across three components;
- has an additional set of high-availability storage for operation and maintenance.

> only has synchronous calls, low traffic, and strong consistency scenarios. Don’t use MQ just for the sake of “beautiful architecture.”

## 2. Two basic models
### 1. Queue model (RabbitMQ)
```
Producer → Exchange → Queue → Consumer（ack 后删除）
```
- The message is consumed and deleted from the queue after ack;
- supports complex routing (direct/fanout/topic/headers);
- has low single message latency and is suitable for task distribution and business events;
- has medium throughput, stacking capacity is limited by memory/disk.

### 2. Log model (Kafka)
```
Producer → Topic/Partition（追加写）→ Consumer Group（按 offset 消费）
```
- messages are appended by partition, **is not deleted due to consumption,** is retained by time/size;
- consumer maintains offset, which can be reset and replayed;
- order is only guaranteed within the partition;
- has high throughput and is suitable for logging, stream processing, and event tracing.

### 3. Other forms
- **RocketMQ**: CommitLog + ConsumeQueue, supports transaction messages, delayed messages, and retry queues;
- **Pulsar**: separation of storage and computing, multi-tenant, tiered storage;
- **Cloud messaging service**: SQS/SNS, Pub/Sub, operation and maintenance hosting but limited capabilities.

| Dimensions | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| model | queue | partition log | log + queue index |
| Throughput | Medium | High | High |
| Latency | Low | Lower (higher in batches) | Low |
| Sequence | Single queue | Single partition | Single queue |
| Replay | Difficult | Native support | Support |
| Transaction message | Not supported | Transaction producer (limited scope) | Native transaction message |
| Typical scenarios | Business tasks, complex routing | Logs, stream computing | E-commerce transactions, orders |

## 3. Core concepts
| Concept | Meaning |
|---|---|
| Producer | Sender, responsible for partition selection, retry, batch |
| Broker | Store and forward node |
| Topic | Logical classification |
| Partition / Queue | The basic unit of parallelism and sequence |
| Consumer Group | A group of consumers consumes a topic together, and the partitions within the group are not allocated repeatedly |
| Offset | The position of the consumer in the partition |
| Ack | Consumption confirmation, determines when the message can be deleted/submitted |
| Retention | Message retention time/size |
| Rebalance | Increase or decrease in consumers leads to partition redistribution |

**The upper limit of parallelism is determined by the number of partitions**: A partition can only be consumed by one consumer in the same consumer group. It makes no sense to add machines to exceed the number of partitions.

## 4. Delivery semantics
| Semantics | Behavior | Risks |
|---|---|---|
| At-most-once | At most once, may be lost | First ack and then process, network loss |
| At-least-once | At least once, may be repeated | Processing is successful but ack fails, try again |
| Exactly-once | Exactly-once | Realizable only within specific boundaries |

Realistic conclusion:
- **Most businesses use At-least-once + idempotent consumption**;
- Kafka's Exactly-once dependent transaction producer, `read_committed` and "read-process-write" are all closed loops in Kafka;
- As long as the downstream is the database/HTTP interface, end-to-end Exactly-once must rely on **business idempotence**, there is no free lunch.

## 5. Producer reliability
### 1. Confirm and retry
```properties
# Kafka 生产者关键配置
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
min.insync.replicas=2
delivery.timeout.ms=120000
```
- `acks=0`: It is considered successful when issued and may be lost;
- `acks=1`: The leader is written successfully, and may be lost if the leader is down;
- `acks=all`: All ISR confirmed, most secure;
- `enable.idempotence=true`: Broker side removes duplicates to avoid duplication caused by retries;
- `max.in.flight` can be combined with idempotence to improve throughput without disordering the order.

### 2. Partition and order
- Only when the same key enters the same partition can the messages of this key be ensured in order;
- Increasing the number of partitions will change the key mapping. **The existing key sequence may be interrupted**;
- Polling/sticky partition when there is no key, the order is not guaranteed.

### 3. Do not "double write"
```java
// 错误：数据库和 MQ 无法在同一个本地事务里
db.insert(order);
mq.send("order-created", order);  // 可能发送成功但事务回滚
```
Both results can be wrong:
- DB succeeds, MQ fails → the downstream will never receive it;
- MQ successful, DB rollback → the downstream received a non-existent order.

For the correct solution, see Section 8: **local message table (Outbox)** or **transaction message**.

## 6. Consumer reliability
### 1. When ack
```
拉取消息 → 执行业务 → 提交本地事务 → ack / 提交 offset
```
- ack first and then process: if the process crashes, the message will be lost;
- is processed and then acked: it may be consumed repeatedly (ack fails/times out) and needs to be idempotent;
- RabbitMQ uses `basic.ack`, Kafka turns off automatic submission and manually `commitSync`.

### 2. Idempotent consumption
Duplicate messages are inevitable, and the consumer must achieve the goal of "executing the same message multiple times with consistent results":
Commonly used methods for ```java
@Transactional
public void consume(OrderPaidEvent event) {
    // 唯一索引：message_id 或业务唯一键
    if (!dedupMapper.tryInsert(event.getMessageId())) {
        return;  // 已处理，直接忽略
    }
    orderMapper.markPaid(event.getOrderId());
    pointService.addPoint(event.getUserId(), event.getAmount());
}
```
:

| means | Description |
|---|---|
| unique index | is the most reliable, conflicts are considered duplicates |
| Deduplication table | records messageId + processing time, and is cleaned regularly |
| state machine | only allows legal state transitions (pending → paid) |
| version number | Bring the version when updating, old events will not take effect |
| is naturally idempotent | `SET status = 'PAID'` instead of `balance = balance + 1` |

### 3. Retries and dead letters
- failed retry requires **exponential backoff + random jitter** to avoid retry storm at the same time;
- sets the maximum number of retries, exceeding **DLQ (dead letter queue)**;
- Poison message (deserialization failure, logic failure forever) cannot be retried infinitely and blocks the partition;
- DLQ requires alarm, viewing, and replay tools.

```java
// 重试主题分级（示意）
int attempt = headers.getAttempt();
if (attempt < 5) {
    publish("order-paid-retry-" + (attempt + 1), msg, backoff(attempt));
} else {
    publish("order-paid-dlq", msg);
}
```

### 4. Rebalance
- Consumer join/leave/heartbeat timeout will trigger partition reallocation;
- consumption is suspended during rebalancing, and frequent rebalancing will significantly reduce throughput;
- Kafka focuses on `session.timeout.ms`, `heartbeat.interval.ms`, `max.poll.interval.ms`;
If - takes too long to process a single batch, it will exceed `max.poll.interval` and will be kicked out of the group;
- uses cooperative sticky allocation to reduce overall pauses.

## 7. Sequence issues
| Requirement | Solution | Cost |
|---|---|---|
| Globally ordered | Single partition/single queue, single consumer | Throughput limited |
| Ordered by business key | key hash to the same partition | Hotspot key may be skewed |
| Out-of-order | Multi-partition parallel | Fastest, but the business must be able to tolerate out-of-order |

Operations that easily disrupt the order:
- Try again after consumption failure, the latter one succeeds first;
- Multiple consumers consume the same business key;
- The production end retried and did not enable idempotence;
- key remapping after partition expansion.

When strict order is required, the consumer must also use the **serial number/version number** for verification, and cannot rely solely on MQ.

## 8. Transaction messages and Outbox
### 1. Local message table (Outbox)
Two implementations of ```
业务表 + outbox 表在同一个本地事务中写入
        ↓
中继器（定时任务 / CDC）读取 outbox 并发送到 MQ
        ↓
消费者幂等处理
```
```sql
CREATE TABLE outbox (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  aggregate_id BIGINT NOT NULL,
  event_type VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,  -- 0 待发送 1 已发送
  created_at DATETIME NOT NULL,
  INDEX idx_status_created (status, created_at)
);
```
```java
@Transactional
public void pay(long orderId) {
    orderMapper.markPaid(orderId);
    outboxMapper.insert(new OutboxEvent(orderId, "OrderPaid", payload));
}
```
 repeater:
- **polls**: `SELECT ... WHERE status = 0 LIMIT 100`, and updates the status after sending; multi-instance relays need to use `FOR UPDATE SKIP LOCKED` or preemption markers to avoid the same batch of messages being sent repeatedly;
- **CDC**: Debezium/Canal reads binlog and delivers directly, with lower latency.

Advantages: Does not rely on MQ transactions, the database is the only source of truth; Disadvantages: At least once delivery, the consumer must be idempotent.

### 2. RocketMQ transaction message
```
发送半消息（对消费者不可见）
  → 执行本地事务
  → 提交/回滚半消息
  → Broker 定时回查本地事务状态
```
 is suitable for "local transaction + message sending" strong binding scenario; the consumer end is still required to be idempotent.

### 3. Kafka transaction
```java
producer.initTransactions();
producer.beginTransaction();
producer.send(record1);
producer.send(record2);
producer.sendOffsetsToTransaction(offsets, groupId);
producer.commitTransaction();
```
 guarantees "multiple partition writes + offset commit" atomicity, but **does not include database transaction**.

### 4. Saga
Long transactions across multiple services:
- Each service performs local transactions and publishes events;
Perform compensation actions (refund, release inventory) when - fails;
- Orchestrated (with central coordinator) or collaborative (event-driven);
- must accept intermediate states and provide reconciliation and manual repair.

## 9. How to implement eventual consistency
1. **Define the consistency window**: Allow a few seconds/minutes to be inconsistent, and alarm if it exceeds;
2. **Idempotent + Retry + Dead Letter**: Ensure that the message is not lost or repeated;
3. **status is visible**: the front end displays "Processing" to avoid users mistakenly thinking it has failed;
4. **Reconciliation**: regularly compare the source and target (order vs points flow), and repair the differences;
5. **version/serial number**: Old events cannot overwrite new status;
6. **can be replayed**: events and offsets are retained, and problems can be replayed to fix them;
7. **Downgrade**: When the downstream is unavailable for a long time, suspend consumption or switch to manual work. Do not retry indefinitely to overwhelm the downstream.

> The final agreement is not to "don't care", but "to have a clear window, compensation, and reconciliation."

## 10. Monitoring and operation and maintenance
| Indicator | Description | Alarm suggestion |
|---|---|---|
| Consumer Lag | Number of unconsumed messages/delay | Alarm if it continues to increase |
| Production/consumption rate | Is it unbalanced? | Consumption < Production lasts N minutes |
| End-to-end delay | Production time → consumption completion | Exceeds SLO |
| Number of retries | Failure ratio | Sudden increase indicates downstream anomaly |
| DLQ quantity | Dead letters accumulate | >0 just follow |
| Rebalance times | Frequent rebalance | Sudden increase affects throughput |
| Partition tilt | Single partition traffic is too high | Hotspot key |
| Disk/retention | Storage water level | Near upper limit |
| ISR/replica | Replica synchronization status | Replica behind |

Other operation and maintenance points:
- It is recommended that the message body be < 1MB, large files should be stored in object storage, and messages should only be sent to the URL;
- turns on compression (lz4/zstd) to reduce bandwidth;
- Schema evolution must be compatible (Avro/Protobuf, backward/forward compatible);
- permissions: TLS, authentication, Topic-level ACL;
- Capacity: The number of partitions, the number of copies, and the retention time jointly determine the disk.

## 11. Selection suggestions
| Scenario | Recommended | Reason |
|---|---|---|
| Business events, task distribution, complex routing | RabbitMQ | Flexible routing, low latency |
| Logs, buried points, stream computing, need to replay | Kafka | High throughput, partition logs |
| E-commerce transactions, transaction messages, delayed messages | RocketMQ | Transaction/delayed messages native support |
| Multi-tenant, tiered storage | Pulsar | Storage and calculation separation |
| Don’t want to operate and maintain | Cloud MQ | hosting, but pay attention to the quota and locking period |

> Do not use Redis List as core MQ: there is no reliable ack, retry, dead letter, accumulation monitoring, and it is difficult to check when messages are lost.

## 12. Common misunderstandings
1. ❌ Using MQ, messages will not be lost: acks, manual ack, copy, and DLQ are all indispensable;
2. ❌ Exactly-once out of the box: only true within specific boundaries, still idempotent end-to-end;
3. ❌ Automatic ack is simpler: the message will be lost if the process crashes;
4. ❌ Just try again if it fails: poisonous messages will block the partition, and there must be an upper limit and dead letters;
5. ❌ Global order is very important: most businesses only need to be ordered by business keys;
6. ❌ The more partitions, the better: it increases the overhead of rebalancing, file handles, and metadata, and the order will be affected;
7. ❌ MQ can be used as a database: the retention period is limited, not long-term storage;
8. ❌ Consumers can expand indefinitely: parallelism is limited by the number of partitions;
9. ❌ Final consistency equals inconsistency: windows, compensation, and reconciliation are required;
10. ❌ No problem with dual-write DB and MQ: there is no local transaction guarantee, Outbox/transaction messages must be used.

## 13. Summary
The value of - MQ is **decoupling, asynchronous, peak clipping, and replay**, at the cost of complexity and final consistency;
- reliability formula: **production side confirmation + persistent copy + consumer side manual ack + idempotent + retry upper limit + dead letter**;
- order is only guaranteed within the partition/queue, and global order across keys has a throughput cost;
- For cross-service consistency, use **Outbox / transaction messages + idempotent consumption + reconciliation** first, and don’t imagine end-to-end Exactly-once.
